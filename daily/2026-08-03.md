## Technical Anatomy：一条视频数据 → 模型发版完整链路

### 数据形态

```text
视频（货架镜头） + prompt（数第二层有几瓶可乐）
+ CoT（定位 → 逐项数 → 汇总）+ response（5 瓶）
= 一条完整 SFT 数据（instruction-following data）
```

### SFT 训练机制（输入/输出/中间过程）

```text
输入：视频 → 均匀抽帧（8 帧）→ 视觉编码器 → 视觉 token
     + 时间位置编码（帧先后顺序）
     + prompt 文本 token
期望输出：模型逐 token 生成 CoT + response
Loss：teacher forcing 下逐 token 交叉熵 → 反向传播
```

### CoT 为什么重要

```text
只给 response → 模型学"视频 → 数字"映射 → 死记硬背
给 CoT → 模型学"定位 → 逐项数 → 汇总"推理模式 → 跨场景泛化
= 学会推理 vs 记住答案
```

### 八环节链路

```text
① 采集（你在）→ ② 数据条目生成（你在：prompt/CoT/response 合成）
→ ③ 质检（CoT 质检 Pipeline 迁移）→ ④ 混入训练集（数量→覆盖度，质量→信噪比）
→ ⑤ SFT 训练 → ⑥ 评测（Video-MME 等，闭环反馈端）
→ ⑦ 迭代反馈（评测决定下一轮采什么）→ ⑧ 合规评审 → 发版
```

**关键洞察**：这是闭环不是流水线。发版涨不涨直接取决于环节 1-3 的产出质量；"离我好远"是组织信息流问题（评测结果没有回流），不是价值问题。

### 四视角补充

- **算法视角**：CoT 数据教的是推理模式，怎么量化"模式"学会了？→ 换场景评测（跨场景泛化率）；loss 每 token 都来自标注，错标怎么污染训练？
- **工程视角**：抽帧密度 vs 上下文窗口（1h 视频 = 多少 token）；数据配比、去重（MinHash）；模板版本化保证可复现
- **策略视角**：数据量级 vs 质量的信噪比权衡；怎么证明"这批数据让计数能力涨了"（Ablation：有这批 vs 无这批）；评测回流机制设计

## 行业认知：基座模型 vs 业务适配（后训练工程师吐槽的本质）

### 核心机制

```text
1. 目标函数错位：预训练刷 benchmark（通用能力加权平均）
   vs 业务看场景指标（特定能力子分布密度）
   → 模型换代 = 能力权重重新分布，A 涨 B 跌，B 恰是业务依赖 → 分数涨业务不涨
2. 能力上限 vs 能力分布：scaling 提升上限 ≠ 业务依赖维度变密
3. "预训练不用业务数据"拆解：
   一半对（业务数据量级太小，对预训练 loss 贡献可忽略）
   一半不对（正确诉求是 benchmark 贴近业务场景，不是预训练喂业务数据）
4. 适配成本：失配期（新基座+旧适配=行为漂移=短期回退）
   + 适配债（每季度换版 → 永远追版本）+ 数据资产失效（旧 prompt 模板/CoT 格式不兼容）
```

### 结构性原因

基座公司竞争信号 = 排行榜（市场信号）；业务公司信号 = 业务指标（业务信号）。平台层与应用层的经典博弈——LLM 的"API 变更"更致命：变的是行为模式、推理风格、输出分布。

### 应对策略（可建立的竞争力）

```text
模型无关的数据管线：
├── prompt 模板版本化（每个基座版本一套模板，不互相覆盖）
├── 数据格式与模型解耦（CoT 标注规范独立于任何模型）
├── 评测分版本记录（不跨版本比分数，避免假象）
└── 业务评测集：真实业务场景抽样 → 换基座唯一决策依据（A/B）
    → 谁掌握业务评测集，谁有换基座否决权
```

## 学习与准备：LLM 数据集全景

- 梳理了预训练语料 / 后训练数据（SFT/偏好/RL）/ 训练期验证集 / 开发期验证集 / 测试集 / Benchmark 的关系与异同
- 三个关键区分：
  - 两个"验证集"同名不同物（训练流水线仪表盘 vs 评测体系考试）
  - 评测集 ⊇ Benchmark（benchmark = 公开标准化子集，内部评测集保密防泄漏）

- 关键认知：评测集构建（Eval Engineer）是独立岗位，自己的工作（质检 Gate / Eval Set 建设）已覆盖其核心职责
