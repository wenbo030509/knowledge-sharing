# 精读拆解方法论：事实-过程-方法三层法

> 建立于：2026-08-20
> 适用范围：**每一篇精读文章、每一个技术案例、每一次 Technical Anatomy**——读之前、读之中、笔记落盘前都要过一遍。
> 定位：这是"怎么学"的操作手册。与 learning-manifesto（为什么学）、Technical Anatomy 八层（学多深）、四视角（从哪些角度看）互补，本方法是**决定"学什么"**的拆解框架。

---

## 零、核心论断（先记住这一句）

> **数据集是载体，过程是现象，方法论才是弹药。**
>
> 案例的价值不在于它的数据有多新、多权威，而在于你能从它里面提取出多少**可以迁移到下一个场景**的方法。学完一个案例后问自己：如果我明天被放到一个全新领域，能用上今天学的哪几条？

---

## 一、三层定义

### 第一层：事实（Fact）——"是什么"

```text
定义：案例本身的静态数据、结论、参数
特征：具体的、数字化的、会过时的
例子：
├── SWE-bench 有 2294 个任务、12 个仓库
├── Claude 2 通过率 1.96%
├── RealReplicaBench 的 160 万对话 → 107 任务
└── 美团人机一致率 99%

处理方式：理解即可，不背。面试不会考"数字是多少"，
但数字背后的"为什么是这个规模/这个比例"要理解
```

### 第二层：过程（Process）——"怎么演变"

```text
定义：案例从发生到现在的演进轨迹、关键转折点
特征：时间线上的、故事性的、行业阶段性的
例子：
├── SWE-bench 从 1.96% → 93.9% → 污染失效 → Pro 抗污染设计
├── Verified 发布 → 饱和 → OpenAI 审计 → 停用
├── 美团数字站长从 20 个指标 → 200 个指标
└── Agent 评测从"答案评测" → "行为评测"

处理方式：用来建立"行业演进感"——面试谈行业判断时，
过程是你的论据来源。但过程本身不直接回答"你会不会做"
```

### 第三层：方法（Method）——"能带走什么" ⭐

```text
定义：从案例中提炼的、可迁移到任何场景的原则/流程/模式
特征：与具体领域无关的、可复用的、面试可直接输出的
例子：
├── 评测任务从真实场景提炼，不靠设计（三阶段过滤）
├── 判分要双条件：修复有效 + 不回归（FAIL_TO_PASS + PASS_TO_PASS）
├── 评测环境必须可复现（环境固化 = 观测是评测的基石）
├── 静态公开评测集有寿命，要预埋退役机制（污染是宿命）
└── 评测结果受框架影响，要区分"模型贡献"和"框架贡献"

处理方式：笔记的核心产出。每条方法要能配一句
"面试说法"——能说出口才算提取成功
```

## 二、操作流程（每次精读按这个走）

```text
读之前（1 分钟）
├── 预判三层：这篇的"事实"大概是什么？
│   可能的"方法"是什么？带着问题读
│
读之中（边读边标）
├── 标注三类内容：哪些是事实（数字/结论）、
│   哪些是过程（演进/转折）、哪些是方法（原则/模式）
│
笔记落盘前（最关键）
├── 三层分离检查：
│   ├── 笔记里的事实是否过多？（>30% 说明停留在第一层）
│   ├── 过程是否只作为"背景"而非"论据"？
│   └── 方法是否足够？每条方法是否配了面试说法？
│
落盘后（5 分钟）
├── 可迁移性检验：把方法抄出来，删掉案例名字，
│   如果还能读懂 → 成功；如果看不懂 → 方法还带着
│   案例的壳，提炼不够
```

## 三、方法层的提取模板（每条方法长这样）

```text
【方法】评测任务从真实场景提炼，不靠设计
【来源案例】SWE-bench / RealReplicaBench
【适用场景】任何评测集建设的冷启动
【面试说法】"我会从真实使用数据里沉淀任务，
  用可复现性和结果可判定性过滤，而不是拍脑袋设计题目"
【反面案例】"SWE-bench 用三阶段管线过滤了 PR"（还带着案例的壳）
```

## 四、检验标准（五问）

读完任何一篇文章/案例，用这五问自检：

```text
① 我能说出这篇的 3 条以上可迁移方法吗？（数量）
② 这些方法删掉案例名还能独立成立吗？（纯度）
③ 每条方法我都能配一句面试说法吗？（可输出性）
④ 如果把我放到一个全新领域，我能用上几条？（迁移性）
⑤ 我记住的更多是数字还是原则？（注意力分配）

< 3 条方法 → 这篇读得不够深，回去重提
方法带案例壳 → 提炼失败，重新抽象
全是数字 → 停在事实层，危险信号
```

## 五、完整示例：SWE-bench（三层分离示范）

```text
事实层（理解即可，不背）
├── 2294 任务 / 12 Python 仓库 / 三阶段管线 / Docker 评测
├── Claude 2: 1.96% → Verified 93.9% → Pro 初始 23.3%
└── SWE-smith: 52k 实例 / 128 仓库 / 40.2% Pass@1

过程层（建立行业演进感）
├── 2023 发布（几乎无人能解）→ 2024 Verified（行业标配）
├── → 2025 Pro（抗污染设计）→ 2026 验证器被审计（32% 错误率）
└── 完整生命周期：诞生 → 饱和 → 失效 → 迭代

方法层（笔记核心产出，5 条可迁移）
├── 1. 评测任务从真实场景提炼：真实数据 + 属性过滤 + 执行验证
├── 2. 判分双条件：修复有效（FAIL_TO_PASS）+ 不回归（PASS_TO_PASS）
├── 3. 评测环境可复现：环境固化 + 结果缓存
├── 4. 静态评测集有寿命：污染是宿命，预埋退役和抗污染机制
└── 5. 框架贡献与模型贡献分离：报告成绩要标注评测框架
```

## 六、常见误区

```text
误区 1：只记事实 ——"SWE-bench 有 2294 个任务"
→ 面试官问"你会怎么建评测"时一个字用不上
→ 事实只服务于"理解为什么这么设计"，不服务于输出

误区 2：只背过程 ——"Verified 从 22% 涨到 93.9%"
→ 能讲故事，但讲不出"你会怎么做"
→ 过程是论据，不是答案

误区 3：把案例当方法 ——"我也用三阶段管线"
→ 方法还带着案例的壳，迁移时生搬硬套
→ 提炼标志：删掉案例名后是否还成立

误区 4：方法提取后不连接自身 —— 提取完就结束
→ 每条方法必须连接：我的项目里有对应物吗？
→ 连接标志：能说出"这对应我的 XX 环节"
```


## 八、一句话收束

> 每篇笔记落盘前问最后一个问题：**"这篇里的哪三条，是我下个月换一个领域还能用的？"** 答得出来，这篇就完成了它的任务。
