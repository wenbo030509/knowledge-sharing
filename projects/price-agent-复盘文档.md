# Price Agent 面试演示逐字稿

---

所以我希望今天的面试和传统的面试不太一样，可能更像是一个交流会，一方面是我会尽全面的展示我自己，另一方面您也可以随时打断随时向我提问，考察我的个人能力，我们一起来了解和学习这个项目。首先，这个项目的背景源自于我想把最近这段时间所了解学习的知识到以及个人思考融合起来，所以综合考虑借助了电商ai搜索的业务场景来落地。目前来看ai的出现对传统搜索进行了全面的重构，从单一的结果列表，到现在直接完成了决策和结果展示。大大提高了搜索效率和用户体验。

## Part 0：概述（1 分钟）

---

**我**：


我用"智能比价购物"作为业务载体，把 Agent 领域一些核心概念和能力——function calling、ReAct、Plan-Execute、RAG、评估闭环——串成了一条可演示、可讲解、可复用的完整链路。

为什么选购物比价呢？因为它的场景天然有层次。，比如查单品价格、多品对比、模糊需求推荐、引导式购物——四种用户状态，恰好对应四种 Agent 模式。而且跨平台并行查询、语义搜索、知识库增强，这些工具调用的复杂性在一个领域里全都能覆盖到。

一句话概括架构的话：用户输入 → 意图分类 → 路由到四种模式之一 → 工具执行层 6 个 tool → Trace 事件流式推前端可视化。

好，我直接通过 4 条 query的查询， 从简单到复杂，来演示每一种 Agent 模式的核心能力。

---

## Part 1：智能查价 · ReAct（1-2 分钟）

---

**我**：第一条，也是最简单的一条——"iPhone 15 各平台最低价是多少"。

（演示：点击 ReAct 快捷按钮，或输入 query，观察推理面板）

先看发生了什么。系统第一步不是直接调工具——它先做意图分类。`_detect_intent` 分析这句话：有明确型号 "iPhone 15"，没有对比词，没有场景词，有"最低价"这种查价词 → 判定为 query，走 ReAct 模式。

ReAct 模式是什么？它的核心循环是 Thought → Action → Observation。Agent 先思考"我要查 iPhone 15 的价格，应该调用 multi_platform_comparison"→ 执行这个 Action → 拿到返回结果 Observation → 再思考"四个平台都有数据，我需要对比输出最低价"→ 最终回答。

这里有一个细节值得注意：当 Agent 调用 `multi_platform_comparison` 这个工具时，背后是 ThreadPoolExecutor 并行打京东、淘宝、拼多多、苏宁四个平台。不是串行等 4 次，而是一次调用并行返回。你可以在推理面板里看到单次 tool_call，但实际上它命中了 4 个数据源。

（指向前端推理面板）

推理面板右侧展示的是什么？是每一步 Thought → Tool Call → Observation 的完整链路。这不是事后加的日志，是嵌入在 Agent 内部的结构化 Trace 事件，通过 SSE 流式推送到前端。

这是第一个能力：**Agent 不是黑盒，每一步思考和执行都可追溯。**

好，这是最简单的场景——我知道要查什么，Agent 帮我去查。但如果我不知道该买哪个呢？

---

## Part 2：多品对比 · Plan-Execute（2 分钟）

---

**我**：第二条 query——"iPhone 15 和小米14 哪个更值得买"。

（演示：点击 Plan-Execute 快捷按钮，或输入 query）

这条 query 触发了 Plan-Execute 模式。为什么？因为意图分类检测到两个商品型号，而且有"更值得买"这种对比词，这是 comparison 意图。

Plan-Execute 和 ReAct 有什么区别？ReAct 是一边想一边做，Plan-Execute 是先规划、再执行、最后综合。分三个阶段。

Phase 1：计划生成。Agent 用 LLM 把用户问题拆成结构化计划。来看——

（指向推理面板中的 DAG 图）

它拆出了什么？Step 1 查 iPhone 15，Step 2 查小米 14，Step 3 综合对比。注意 Step 1 和 Step 2 之间没有依赖关系——它们可以并行执行。Step 3 依赖于前两步的结果——它必须等前两步都完成。这就是一个 DAG，有向无环图。

Phase 2：执行。看这个 DAG 图——Step 1 和 Step 2 的两个节点同时从 pending 变成 running，再同时变成 done。这就是并行执行。然后 Step 3 开始串行执行。每个节点上显示工具名、目的描述、状态。鼠标悬停看完整信息。

（指向 DAG 并行节点）

为什么要这样设计？因为如果我们把三个步骤串行执行，用户要多等一倍的时间。Plan-Execute 的核心价值就是把**计划编排**和**工具执行**解耦——先看清楚哪些步骤可以并行，再调度执行。

Phase 3：综合回答。执行完所有步骤后，LLM 把前两步的价格数据和第三步的知识增强结果综合成对比结论，告诉用户"哪个更值得买、为什么"。

这里还有一个技术细节：Phase 2 的每个 Step 内部其实是一个 mini-ReAct 循环。也就是说 Plan-Execute 不是替代 ReAct，而是在 ReAct 上面加了一层编排。

第二个能力：**多步骤任务可以自动拆解 DAG，并行和串行混合调度，前端实时可视化。**

好，前两个都是"我知道查什么"的场景。那如果"我不知道该买什么"呢？

## Part 3：场景推荐 · ReAct + 语义召回（1-2 分钟）

---

**我**：第三条——"5000以内拍照好的游戏手机推荐"。

（演示：点击 Recommend 快捷按钮，或输入 query）

注意，这句话和前面两条有一个本质区别：它没有提到任何具体商品型号。传统搜索引擎怎么处理这句话？它会把"拍照""游戏""手机""5000"拆成关键词去数据库做 like 匹配。但问题来了——数据库中可能没有任何商品描述里包含"拍照好的游戏手机"这个短语。

我们的 Agent 怎么处理？意图分类识别到场景词"拍照""游戏"和预算词"5000"→ 判定为 recommendation → 走 ReAct 模式，但带上 intent_hint = "recommendation"。

这个 hint 告诉 Agent：你应该用 `semantic_product_search` 这个工具，而不是 `multi_platform_comparison`。这两个工具的背后逻辑完全不同——前者做语义召回，后者做精确匹配。

`semantic_product_search` 内部是向量召回 + 规则过滤的混合检索：
- 向量召回：把用户 query 转成 embedding，和商品 embedding 做余弦相似度匹配，找到语义相关的商品
- 规则过滤：预算、品牌、处理器这些硬约束通过规则过滤——你不能因为语义相近就给用户推荐超预算的商品

而且，这个模式下 Agent 还可以调用 RAG 工具——`search_product_knowledge`——把手机领域的专业知识注入到推荐理由中。比如"骁龙 8Gen3 是当前旗舰芯片，游戏性能强""大底传感器对拍照更重要"。

第三个能力：**传统搜索靠关键词匹配，Agent 靠语义理解加领域知识。向量召回 + RAG 是 Agent 从"查到"到"查对"的关键。**

好，三种模式都展示了 ReAct 或 Plan-Execute 的变体。接下来是最复杂的一种——用户完全不知道自己要什么。

## Part 4：引导购物 · 状态机（2-3 分钟）

---

**我**：第四条——"想买个手机，帮我看看有什么"。

（演示：点击 Shopping 快捷按钮，或输入 query）

这句话没有任何型号、没有预算、没有场景。如果交给 ReAct，Agent 会不知道调什么工具，可能乱搜一通。

所以意图分类把它路由到了 shopping 模式，进入一个 6 状态的状态机。

（指向前端购物步骤条）

第一轮：Agent 打招呼，然后追问第一个必填槽位——"主要是打游戏、拍照，还是日常使用？"这不是 LLM 自己想出来的话，是行业配置里定义的槽位问题。

我来回答"打游戏"。Agent 提取到 primary_use_case = gaming，槽位已填。

第二轮：必填槽位已满足，Agent 追问可选槽位——"预算大概多少呢？"这是把用户从模糊逐步带到精确的过程。

我说"5000以内"。Agent 提取到 budget_max = 5000。

第三轮：所有必填已满足，Agent 进入 searching 状态，调用 semantic_product_search 搜索，然后展示推荐列表。

现在我在推荐阶段。我可以说"对比前两个"——Agent 进入对比状态，调用 LLM 逐维度分析两个商品。我可以说"便宜点的"——Agent 重新搜索。我可以说"就这个吧"——Agent 结束购物。

（指向购物步骤条的状态变化）

前端实时追踪状态流转：slot_filling → searching → recommending → comparing。

这个状态机有 200 行代码。为什么不直接用 LangGraph？三个原因：第一，这个场景的状态分支非常明确，200 行代码比引入一个 10 万行的框架更可控；第二，Trace 事件需要精确控制每个状态变化的颗粒度；第三，避免框架 API 变动带来的维护成本。**场景越垂直，框架的收益越低。**

这里有几个边界处理我想展开讲一下，因为它们是实际踩过的坑：

第一个坑：**无关输入怎么办？** 用户在 slot_filling 阶段说"今天天气不错"。按朴素逻辑，这也算一轮对话，应该消耗追问次数吧？但我们决定不计入。因为消耗追问次数等于惩罚用户闲聊，3 次之后就强行搜索了，体验很差。所以只有提取到有效槽位才算一次有效追问。

第二个坑：**路由怎么保持？** 购物模式激活后，用户再输入"打游戏""预算4000"，按正常意图分类会被误判为 recommendation——因为"打游戏"是场景词。所以我们在 run() 入口加了判断：如果购物状态机已激活，后续所有输入直接路由到 `_guided_shopping`，不再经过意图分类。这是从 bug 中修复的。

第三个坑：**话题怎么切换？** 购物途中用户说"帮我查 iPhone 15 价格"，这是想退出购物模式做精确查询。但"算了帮我查 iPhone 15"里的"算了"又是结束词又是新查询——不能直接判为结束，应该判为话题切换。优先级是：话题切换 > 结束购物。而且还要判断提到的型号是不是当前推荐列表里已有的——如果是，说明用户在对比推荐商品，不是要退出。

第四个能力：**多轮对话不等于把历史拼接进 prompt。真正的对话 Agent 需要状态机管理上下文、控制流程分支、处理边界情况。**

好，四种模式演示完了。最后讲评估。

## Part 5：评估体系（3 分钟）

---

### 5.1 为什么 Agent 测试是传统方法失效的难题

**我**：最后讲评估。这可能是面试官最关心的问题之一。

传统软件测试是"输入 A，断言输出 B"。Agent 有三个问题让这个模型失效：

第一，**非确定性**。同样的输入，LLM 可能输出不同措辞、不同工具调用顺序。"iPhone 15 和小米 14 哪个好"——Agent 可能先查 iPhone 再查小米，也可能反过来。顺序不影响结果，但如果你用精确字符串匹配断言，两个都算"错"。

第二，**状态空间爆炸**。多轮对话中用户输入的组合是指数级的。M5 购物状态机有 6 个状态，用户在每个状态里可以说任何话——有效槽位、无效闲聊、话题切换、结束词。6 个状态 × 每状态 5+ 种输入类型 = 至少 30 种分支组合。传统自动化测试需要每条路径写一个 case——但 30 个 case 只覆盖了最基础的分支。

第三，**怎么定义"对"？** Agent 说"iPhone 15 京东卖 7999 元"——这个价格对不对？你需要 Ground Truth。但 Ground Truth 从哪来？人工标注成本太高，且电商价格实时在变。

这三个问题决定了：Agent 的评估不能照搬传统测试方法论。

---

### 5.2 两层评估架构

我设计了两层结构。

**第一层：tests/——独立模块验证。** 开发期手动跑，秒级反馈。大部分不需要 LLM 调用。

（可展示 tests/ 目录）

| test 文件 | 验证内容 | 数量 |
|---|---|---|
| `test_react_engine.py` | 滑动窗口、意图分类、ReAct 循环、ShoppingContext 状态机 | 10 |
| `test_trace.py` | Trace 事件创建/序列化/SSE 流式 | 72 |
| `test_m1_config.py` | 行业配置加载、Schema 验证、默认值补齐 | 8 |
| `test_m2_recall.py` | 向量召回、规则过滤、混合检索、开关降级 | 5 |
| `test_m3_rag.py` | 知识库索引、BM25+语义混合检索 | 6+16 回归 |
| `test_m5_shopping.py` | 购物状态机、意图分类、槽位提取、路由持久 | 9+33 回归 |

每个文件都可以独立运行：`python3 tests/test_m5_shopping.py`，10 秒出结果。

**第二层：eval/——评估框架回归套件。** 需要 LLM 调用的测试放这里。由 `run.py` 统一编排调度，自动生成 JSON 报告。

`run.py` 里定义了 9 个阶段，按依赖层级编排：

| 阶段 | 内容 | LLM 依赖 | 案例 |
|---|---|---|---|
| P0 单元 | DB CRUD、评分逻辑、复杂度检测、自反思消息 | 无 | 43+ |
| P1 属性提取 | LLM 从 query 解析商品名/颜色/内存 | 单次调用 | 17 |
| P2 端到端 | 完整 ReAct/Plan-Execute 循环 + 幻觉检测 | 多轮 | 17 |
| P3 边界 | 不存在商品、歧义输入、空输入、矛盾需求 | 多轮 | 15 |
| P4 基准 | 聚合同 session 所有阶段，多维指标报告 | 无 | — |
| P5 优化 | 自反思纠错、System Prompt 质量 | 多轮 | 13 |
| P6 图片 | 图片搜索工具注册 + 多模态识别 | 多轮 | 10+ |
| IT3C | 行业三部曲回归 | 混合 | 51+ |

关键设计：P0 不需要 LLM，改了代码立刻跑，1 秒出结果。P2 需要多轮 LLM 调用，一次跑几分钟。**分层意味着改了什么就验证什么，只有发版前跑全套。**

### 5.3 评估框架的四个核心设计

**设计 1：Ground Truth 不靠人工标注。** eval 框架的核心创新——直接从 SQLite 数据库计算标准答案。`compute_cheapest()` 查 SQL 找真正的最低价，`compute_all_prices()` 列出所有平台价格。Agent 的回答里提取价格数字，跟 Ground Truth 比对，容差范围内算对。不需要人工标注一条数据。

**设计 2：幻觉检测是硬指标，不是软评价。** `detect_hallucination()` 从 Agent 回答中提取所有 ≥2000 的价格数字，跟 Ground Truth 交叉比对，5% 容差。Agent 说了数据库里不存在的价格 → 标记为幻觉失败。这是自动化、可量化的硬指标，不是"感觉回答不太对"的主观判断。

**设计 3：P4 基准报告的 7 维度拆分。** 不从单一通过率评判 Agent。每个阶段输出不同维度的指标：基础功能（P0）、参数提取（P1）、答案正确性（P2）、幻觉率（P2）、优雅降级（P3）、自反思（P5）、System Prompt 遵循（P5）。**单一数字掩盖问题，维度拆分才能精准定位。**

**设计 4：Session 机制让全流程可追溯。** `run.py` 每次运行生成 session ID，所有阶段共享。P4 自动扫描同 session 报告，聚合生成基准报告。不同 run 之间可以横向对比——"这次 PR 改了意图路由，P2 通过率从 100% 降到 94% → 需要排查"。

### 5.4 评估驱动开发的真实案例：M5 的三个坑

（这里可以和 Part 4 的演示呼应）

M5 购物测试从 6 个 case 长到 9 个。新增的 3 个 case，每个都对应一个实际踩到的坑：

**坑 1 → Case 7：话题切换与结束检测。** 线上发现："算了帮我查 iPhone 15 价格"——"算了"是结束词，"iPhone 15"是具体型号。最初先判结束 → 购物退出 → 下一条消息才走 ReAct。修复为话题切换优先级高于结束检测。加的 test case 覆盖了 12 个子场景：纯结束/结束+查询/纯闲聊/型号切换/候选内型号等全部组合。

**坑 2 → Case 8：无关输入消耗追问次数。** 用户说了两次"天气不错""你好"后，question_count 到 3 → Agent 跳过追问直接搜索了。修复为只统计有效槽位提取。加的 test case 验证：连续 2 轮无关输入 + 1 轮有效输入的正向/反向路径。

**坑 3 → Case 9：路由被意图分类覆盖。** 购物激活后用户说"打游戏"，被 `_detect_intent` 判为 recommendation → 购物上下文丢失。修复为激活后跳过意图分类。加的 test case 验证：续对话/话题切换/结束退出 3 个场景的路由正确性。

**评估不是事后的质量检查，是开发过程中的护栏。坑踩一个，case 加一个，不重复犯同一个错误。**

---

### 5.5 tests/ 和 eval/ 的分工哲学

最后讲一个架构决策：为什么是两层，而不是全放一个框架里？

```
tests/  → 第一道防线：模块级、秒级反馈、mock、开发期每次改动都跑
eval/   → 第二道防线：Agent 级、需要 LLM、分钟级、PR 或发版前跑
```

这个分工背后的工程判断：**Agent 系统的质量保障，必须在不依赖 LLM 的测试上投入更多。** LLM 调用慢、贵、不确定——你没法在每次改代码后等 5 分钟跑完 50 个 case。只有把不依赖 LLM 的测试跑快了，开发者才愿意频繁跑。频繁跑测试 → 快速发现问题 → 不让问题累积。

实际数据：最近一次全量评估（2026-05-14）166 个可评分 eval case，综合通过率 94.6%（157/166）。其中 P0（无 LLM）97.7%、P2（端到端）88.2%。失败案例集中在 P1 属性提取（3 个，苹果别名类）和 P2 端到端（2 个，最便宜判断/平板幻觉）——这些恰是 LLM 表现最不稳定的地方，也是下一步优化的方向。后续 Skills 架构验证（2026-05-26，P0/P1/P2/P3/P5）综合通过率提升到 95.9%。

好，以上就是评估体系的全部内容。

## 总结（收尾）

---

**我**：回到最开始那句话——AI 搜索重构了传统搜索，Agent 重构了 AI 应用。

这个项目就是把"重构"两个字拆成了可执行的七个层次：Function Calling 工具层、ReAct 推理循环、Plan-Execute 编排调度、RAG 知识增强、ShoppingContext 状态机交互、Trace 可观测性、Eval 评估闭环。

七层，每一层都有代码、有测试、有可视化。载体是比价购物，但我真正想展示的是：**Agent 不是调个 API 就完事了。它是一个需要架构设计、状态管理、边界处理、评估体系的系统工程。**

谢谢，有什么问题可以随时问。

## 附录：面试官可能提问的问题

### 架构设计

**Q1：你为什么设计了四种执行模式，而不是一个通用 Agent？**

因为用户买手机的决策状态完全不同。目标明确的"查 iPhone 15 价格"需要的是一次性多平台并行查询；纠结对比的"小米14 和 iPhone 15 哪个好"需要的是 DAG 拆分加并行执行再综合；模糊需求的"5000 以内拍照好的推荐"需要的是语义召回，不是精确匹配；完全不懂的"想买个手机"需要的是一轮一轮引导收敛。

如果把四种场景塞进一个 prompt，让 LLM 自己判断怎么处理——那 LLM 的决策质量是不可控的。显式路由意味着：我清楚每一种输入会走哪条路径，我可以为每条路径独立优化、独立测试、独立排查问题。代价是维护四套逻辑，收益是可控、可调试、可优化。这是一种用代码复杂度换取行为确定性的设计选择。

---

**Q2：这套系统具体是如何触发不同执行模式的？为什么用关键词规则而不是让 LLM 做意图分类？下一步怎么优化？**

这是一个非常核心的问题。我从三个层面来回答：触发机制的产品逻辑、为什么选规则而不是 LLM、以及下一步的优化方向。

---

**一、触发机制的本质：识别用户处于购买决策的哪个阶段**

这不是一个技术问题，是一个用户行为理解问题。买手机的人天然有四种状态：

| 用户状态 | 典型话术 | 心里在想什么 |
|---|---|---|
| 目标明确 | "iPhone 15 最低价多少" | 已经选好了，就差比价 |
| 犹豫对比 | "小米14 和 iPhone 15 哪个好" | 二选一，需要决策依据 |
| 有方向没目标 | "5000以内拍照好的推荐" | 知道要什么，不知道买什么 |
| 完全没方向 | "想买个手机，帮我看看" | 需要人引导 |

**这四种状态不是我们定义的，是用户真实存在的。** 我们只是识别它，然后匹配最优的交互方式。识别的实现目前是 `_detect_intent()` 函数——关键词 + 正则匹配，约 60 行代码。核心逻辑：

```
有购物词(买/想买/挑/选) + 无型号 + 无场景词 + 无预算词 → shopping
有场景词 or 预算词 or 推荐词 → recommendation
有多商品 or 对比词 → comparison
有单型号 + 查价词 → query（ReAct 兜底）
```

---

**二、为什么不是让 LLM 做意图分类？三个产品决策层面的理由**

**第一，确定性。** "想买个手机"必须每次都路由到 shopping，不能说 95% 的概率走 shopping、5% 的概率走 recommendation。意图分类的错误不是"回答不够好"——是走了完全错误的交互模式。用户说"想买个手机"，Agent 去调 `multi_platform_comparison` 搜一圈返回空——用户会困惑"我还没说要什么，你怎么就开始搜了"。对于模式路由这种决策，确定性比灵活性更重要。

**第二，零成本零延迟。** 关键词匹配不需要调 LLM，0 token，0 毫秒。如果用 LLM 做分类，每次对话多一次 API 调用，多 200ms 延迟，多约 0.001 元成本。单次无所谓，积少成多。对于高频调用路径，能省则省。

**第三，可维护。** 关键词表是透明的——加一个场景词、改一个触发条件，改一行代码，效果立即可验证。LLM 分类是改一句 prompt，行为可能变也可能不变，只能靠大量 case 回测。可维护性的差距在快速迭代阶段会被放大。

---

**三、关键设计：购物模式激活后的路由保护**

这里有一个从 bug 中长出来的设计，值得展开讲。

**问题**：购物模式激活后，用户说"打游戏"——这是对"主要什么用途"的正常回答。但 `_detect_intent()` 会把"打游戏"判为 recommendation（因为"游戏"是场景触发词），然后路由到 ReAct 模式，购物上下文丢失。

**修复**：在 `run()` 入口加了判断——如果 `shopping_context.phase != "greeting"`（购物已激活），跳过意图分类，直接进 `_guided_shopping()`。

**背后的产品原则**：**一旦用户进入了一个需要上下文的交互模式，就不要因为单条消息的字面含义而切换模式。** "打游戏"在购物上下文中是槽位信息，在搜索上下文中是推荐需求。同一条消息，在不同模式下含义不同。路由系统必须感知当前状态，不能只做字面匹配。

同样的逻辑还处理了两个边界：
- **话题切换优先于结束**：购物途中用户说"算了帮我查 iPhone 15 价格"——"算了"是结束词，"iPhone 15"是具体型号。如果先判为结束购物 → 购物退出 → 用户的下一条消息才走 ReAct。但用户本意是"退出购物，立刻查价格"。所以话题切换检测优先级高于结束检测。
- **候选中型号不算切换**：如果用户说的型号正好在推荐列表中（比如购物推荐了小米 14，用户说"小米 14 怎么样"），不算话题切换——用户在对比推荐商品，不是要退出。

---

**四、为什么不做一个"通用模式"，让 LLM 全权判断？**

让 LLM 自己判断"用户是什么状态、该用什么策略、该调什么工具"——这是在用一个不可靠的决策者去完成一个不容出错的任务。

LLM 可能把"想买个手机"理解为推荐需求，可能把"iPhone 15 和小米 14 对比"理解为两个独立的查价任务。每次决策的不确定性会层层放大——模式选错 → 工具选错 → 回答偏离用户意图 → 用户困惑和信任丧失。

**显式路由的本质是用代码的确定性换取 LLM 的不确定性。** 代价是维护关键词库，收益是行为可控、可调试、可优化。这是 Agent 工程中最重要的 trade-off 之一。

---

**五、当前方案的局限和下一步优化方向**

坦率说，纯关键词路由也有天花板。我设想的优化方向是 **两级路由**：

```
用户输入 → 关键词规则粗筛（快速、确定、覆盖 95% 场景）
                ↓
         高置信度匹配？
        /          \
      是            否（长尾表达、多意图混合、新品类）
       ↓            ↓
    直接路由      LLM 语义分类兜底
                         ↓
                  路由结果 + 记录日志
                         ↓
              定期 Review → 高频长尾 case → 沉淀为规则
```

**两级路由的核心思想**：规则负责高频、确定、已知的场景；LLM 负责低频、模糊、未知的场景。两者不是替代关系，是互补关系。

具体要解决的三个问题：

1. **覆盖长尾表达**。"给安利个手机呗"、"求推荐"、"有没有好用的"——这些口语化、网络化的表达，关键词库不一定全覆盖。第一版先补关键词，但如果长尾表达太多，维护成本就会超过 LLM 分类的成本——到那个拐点时就应该引入 LLM 兜底。

2. **多意图混合**。"推荐游戏手机，顺便和 iPhone 15 对比一下"——这句话既有 recommendation（推荐+场景词）又有 comparison（对比+型号）。当前规则只能选一个主意图。如果用户量上来后混合意图占比高，就需要 LLM 理解"先推荐、再对比"的先后顺序，甚至拆成两阶段任务。

3. **跨品类扩展**。当前关键词是为手机品类设计的。扩展到笔记本电脑时，"显卡"是场景词、"轻薄"是场景词——需要重新梳理关键词库。长期看，让 LLM 直接理解品类无关的意图（"推荐"、"对比"、"模糊探索"）比每个品类维护一套关键词库更可持续。

**引入 LLM 兜底的时机判断**：当关键词库的维护成本 > LLM 分类的调用成本时，就应该引入两级路由。具体量化：如果每周需要花超过 2 小时维护关键词、长尾 case 占比超过 10%、跨品类扩展频繁——这三个条件满足任意一个，就是引入 LLM 兜底的拐点。

**从 LLM 兜底中学到的长尾 case 怎么回流**：LLM 分类的结果不是"分类完就完了"。定期 Review LLM 兜底的 case → 分析高频长尾表达 → 把这些表达的关键词补回规则层。这样规则层会随着时间越来越精准，LLM 兜底的调用量会逐步收敛。**这本身就是一个数据飞轮——用 LLM 发现规则盲区，用规则降低 LLM 调用量。**

---



**Q3：Plan-Execute 模式中，你怎么决定哪些步骤可以并行、哪些必须串行？**

不是靠代码规则判断的，是靠 LLM 在 Phase 1 生成的计划决定的。LLM 分析用户问题后输出结构化 JSON，每个步骤可以声明 `depends_on` 字段引用前置步骤。DAG 渲染时，没有 `depends_on` 的步骤全部放入"并行组"，有依赖关系的步骤按拓扑序放入"串行组"。

举例：查 iPhone 15 和查小米 14 没有依赖 → 并行。综合对比依赖前两步的结果 → 串行，排在前两步之后。这个设计的巧妙之处在于：代码不做任何领域假设，并行/串行的决策权完全交给 LLM 的语义理解。换一个领域，LLM 自然能理解该领域的依赖关系。

---

**Q4：Shopping 状态机为什么是 6 个状态？状态之间是怎么流转的？**

6 个状态覆盖了从首次对话到结束的完整生命周期：

```
GREETING → SLOT_FILLING → SEARCHING → RECOMMENDING → COMPARING → FOLLOW_UP
```

GREETING 只在首次激活时经过，立即转入 SLOT_FILLING。SLOT_FILLING 有三个出口：必填槽位全满足 → SEARCHING；追问次数超限 → SEARCHING（强制）；还有可选槽位 → 追问。SEARCHING 完成后 → RECOMMENDING。RECOMMENDING 阶段用户可以说"对比一下" → COMPARING，也可以说"便宜点" → 重新搜索，也可以结束。COMPARING 完成后 → FOLLOW_UP，继续处理后续指令。

设计要点：每个状态只做一件事，状态的出口条件明确。代码中每个 `if ctx.phase == "xxx"` 块都是一个独立的处理逻辑，不会和别的状态耦合。

---

**Q5：这个项目如果要支持一个新的商品品类（比如笔记本电脑），需要改哪些地方？**

只需要加一份配置文件 `config/industries/laptop.py`，定义 shopping_slots、compare_dimensions、extract_keywords、processor_normalize。Agent 代码一行不用改。意图路由、状态机流转、工具调用全部通过 `industry_config` 驱动。这是 M1 行业配置框架的核心价值——Agent 能力和行业知识解耦。

### 技术选型

**Q6：为什么自研 Agent 框架，而不是用 LangChain/LangGraph？**

三个层面回答。代码量层面：核心 ReAct 循环不到 100 行，Plan-Execute 编排不到 100 行，ShoppingContext 状态机不到 200 行，加起来 400 行。引入 LangGraph 要理解 StateGraph、Node、Edge、ConditionalEdge 概念，代码量未必更少，调试反而更复杂。可控性层面：Agent 的 Trace 事件流需要精确控制，自研可以在任何位置插入 trace 调用。依赖风险层面：LangChain API 变动频繁，400 行自研代码比 10 万行框架更可控。核心判断：**场景越垂直、需求越定制，框架的收益越低，自研的性价比越高。**

---

**Q7：为什么选择 DeepSeek 和豆包，而不是直接用 GPT-4？**

成本和延迟。这是一个需要多轮 LLM 调用的系统——意图分类 1 次、ReAct 每轮 1-2 次、Plan-Execute 每个 step 多次、对比还需要一次综合调用。实际策略是多模型路由：ReAct 循环用 DeepSeek V4 Flash（便宜、快）、Plan 生成用 DeepSeek 主力模型（推理能力强）、综合回答也是 DeepSeek 主力、图片识别用豆包多模态模型。**不同阶段对模型能力的需求不同，没必要全用最强模型。**

---

**Q8：你的 RAG 为什么选择自研 + BM25，而不是直接用 LlamaIndex 或向量数据库？**

手机知识库的数据量不大（几十篇评测文章），不需要分布式向量数据库。numpy + 内存 embedding 缓存完全够用，启动时预热，查询时直接内存计算余弦相似度，毫秒级。BM25 做关键词召回、embedding 做语义召回，两者融合。如果数据量上到百万级，再考虑引入向量数据库。**不要为不需要的规模做过度设计。**

---

### Agent 设计

**Q9：你是怎么防止 Agent 产生幻觉的？**

两层防护。第一层，工具层面：Agent 查价格通过 `multi_platform_comparison` 工具，这个工具直接从 SQLite 查数据返回结果。Agent 没有能力"编造"价格——只能基于工具返回的数据回答。第二层，评估层面：`detect_hallucination()` 从 Agent 回答中提取所有价格数字，跟 Ground Truth 交叉比对，5% 容差。

---

**Q10：SLOT_FILLING 阶段用户的无效输入怎么处理？为什么不计入 question_count？**

只有提取到有效槽位才算一次有效追问。用户说"今天天气不错"→ 关键词字典和正则全都没匹配上 → 不算有效追问 → 不计数 → 重新追问当前缺失的槽位。这个决策背后的原则是：**惩罚用户的无意行为是不合理的。** 追问次数限制是为了防止无限对话，不是为了惩罚用户闲聊。

---

**Q11：你是怎么管理多轮对话的上下文的？为什么不无限拼接历史消息？**

三个机制。滑动窗口：按轮数（默认 6 轮）和字符数（默认 6000）双重截断。购物状态上下文：ShoppingContext 不依赖历史消息，槽位存储在 `ctx.slots` 字典，状态保存在 `ctx.phase`。历史注入：GREETING 阶段从最近 6 轮用户消息中提取槽位信息。核心原则：**对话状态不应该只靠 LLM 从历史消息中理解，应该有程序化的上下文管理。**

---

### 评估

**Q12：Agent 的 Ground Truth 怎么来？没有人工标注怎么评估正确性？**

Ground Truth 直接从数据库计算。举例：case 问"iPhone 15 最便宜多少钱"，Ground Truth = SQL 直接查 MIN(price)。Agent 的回答里提取价格数字，跟 Ground Truth 比对，在容差范围内算对。这个设计的启示是：**Agent 评估的 Ground Truth 不一定是"人工标注"，可以是"从可信数据源自动计算"。**

---

**Q13：P4 基准报告为什么设计 7 个维度，而不是一个总通过率？**

因为一个总通过率掩盖了太多信息。Agent 系统不同维度的能力是独立的。P2 端到端通过率 100% 但 P1 属性提取只有 88%，你知道问题出在 LLM 的参数解析能力，不是出在工具调用逻辑。**单一数字不能驱动决策，维度拆分才能。**

---

**Q14：tests/ 和 eval/ 的分工逻辑，你是怎么考虑的？**

一个原则：**让开发者愿意频繁跑测试。** 不需要 LLM 的测试放在 tests/，秒级跑完。需要 LLM 的放在 eval/，分钟级，发版前跑一次。还有成本考量：eval 要真实调用 LLM，每次跑要花钱。开发期一天改 20 次代码，每次都跑 eval 的话 API 费用可能上千。这种分层本质上是**用架构设计降低质量保障的成本。**

---

**Q15：M5 测试从 6 个 case 长到 9 个，每个新增 case 对应的坑是什么？**

Case 7（话题切换与结束检测）："算了帮我查 iPhone 15"既包含结束词又包含新查询。修复为话题切换优先级高于结束检测。Case 8（无关输入处理）：用户闲聊消耗 question_count。修复为只统计有效槽位提取。Case 9（路由持久性）：购物激活后"打游戏"被意图分类误判为 recommendation。修复为激活后跳过意图分类。**每个 case 都是一个线上 bug 的结构化沉淀。**

---

### 可观测性

**Q16：Trace 事件系统从 Day 1 就设计的吗？为什么不在后期再加？**

是的。经验教训：以前项目后期加可观测性，每个模块日志格式都不一样，重构成本极高。Trace 系统的核心设计：事件类型枚举 → 工厂方法 → `to_dict()` 序列化 → SSE 流式推送。**先定义观测协议，再写业务逻辑。** 每个模块接入时只需调用 `self.trace.xxx()` 工厂方法。

---

**Q17：前端 DAG 图渲染中，并行节点和串行节点是怎么区分展示的？**

并行节点用 CSS Grid `repeat(auto-fill, minmax(220px, 1fr))` 自动分列。串行节点用 Flex column 纵向堆叠，`width: 100%` 撑满容器。每个节点内部 tool/purpose/dep 都有 text-overflow: ellipsis 截断，hover 显示完整文本。这里的坑：第一版用 Flexbox wrap + max-width 硬编码两列，3 个以上并行步骤时布局错乱。换 Grid 后彻底解决。

### 工程实践

**Q18：这个项目里你做的最大 trade-off 是什么？**

意图显式路由 vs. LLM 自主判断。当前方案是关键词 + 正则的条件判断，好处是快速、确定、不消耗 token；坏处是需要维护关键词库。如果换成 LLM 做意图分类，能覆盖更多表达变体，但每次多一次 LLM 调用。当前选择规则路由的原因是：**意图分类的错误代价很高**——shopping 被误判为 recommendation 会导致整个状态机跳过。与其依赖不可控的 LLM 判断，不如用规则做到 99% 准确。

---

**Q19：如果这个项目要上生产环境，最大的三个差距是什么？**

第一，真实数据源。当前 SQLite mock 数据，上生产需要接入电商平台实时 API。工具接口已通过 tool_registry 做了抽象，但抽象层本身还需要验证。第二，会话持久化和并发。当前 Flask 单进程 + 内存状态，多用户并发时购物状态会混乱，需要引入 Redis。第三，评估数据时效性。真实电商数据价格实时变化，评估需要用价格快照做离线回放。

---

**Q20：这个项目中你觉得最值得跟别人分享的一条工程经验是什么？**

**Agent 的状态不要只交给 LLM。** LLM 擅长语义理解，但不擅长管理流程。购物模式的 6 个状态、追问次数上限、话题切换判断——这些应该由代码管理，不是靠 prompt 约束。用代码管理状态的好处：可测试、可调试、可修改。这个经验可以推广：**规则负责控制流，LLM 负责语义判断。两者解耦。**

**Q21：如果再给两个月时间，你最想在这个项目上加什么？**

M4 生成式推荐。当前推荐只是把槽位映射为搜索参数，返回排序列表。缺的是"为什么推荐这一款"。理想形态是 LLM 基于用户需求 + 商品参数 + RAG 知识，生成个性化的推荐理由。推荐解释是把"能查到"升级到"能说服"——这是 Agent 从工具变成助手的质变。

**Q22：如果让你在其他业务场景搭建一个 Agent，你的通用方法论是什么？**

这是一个非常重要的问题。面试官可能在考察：你的经验是可复用的，还是只绑定在一个项目上。我从 Price Agent 的搭建过程中提炼出一个通用框架——**六步法**。不管什么业务领域，搭建 Agent 都可以按这个思路推进。

---

**Step 1：定义 Agent 的目标和边界（最重要的第一步）**

不是"Agent 要做什么"，而是"Agent 不做什么"。

- 目标：Agent 要替用户完成什么任务？输出什么？
- 边界：什么情况 Agent 应该拒绝？什么决策必须由人做？
- 成功标准：什么算"做得好"？（定义清楚才能评估）

Price Agent 的例子：目标是"帮用户找到合适的商品并比价"，边界是"不做购买决策、不处理支付、不评价商品好坏"。

反例：如果你说"Agent 帮运营做数据分析"，这个定义太模糊——是自动出日报？是异常检测？是归因分析？还是策略建议？模糊的定义导致你根本不知道 Agent 该有什么工具。

**判断标准：如果你不能用三句话说清楚 Agent 的目标、边界、成功标准，先不要写代码。**

---

**Step 2：梳理用户场景 → 反推 Agent 能力**

不是先设计架构，是先理解用户。

关键方法：列出 5-10 个真实用户场景（不是编的，而是观察或访谈得到的），每个场景标注两个要素——**用户输入了什么**、**期望得到什么结果**。然后从场景中反推 Agent 需要什么能力。

举一个非电商的例子——**客服工单 Agent**：

| 用户场景 | 需要的能力 |
|---|---|
| "这个订单怎么还没发货" | 查订单状态（调 ERP API） |
| "我要退货，已经寄回去了" | 查退货物流 + 更新工单状态 |
| "上次说给我补偿，到现在没到账" | 查历史工单 + 补偿记录 |
| "这个问题你们解决不了，找主管" | 判断升级条件 + 转人工 |

从 4 个场景反推出 Agent 需要：订单查询能力、物流查询能力、工单历史查询能力、升级判断逻辑。不需要的：推荐能力、对比能力——因为这个场景不需要。

**Price Agent 的四种模式不是凭空设计的，是从四种用户购买状态反推出来的。** 场景驱动 = 你需要什么能力就加什么能力，不加不需要的。

---

**Step 3：设计工具清单（Skill/Tool）——Agent 的手**

每个需要的能力对应一个工具。工具设计的三个要点：

1. **输入明确**：函数签名清晰，每个参数有类型和含义。`check_order_status(order_id: str) -> dict` 比 `check_order(query: str) -> dict` 好——前者 Agent 知道该传什么，后者太模糊。

2. **输出结构化**：返回 dict，包含"原始数据"和"业务结论"两层。Price Agent 的 `ttest_ab` 返回 `{"p_value": 0.03, "suggestion": "launch"}`——Agent 可以直接读 suggestion 做决策，不需要理解 p 值含义。

3. **错误友好**：工具失败不抛 traceback，返回 `{"error": "订单不存在", "suggestion": "请确认订单号"}`。结构化的错误让 Agent 知道怎么跟用户解释。

---

**Step 4：判断交互模式 → 选 Agent 架构**

这一步是根据场景特征选择最合适的 Agent 模式。决策树：

```
用户需求是否明确？
  ├── 明确（用户知道要什么）
  │     ├── 单步骤 → 直接调工具（不需要 Agent）
  │     ├── 多步骤无依赖 → 并行工具调用
  │     └── 多步骤有依赖 → Plan-Execute（DAG 编排）
  │
  └── 不明确（用户不知道要什么/需要引导）
        ├── 简单引导（1-2 轮追问） → ReAct + 追问策略
        └── 复杂引导（多轮信息收集） → 状态机（ShoppingContext 模式）
```

举三个不同领域的例子，说明怎么选：

**场景 A：客服工单处理**。用户需求明确（"查订单状态"），单步骤 → 直接调工具 + ReAct 简单模式。不需要 Plan-Execute，不需要状态机。

**场景 B：策略决策 Agent（快手 JD 场景）**。用户需求明确但步骤有依赖——"分析这个 AB 实验结果"→ 先取数、再统计检验、最后综合判断。取数步骤之间可以并行（CTR 和留存互不依赖），统计依赖取数结果。→ **Plan-Execute**，DAG 拆分 + 并行调度。

**场景 C：保险理赔引导 Agent**。用户需求不明确——"我出车祸了，要理赔"。Agent 需要收集事故信息、保单号、责任认定、维修估价，逐步引导。→ **状态机模式**，每个必要信息是一个槽位，追问上限防止无限对话，话题切换检测（用户说"我不理赔了，直接问保单到期时间"）。和 ShoppingContext 同构不同域。

**关键原则：不需要为了炫技选最复杂的架构。场景需要什么就用什么。**

---

**Step 5：设计兜底和护栏**

这是 Agent 和 Demo 的分界线。不是"Agent 正常工作时有多好"，而是"Agent 出错时有多安全"。

三层护栏：

1. **工具层**：工具函数的 try/except + 结构化错误返回。不要让 Agent 看到 Python traceback。
2. **推理层**：空结果 → 自反思重试；连续失败 3 次 → 告知用户并给替代建议；不确定时 → 承认不确定，不是编造。
3. **安全层**：破坏性操作（发邮件、修改数据库、退款）→ 必须 Human-in-the-loop 确认。用户说"帮我退款"→ Agent 可以准备退款信息，但不能执行。

**设计时要考虑的不是"正常路径"，而是"最坏情况下 Agent 能做什么"。** 如果你想不到最坏情况——找个同事扮演"恶意用户"，试试能不能让 Agent 做出不该做的事。

---

**Step 6：先定义评估，再写业务代码**

在写第一行业务代码之前，先回答三个问题：

1. **怎么判断 Agent 做对了？** 能自动化判断吗？还是必须人工评估？
2. **评测集从哪来？** 有没有现成的数据可以转化为 Ground Truth？还是需要从头构建？
3. **最可能出错的环节是什么？** 在这个环节上投入最多的测试资源。

Price Agent 的做法：Ground Truth 从数据库自动计算 → 不需要人工标注。其他场景的启发——客服工单 Agent 可以用"历史工单的处理结果"作为 Ground Truth（Agent 给出的建议和实际客服的操作对比）。策略决策 Agent 可以用"AB 实验的实际结论"作为 Ground Truth。

**评估先行的好处**：当你定义完评估指标后，你会发现 Step 1 定义的"成功标准"可能太模糊需要细化，Step 3 的工具设计可能缺少关键输出字段。评估定义会反过来优化你的设计。

---

**通用框架速查**

| 步骤 | 关键问题 | 交付物 |
|---|---|---|
| Step 1：目标边界 | Agent 做什么、不做什么？ | 一句话定位 + 边界清单 |
| Step 2：用户场景 | 用户会怎么用？期望什么结果？ | 5-10 个场景 + 能力清单 |
| Step 3：工具设计 | 每个能力对应什么工具？ | 工具清单 + 输入输出 Schema |
| Step 4：架构选择 | 单步/多步/引导？有依赖吗？ | 模式选择（ReAct/Plan-Execute/状态机） |
| Step 5：兜底护栏 | 出错时怎么办？安全底线在哪？ | 兜底策略 + 护栏规则 |
| Step 6：评估先行 | 怎么判断对错？评测数据从哪来？ | 评估方案 + Ground Truth 来源 |

---

**面试时怎么用这个框架**

如果面试官问"你怎么在其他场景搭 Agent"，不要急着说技术细节。按这个思路回答：

"我会分六步来做。首先定义 Agent 的目标和边界——它解决什么问题、不做什么。然后从真实用户场景出发反推需要的能力。接着把能力映射为工具。然后根据场景特征判断用什么样的交互模式——简单任务用 ReAct、多步骤有依赖用 Plan-Execute、需要多轮引导用状态机。接着设计兜底和护栏，确保出错时优雅降级。最后在写代码前先定义好评估指标和 Ground Truth 来源。"

然后——**最关键的一步**——选一个面试官熟悉的业务场景，现场套用这个框架演示一遍。比如：

"如果您让我给客服场景搭一个 Agent，我会先梳理 4 个核心场景——查订单、查物流、历史工单、升级判断。前三个是单步工具调用，用 ReAct 模式。升级判断需要一个规则引擎——超过 3 次交互未解决或用户明确要求转人工，自动升级。评估用历史工单的处理结果作为 Ground Truth——Agent 的升级判断和实际客服操作对比。"

**现场套用框架比背诵方法论更有说服力。**

**Q23：从意图识别到 Agent 执行模式选择到 Skills 调用再到 Tool Call 是如何实现的？**

### 一、意图识别 —— 规则引擎快速分类

用户输入一句话，系统通过 `_detect_intent()` 做意图分类。采用规则引擎而非 LLM 判断，因为比价场景的信号非常明确：

| 用户说什么 | 信号 | 判为 |
|-----------|------|------|
| "打游戏推荐什么手机" | 场景词 gaming + 推荐词 | recommendation |
| "iPhone 15 和小米14 哪个好" | 对比词 + 多商品 | comparison |
| "想买个手机" | 购物词 + 无型号 | shopping |
| "iPhone 15 京东多少钱" | 单型号 | query |

判断逻辑：有场景词/预算词/处理器词 → recommendation；多商品 + 对比词 → comparison；购物词 + 无型号 + 无场景 → shopping；其余 → query 兜底。

**产品视角**：毫秒级判断，不消耗 LLM token。只在边界模糊时（如"推荐 iPhone 15"）降级为普通查价。

### 二、执行模式选择 —— 三种策略匹配场景

意图决定后，`run()` 方法路由到三种执行模式之一：

- **recommendation → ReAct 循环**：注入语义推荐优先提示，LLM 自主选择工具
- **comparison → Plan-Execute**：专用模型 `model_plan` 生成 JSON 执行计划 → 无依赖步骤并行（ThreadPoolExecutor × 4）→ 有依赖步骤串行 → Step 级 mini-ReAct 自反思 → `model_synthesize` 综合回答
- **shopping → 购物状态机**：GREETING → SLOT_FILLING → SEARCHING → RECOMMENDING → COMPARING → FOLLOW_UP，逐步收集需求后搜索
- **query → ReAct 循环**：默认兜底，标准 Think → Act → Observe

**产品视角**：简单问题不绕路（ReAct），复杂问题并行加速（Plan-Execute），模糊需求主动引导（Shopping）。三种模式覆盖用户从"明确知道要什么"到"完全不知道要什么"的全部场景。

### 三、Skills 调用 —— LLM 按需加载专业知识

模式选定后，`_resolve_skills()` 根据意图解析 Skill 集合，`_preload_skills()` 将对应 SKILL.md 内容注入 system prompt：

| 意图 | 预加载的 Skill |
|------|--------------|
| query | price_comparison |
| recommendation | semantic_recommend + price_comparison |
| comparison | price_comparison + rag_knowledge |
| shopping | shopping_guide |
| 有图片 | 叠加 vision_search |

每个 SKILL.md 包含该场景专属的行为规则、工具使用指南（含反例）、Few-shot 示例。同时 LLM 可通过 `load_skill` 元工具在对话中自行加载额外 Skill，内容跨 ReAct 轮次持久化。

**产品视角**：Skill Catalog 仅 253 chars 始终可见（vs 原 5,825 chars 全量注入），Token 消耗降低 74-80%。新增 Skill 只需加一个 .md 文件，零代码扩展。

### 四、Tool Call —— LLM 自主决策执行

Skill 加载后，LLM 在 ReAct 循环中每一步先思考（Thought）再调用工具（Action），拿到结果（Observation）后决定下一步。

以 "iPhone 15 在哪个平台最便宜" 为例：

```
Round 1:
  Thought：用户想看全平台比价，一次搞定
  Action：multi_platform_price_comparison(product_name="iPhone 15")
  → PlatformParallelAgent 并行查京东/淘宝/拼多多/苏宁
  → Observation：拼多多 ¥5750, 京东 ¥5999, 淘宝 ¥5899, 苏宁 ¥6049
  Final Answer：最便宜是拼多多 ¥5750
```

**自反思纠错**：如果工具返回空结果，引擎自动注入反思提示，LLM 自我判断是换参数重试、换工具、还是放弃。最多 2 轮反思后如实告知用户"数据库未收录"。

**产品视角**：LLM 像真人一样会反思——换关键词、放宽条件、换工具——而不是调一次失败就放弃。

### 完整链路示例

用户："5000以内拍照好的手机推荐一下"

```
1. 意图识别：场景词(拍照) + 预算词(以内) → recommendation
2. 模式选择：ReAct 循环 + 推荐优先提示
3. Skill 预加载：semantic_recommend + price_comparison
   → 注入工具指南："优先用 semantic_product_search，不要用比价工具"
4. ReAct Round 1：
   Thought：推荐型需求，用 semantic_product_search
   Action：semantic_product_search(use_case="photography", budget_max=5000)
   → 返回小米14（¥3999 徕卡影像）、小米14 Pro 等
5. Final Answer：
   🥇 小米14 ¥3999 — 徕卡联合调校，拼多多 ¥3899
   🥈 小米14 Pro ¥5299 — 旗舰拍照
   "需要帮您查具体型号的全平台最低价吗？"
```

### 总结

四层协作各司其职：意图识别快速分类 → 模式选择匹配策略 → Skills 精准注入知识 → Tool Call 执行动作。从用户的一句自然语言，到跨四电商平台的真实验证数据，整个链路在 ReActAgent 引擎中自动编排完成。

**Q24：Skills 调用是在 Agent 思考之前还是之后发生的？**

从产品视角看，Skill 的加载时机取决于"谁在做决策"——是系统预判、Agent 自主判断、还是用户主动指定。三种场景对应三种产品逻辑。

**场景一：系统预判加载（90%+ 的请求走这条路）— 在 Agent 思考之前。**

用户说"iPhone 15 最低价多少钱"，系统在把问题交给 Agent 思考之前，已经完成了两件事：识别意图（这是查价，不是推荐，不是购物引导）→ 匹配 Skill（查价场景需要"比价指南"这个 Skill）→ 把 Skill 内容提前装进 Agent 的"知识背景"里。

也就是说，Agent 开始思考"我该怎么回答这个用户"的时候，它已经带着比价场景的专业知识了。用户感知不到这个过程——没有额外等待，没有额外交互。就像你去餐厅点菜，服务员还没开口就已经知道你手里的是菜单、你需要的是点餐建议，不需要你再解释一遍"我是来吃饭的"。

**场景二：Agent 自主补课（边缘场景兜底）— 思考之后、行动之前。**

偶尔会有系统没预判到的场景。比如用户在购物过程中突然说"帮我对比一下这两款手机的拍照参数"——系统预判购物场景时只加载了"购物引导"Skill，但 Agent 发现用户想对比参数，需要"比价对比"Skill 的知识。

这时候 Agent 会自己说："这个需求我需要补一下相关知识"，然后主动加载对应 Skill，再基于新知识继续服务用户。用户感受到的是：Agent 稍微多想了一下（多一轮思考），但回答质量没有下降。

为什么不让 Agent 一开始就带着所有 Skill？因为"全量加载"有两个产品代价：一是每次对话的 token 消耗增加 3-4 倍，成本直接翻倍；二是信息过载会让 Agent 的决策质量下降——给你 10 页说明书让你找一个功能，不如直接告诉你"第 3 页是你需要的"。

**场景三：用户主动指定（用户有明确预期时）— 在 Agent 思考之前。**

用户直接说"/比价 iPhone 15"，系统识别到用户明确指定了 Skill，直接加载对应知识，然后交给 Agent 思考。这跟产品里的"高级模式"或"手动挡"逻辑一样——大多数用户不需要，但给有明确需求的用户一个快捷键。

**产品决策的核心**：为什么不是"全量加载"或"全靠 Agent 自己判断"？

全量加载 = 成本高 + 决策噪声大。全靠 Agent 自己判断 = 多一轮交互延迟 + 可能加载错。当前方案是"预判为主，补课兜底"——用系统预判覆盖绝大多数场景，保证成本和延迟最优；留一个补课机制保证边缘场景不崩。这是典型的"二八法则"产品设计：80% 的场景用最优路径，20% 的场景用兜底路径。

---

**Q25：Agent 会自己决定加载 Skill，还是只能等用户下指令？**

**Agent 可以完全自主决定**，不需要用户知道 Skill 的存在。

从产品视角，这相当于给 Agent 配了一个"内部知识库目录"。Agent 在服务用户的过程中，如果发现当前场景需要某个专业知识、但自己还没加载，它可以自己翻目录、自己加载、自己学会，用户全程无感。

举个例子：用户在购物引导中说"推荐一款打游戏的手机，顺便和 iPhone 15 对比一下拍照"。系统预判购物场景，提前加载了"购物引导"Skill。Agent 服务到一半，发现用户要对比拍照参数——这个能力在"比价对比"Skill 里，不在"购物引导"Skill 里。Agent 会自己判断"我需要加载比价对比 Skill"，然后加载，然后继续回答。用户只感受到"Agent 回答得挺专业"，完全不知道背后发生了一次能力切换。

**那为什么不一开始就把所有 Skill 都加载上？**

这是产品设计中一个经典的成本-质量权衡。三个理由：

| 方案 | Token 消耗 | 决策质量 | 加载延迟 |
|------|-----------|---------|---------|
| 全量预加载（5 个 Skill 全装） | 约 5800 token | 信息过载，容易选错工具 | 无 |
| 当前方案（按意图预加载 1-2 个） | 约 1200 token | 信息精准，选工具准确率高 | 偶尔多一轮 |
| 全靠 Agent 自己判断 | 约 1200 token 起步 | 每轮都可能加载，不稳定 | 每次多一轮 |

全量加载相当于给一个员工塞了 5 本操作手册让他全部记住再干活——记是记住了，但找关键信息会变慢，还容易翻错页。按需加载相当于只给当前任务相关的 1-2 本，需要时再去书架拿——大部分时候根本不需要拿第二本。

实际数据：当前 Skill 目录只有约 250 个字的简介始终对 Agent 可见（vs 全量加载 5800+ 字），Token 消耗降低 74-80%。Agent 自主加载 Skill 的触发率不到 5%，因为系统预判已经覆盖了绝大多数场景。

**产品层面总结**：三种激活方式对应三种用户价值：

- **系统预判加载**：用户无感、零延迟、成本最低。对应"好产品不需要用户学习"。
- **Agent 自主补课**：用户无感、偶尔多一轮延迟。对应"聪明助手会在需要时自己查资料"。
- **用户主动指定**：用户有感、零延迟。对应"给高级用户一个快捷键"。

这个设计遵循的产品原则是：**让系统承担复杂度，不要让用户承担。** 用户不需要知道 Agent 有几个 Skill、什么时候加载、怎么加载——他只需要感受到"回答很专业、反应很快"。

### 三、两种模式的产品差异

| 维度 | ReAct | Plan-Execute |
|------|-------|-------------|
| 适合什么用户状态 | "我知道要什么" | "我在纠结选哪个" |
| 典型 query | "iPhone 15 多少钱" | "A 和 B 哪个好" |
| 思考方式 | 边走边想，每步一思考 | 先想清楚全局，再动手 |
| 执行效率 | 串行，N 步就是 N 倍时间 | 无依赖的步骤并行，快 |
| 用户感知的延迟 | 逐步输出，有过程感 | 前段有短暂等待，后段一次性输出 |
| 出错处理 | 每轮可自纠错 | Step 内有 mini-ReAct 反思 |

**为什么不能把对比场景也塞进 ReAct？**

如果"iPhone 15 和小米 14 哪个好"走 ReAct，Agent 会怎么做？第一轮查 iPhone 15 → 第二轮查小米 14 → 第三轮对比。三步串行，用户等待时间是三次 LLM 调用 + 两次工具调用的累加。而且 Agent 可能第一轮查完 iPhone 就直接输出结论了——因为它"边走边想"，不一定意识到还需要查小米 14。

Plan-Execute 的本质是：**在动手之前，先逼迫 LLM 把"要做什么"想清楚。** 想清楚之后，无依赖的步骤并行执行，用户等待时间从"累加"变成"取最长"。

**为什么简单查价不走 Plan-Execute？**

因为没必要。查价只有一步——"调比价工具"。如果走 Plan-Execute 流程：生成计划（调 LLM）→ 执行（调工具）→ 综合（再调 LLM），三次 LLM 调用解决一个一步就能完成的问题，过度设计。ReAct 一步到位：思考 + 调工具 + 回答，两次 LLM 调用。

**产品决策的核心**：场景复杂度决定架构复杂度。不是越复杂越好，是"刚好够用"最好。

**Q27：你在项目中遇到过印象最深的 bug 或问题是什么？怎么解决的？**

这个问题面试官问的不是"你写了多少代码"，是"你遇到问题时怎么想的、怎么拆的、怎么决策的"。我拿一个还没修完的问题来讲——它恰好能展示我的排查思路和方案设计能力。

**问题现象**

对比场景（比如"iPhone 15 和小米 14 哪个更值得买"）偶尔会出现回复质量下降：Agent 只查了一个商品的价格就开始给结论，或者把两个商品的对比变成了单个商品的描述。不是每次都发生，所以一开始很难复现。

**排查过程**

我按调用链倒推——

第一步，确认意图识别有没有问题。日志显示 `intent=comparison`，路由正确走到了 Plan-Execute 模式。排除了意图识别错误。

第二步，看 Plan-Execute 有没有正常执行。发现 Trace 里出现了 `mode_select: react, reason: "LLM 判定为简单查询，回退 ReAct"`。也就是说，Plan-Execute 的 Phase 1（生成计划）阶段，LLM 把这个对比问题判为了"简单查询"，直接回退到了 ReAct。

第三步，顺着往下看，确认 ReAct 模式下对比场景的表现。发现 ReAct 循环本身是为单商品查询设计的——每次"思考 → 调工具 → 观察"的节奏天然适合"查一个东西"，不适合"查两个东西再对比"。LLM 查完第一个商品可能就认为信息够了，直接输出结论。

**根因定位**

问题出在 Plan-Execute 和 ReAct 的衔接处。Plan prompt 里有一条规则："如果只需要 1 个工具且无需后续分析 → complexity: simple"。LLM 在生成计划时可能产生两个误判：

1. 认为 `multi_platform_price_comparison` 一次调用就能覆盖两个商品（对工具能力的幻觉）
2. 忽略了"且无需后续分析"这个条件——用户要的是对比结论，本身就是后续分析

于是 LLM 输出 `complexity: "simple"`，代码无条件信任了这个判断，回退到 ReAct。而 ReAct 不具备多商品对比能力，回复质量就下降了。

```
comparison 意图 → Plan-Execute
  → Phase 1: LLM 误判为 simple
    → 代码无条件回退 ReAct
      → ReAct 不具备多商品对比能力
        → 只查一个商品就下结论
```

**当前状态：已知问题，方案已有，尚未修复**

我目前的判断是：这是一个设计层面的问题，不是简单改一行 prompt 能彻底解决的。因为根本矛盾在于——意图识别（代码层）已经明确判为 comparison，但 plan 生成（LLM 层）仍有权限推翻这个判断。两个层面的决策权没有明确的分级。

**我设计的修复方案**

不改 ReAct 循环（ReAct 本身没问题，是"被错误路由到它"出了问题），而是在 Plan-Execute 入口加一层意图级兜底：

```
当 intent == "comparison" 且 plan 为 None 时：
  → 不信任 LLM 的 simplicity 判断
  → 代码层强制构造最小对比计划：
      Step 1: 查商品A价格
      Step 2: 查商品B价格
      Step 3: 综合对比分析
  → 继续走 Plan-Execute 的正常执行流程
```

一句话概括这个方案的设计理念：**当代码层的确定性判断（意图识别）和 LLM 的不确定性判断（复杂度评估）冲突时，代码优先。** 意图识别判了 comparison，LLM 就没有权限降级为 simple。

**为什么还没修**

因为这个方案的触发前提是"Plan-Execute 确实应该走但 LLM 判错了"，而这类 case 在当前数据量下属于偶发。我需要积累更多线上 trace 来确认两个假设：

1. 回退到 ReAct 的 comparison query 占多少比例，是否值得加这层兜底
2. 代码层强制构造的对比计划质量是否稳定，能不能 cover 多数 case

有数据之后再审慎上线。**这是一个"先观察、再验证、最后落地"的思路，而不是"看到一个 bug 就立刻修"。**

## 附录二：快手电商数据策略产品实习生（Agent 方向）— 针对性面试题 15 道

### 一、Skill/Tool 开发

**Q1：如果你要把一个 AB 实验显著性检验的逻辑封装成 Agent 可调用的 Skill，你会怎么设计这个函数？**

三个要素。第一，清晰的函数签名 + 类型注解：`ab_test_check(experiment_name, control_metric, experiment_metric, control_sample_size, experiment_sample_size, significance_level=0.05)`。第二，结构化返回值：不只返回 p 值数字，还返回 `suggestion` 字段（launch/rollback/retest），Agent 不需要理解 p 值含义，直接读 suggestion 就行。第三，异常处理：样本量为 0、数据缺失，try/except 兜底，返回 `{"error": "xxx", "suggestion": "retest"}`。

---

**Q2：你在 Price Agent 里用过 `@register_tool` 装饰器，和 LangChain 的 `@tool` 装饰器比，本质区别是什么？**

本质区别不在装饰器语法，在工具的描述协议。两者底层都是 OpenAI Function Calling 格式的 JSON Schema——LLM 通过 Schema 理解"工具是干什么的、需要什么参数"。区别在调度层：我的 `tool_registry` 是手动注册、手动调度，LangChain 的 `ToolExecutor` 帮你做了调度。手动调度意味着精确控制调度逻辑，出错时能精准定位。这是调试优势。

---

**Q3：JD 提到"Agent 调用 Skill 时选错、填错参数"，你在 Price Agent 里遇到过类似问题吗？怎么解决的？**

遇到过。LLM 有时传 `"5000"`（字符串）而不是 `5000`（整数）给 budget_max 参数。解决分三层：第一层，参数校验在工具函数入口，类型检查 + 必填检查 + 范围检查，失败返回结构化错误而不是 traceback。第二层，Schema 描述写清楚类型和含义。第三层，自反思纠错——工具返回空结果时，Agent 收到反思消息，自己调整参数重试。

---

### 二、决策 Agent 设计

**Q4：JD 描述的"策略决策 Agent"，如果让你设计架构，你会怎么做？**

三阶段对应 Price Agent 的 Plan-Execute。Phase 1：理解需求 + 制定检查清单（需要哪些指标、样本量是否足够）。Phase 2：并行取数 + 调 Skill——CTR 和留存数据互不依赖可以并行，统计计算依赖取数结果串行。Phase 3：综合判断 + 策略建议——硬规则（p 值阈值）写在 Skill 返回值里，软判断（多指标权衡）交给 LLM。

---

**Q5：你怎么让 Agent 在输出建议的时候精确输出 launch/rollback/retest？**

Prompt 里强制输出格式约束 + Skill 返回值自带 suggestion 字段。Agent 不是凭空判断，而是基于 Skill 的结论做最终决策。这样即使 LLM 不稳定，底线判断（显著性检验的结果）是 Tool 输出的事实，不是 LLM 编的。

---

### 三、Python 工程 + 数据分析

**Q6：如果一个 Skill 要用 pandas 做数据聚合再输出给 Agent，代码结构怎么设计？**

三个原则。单一职责：fetch 归 fetch，统计归统计，不耦合。结构化返回值：Tool 输出必须是 JSON 可序列化的 dict，不能是 DataFrame，Agent 的 Observation 是字符串。参数校验前置：函数入口先检查参数合法性。

---

**Q7：怎么把 SQL 查询封装成 Tool？**

参数白名单防注入 → 参数化查询 → pandas read_sql_query → to_dict(orient="records") 转成 Agent 可读格式 → 附加 sample_sizes 等元信息（Agent 可能不会主动查但需要知道）。

---

**Q8：现场写一个 t 检验的工具函数。**

```python
from scipy import stats
import numpy as np

def ttest_ab(control_values, experiment_values, alpha=0.05):
    if len(control_values) < 2 or len(experiment_values) < 2:
        return {"error": "样本量不足", "suggestion": "retest"}
    t_stat, p_value = stats.ttest_ind(experiment_values, control_values)
    lift = (np.mean(experiment_values) - np.mean(control_values)) / np.mean(control_values) * 100
    suggestion = "launch" if (p_value < alpha and lift > 0) else "rollback" if (p_value < alpha) else "retest" if p_value < 0.1 else "hold"
    return {"t_statistic": t_stat, "p_value": p_value, "lift_pct": lift, "significant": p_value < alpha, "suggestion": suggestion}
```

设计要点：返回值包含统计指标 + 业务结论两层。边缘情况（p<0.1）单独标出。

---

### 四、LLM API + Prompt

**Q9：如果 Agent 调用 Skill 后返回的结果格式不对，怎么处理？**

三层防护。Skill 层面：统一走 `_format_response()` 包装函数，确保返回值包含 `success`、`suggestion`、`error` 三个基础字段。Agent 层面：拿到 Observation 后快速校验，缺字段 → 注入反思消息。Prompt 层面：System Prompt 加兜底规则——"如果工具返回没有 suggestion 字段，根据 p_value 和 lift 自行判断"。

---

**Q10：策略决策 Agent 怎么分配多模型路由？**

取数 + 数值计算：不需要 LLM，Skill 函数直接搞定。意图理解 + 参数提取：便宜模型（DeepSeek Flash），本质是 NER 任务。策略建议 + 风险判断：强模型，因为需要多维度权衡。核心理念：**不要让最强模型去做 SQL 拼接，也不要让最便宜模型去做策略判断。**

---

### 五、调试 + 业务对齐

**Q11：如果线上发现 Agent 把"留存率下降 1%"解读成"应该上线"，你怎么排查？**

按调用链倒推：查 Skill 返回值 → 查 Agent 的 Observation → 查 Prompt 里的判断规则 → 定位到根因后加对应 test case。调试不是改一行代码，是从 Skill → Observation → Prompt → 最终输出的全链路定位能力。

---

**Q12：业务同学说"样本量小于 1000 的实验不要做 t 检验，直接建议再测"，怎么落地？**

代码层面：Skill 函数入口加样本量检查，< 1000 直接返回 `{"suggestion": "retest", "reason": "样本量不足"}`。Prompt 层面：加规则"如果 suggestion=retest 且 reason 包含'样本量不足'，禁止自行判断"。可计算的规则用代码，不可计算的经验用 Prompt。

---

**Q13：你怎么测试一个策略决策 Agent？怎么保证边缘情况下不乱给建议？**

分层测试：Skill 层 pytest 单测（不需要 LLM）。决策场景 Gold Set：20 个标准 case 覆盖全部输出空间（launch/rollback/retest/hold）。边缘 case 的安全断言：对于极端输入（样本量=1、数据全是 0），不要求精确建议，但要求 Agent 不能给出明确的 launch/rollback。**安全断言比正确断言更重要。**

---

**Q14：Dify vs 自研，你怎么选？**

Dify 优势：可视化编排、业务同学能参与、快速原型。自研优势：精确控制、Trace 可定制、深入排查。跟业务紧密配合的阶段用 Dify，技术验证和边界探索用自研。两者都掌握——Dify 做原型和业务对齐，自研代码做核心 Skill 开发和调试。

---

**Q15：Price Agent 的经验怎么迁移到这个岗位？**

六个直接可迁移的能力：Tool/Skill 开发（@register_tool + JSON Schema）、Agent 编排（Plan-Execute DAG 调度）、调试方法论（全链路排查）、LLM API 经验（多模型路由 + 重试）、基础统计（Ground Truth 计算 + 容差校验）、评估意识（写完代码先想怎么测）。

## 附录三：字节跳动 AI 技术产品实习生 — 针对性面试题 25 道

### 一、数据处理 Pipeline

**Q1：JD 要求"设计和维护数据处理 Pipeline"，Price Agent 里有没有类似的数据处理流程？**

有的。embedding 处理链路：原始商品数据 → 商品名去重 → 文本拼接 → 逐条调 Embedding API → numpy 向量存储 → 磁盘持久化 → 启动预热。设计要点：去重规则标准化、错误隔离（单条失败不影响整体）、增量更新（缓存检查 → 加载或重建）。

---

**Q2：如果你要清洗一批电商商品数据给 LLM 做训练，你会检查哪些维度？**

五个维度逐层递进。L1 格式完整性：必填字段缺失率、类型正确率，用 Schema 自动扫。L2 去重：精确去重 + 模糊去重（embedding 相似度）。L3 异常值检测：价格异常、属性矛盾、文本长度异常，用统计规则。L4 语义一致性：商品名和描述是否匹配，需要模型辅助。L5 标注质量：标注者间一致性（Cohen's Kappa）。原则：前两层全自动化，后三层抽样抽检。

---

**Q3：Pipeline 中途挂了怎么恢复？**

断点续传：每 1000 条写一次 checkpoint。幂等设计：每条数据有唯一 ID，写入前查重。渐进式验证：每批做一次抽样校验，问题在早期发现。错误分级：单条 skip + log，整批暂停 + 告警，API 失败重试 3 次后降级。监控：实时指标（进度、错误率、延迟）。

---

### 二、评测体系搭建

**Q4：Price Agent 的 eval 框架对你搭建评测体系有什么启发？**

四个核心设计可复刻。分层评测：L0 格式 → L1 内容 → L2 效果，改什么测什么。指标维度化：不做单一数字，拆成字段完整率、去重率、异常值比例等。Ground Truth 自动化：从数据库直接计算，不靠人工标注。Session + 报告：每次 Pipeline 运行生成 run_id，不同 run 间横向对比。

---

**Q5：怎么设计"数据清洗效果"的评估指标？**

三个层次。基础指标改善：缺失值比例、重复率的前后对比。分布偏移检测：KS 检验或 PSI 量化清洗前后分布是否偏离。下游任务效果：清洗前后数据分别微调同模型，对比准确率。三层递进：基础指标是必要条件，分布检测是安全网，下游效果是最终裁判。

---

**Q6：为"数据质量"定义 5 个自定义评测指标。**

字段完整率、文本有效信息密度（过滤 HTML 标签和重复字符）、标注一致性（Cohen's Kappa）、数据多样性（类目覆盖度 + 长尾覆盖率）、LLM 有价值率（抽样让 LLM 判断"这条数据对训练有价值吗"）。前四个硬指标确保"没毛病"，第五个软指标确保"真有用"。

---

**Q7：你是怎么组织代码的，举一个具体模块的例子。**

`agent/react_engine.py` 的组织方式：按职责拆分类（ShoppingContext 独立 dataclass + ReActAgent 主类），方法按阶段分组（入口 → LLM 调用 → Plan-Execute → ReAct → 滑动窗口 → 购物状态机），每个关键方法独立可测，配置外置（USE_CASE_TRIGGER_MAP 模块常量 + industry_config 外部注入），类型注解 + 异常处理 + 防御性编程。

---

### 三、论文方法落地

**Q8：Price Agent 中有参考论文方法落地的例子吗？**

RAG 模块就是 BM25 + Dense Retrieval 混合检索的工程落地。落地过程：理解方法本质（BM25 做精确匹配，embedding 做语义匹配，互补关系）→ 最小可行验证（20 行代码跑通再优化）→ 与现有系统对接（封装成 `search_product_knowledge` 工具）→ 回归验证（6 新 case + 16 回归 case）。论文落地的关键不是完全复现，而是取其思想、适配场景。

---

**Q9：怎么推进论文方法落地？**

五步法。提炼可落地的部分（选最轻量的 1 种先验证）→ 写独立验证脚本（1000 条小数据集跑通）→ 设计对照实验（对照组 vs 实验组）→ 写落地文档（解决什么问题、为什么不用其他方法、已知局限）→ 灰度上线 + 持续监控。

---

### 四、Agent 自动化 + 提示词工程

**Q10：Price Agent 里做了哪些 Agent 自动化的工作？**

三个可迁移的设计。Prompt 驱动的数据分类：temperature=0 保证确定性，JSON 格式约束，附 reason 字段可审计。错误处理的自动化闭环：API 调用失败自动重试 + 记录 error_list + 人工处理。Pipeline 步骤的 Agent 编排：让 Agent 自己规划步骤顺序、判断并行/串行、遇到错误时决定策略。

---

**Q11：System Prompt 设计有什么经验？**

三个经验。三段式结构：角色 + 工具说明书 + 输出约束。规则写进 Prompt + 给示例（每个等级给例子）。Temperature 按任务分档：分类/提取 0，评分 0.3，建议 0.7。Prompt 工程不是"写一段话就完了"，是为每个任务匹配合适的角色、示例、格式约束和参数。

---

### 五、综合能力

**Q12：跨职能团队协作，你怎么设计模块接口？**

三个"接口先行"的设计。行业配置独立模块（产品同学直接改配置，不需要理解 Agent 代码）。工具注册标准协议（工程同学开发工具，Agent 代码不需要改）。Trace 事件标准化格式（前端同学不需要理解 ReAct 循环，只关心事件类型）。技术产品经理的价值是设计接口和协议，让不同角色并行工作。

---

**Q13：你在 Price Agent 里是怎么保证质量的？**

三个方面。输入质量：industry_loader Schema 验证，配置写错启动时报错。过程质量：每个关键函数有单测，改代码跑对应 test。输出质量：eval 框架端到端验证，P4 基准报告 7 维度量化。核心原则：**质量控制是前置的，不是事后补救的。** 输入校验 → 过程测试 → 输出评测，每一步不可跳过。

---

**Q14：入职第一个月能交付什么？**

分阶段交付。第一周：熟悉 Pipeline + 跑通全流程 + 输出新人上手指南。第二周：找一个小痛点写独立脚本解决（30 行以内、有单测、有说明）。第三-四周：交付完整功能模块（需求 → 验证 → 代码 → 报告 → 文档）。持续积累：每周五写总结。

---

**Q15：你怎么理解"技术产品经理"？**

**能用代码验证想法，能用数据支撑决策，能用文档对齐协作。** Price Agent 体现三个产品思维：技术服务于场景（四种模式诞生于用户场景，不是炫技）、可演示比完美重要（Trace 系统是翻译器）、评估是产品的底线（166 个 case 不是证明做得好，是防止做得差）。

### 六、LLM 训练数据专题（字节高频面试题）

**Q16：SFT（监督微调）数据由哪些部分组成？怎么构建高质量的 SFT 数据集？**

SFT 数据的核心结构是 Instruction-Response Pair。但 Agent 场景更复杂——还要包含工具调用的中间步骤。每条数据 = 完整的对话轨迹：System Prompt + User Query + 多轮 Tool Call + Tool Response + 最终回答。构建方式按质量从低到高：人工编写（种子数据）→ 模型蒸馏（性价比最高，用 GPT-4 跑 case 导出 trace）→ Self-Instruct（LLM 自动生成 + 人工抽检）→ 生产日志回流（最真实，需处理 PII）。质量判断标准：回答正确性、推理步骤完整性、工具调用合理性、格式规范性、简洁性。

---

**Q17：评测集怎么构建？怎么保证评测集覆盖全面但又不会数据泄漏到训练集？**

**构建**：场景覆盖矩阵（意图类型 × 商品数量 × 属性复杂度 × 输入质量 × 异常情况，5 维度交叉 30-50 个组合）+ 边界对抗样本（数值边界、文本边界、逻辑边界）+ 长尾真实分布（线上日志抽样）。**防泄漏四道防线**：时间隔离（评测集冻结后不再修改）、来源隔离（独立来源构建）、相似度检测（embedding + MinHash）、N-gram 重叠检测（13-gram 出现在训练集中 → 标记泄漏）。

---

**Q18：复杂评测集有哪些构建思路？多轮工具调用、多轮对话的数据怎么构建？**

三种思路：组合式构建（原子能力评测 → 组合能力评测）、模板化生成（场景模板 + 参数槽位 → 批量生成 + 人工审核）、对抗式构建（LLM 攻击者不断生成让 Agent 为难的 query → 发现盲区）。多轮数据构建——以 Price Agent Trace 为例：每次 Agent 运行产生完整 TraceEvent 序列（intent → mode → phase → tool_call → tool_result → answer），直接转换为训练格式 JSON。业务利用：优质轨迹 → SFT 数据、失败轨迹 → 错误模式分析、真实分布 → 评测集更新、多轮状态 → 对话管理训练。

---

**Q19：RL（强化学习）在 LLM 训练中是什么？怎么做？和 SFT 有什么区别？**

RLHF 四步：SFT 基座 → 训练 Reward Model（人工排序数据训练）→ PPO 强化学习（Reward Model 打分 + 更新参数 + KL 散度防偏离）→ 迭代。SFT 是"模仿正确答案"，RL 是"探索 + 奖励反馈"。SFT 受限于训练数据覆盖，RL 能超出训练数据分布。新方法 DPO（不用 Reward Model，直接在偏好数据上优化）和 GRPO（DeepSeek-R1 路线，组内相对比较，不用外部 Reward）大幅降低了 RL 的复杂度和成本。实践建议：**SFT → DPO 两步走是当前性价比最高的方案。**

---

**Q20：SFT、RLHF、DPO、GRPO 几种后训练方法对比。**

| 方法 | 核心思路 | 数据需求 | 训练复杂度 | 适用场景 |
|---|---|---|---|---|
| SFT | 模仿正确答案 | (prompt, answer) 对 | 低 | 学会基本格式和领域知识 |
| RLHF-PPO | 奖励模型 + 强化学习 | 偏好排序 + RM 训练 | 高（4 模型并行） | 对齐人类偏好、安全性 |
| DPO | 直接在偏好数据上优化 | 偏好数据（A, B, A更好） | 中（无 RM） | RLHF 的轻量替代 |
| GRPO | 组内相对比较 | 一组回答的相对排序 | 中（无外部 RM） | DeepSeek-R1 路线，推理增强 |

选择：SFT 先让模型"能做事"→ DPO 让模型"做得好"。RLHF-PPO 只适合安全对齐场景。GRPO 适合推理密集型场景。

---

**Q21：如果要训练一个 Agent 模型，什么样的数据是有效数据？什么样的无效？**

**有效数据五特征**：完整的推理链（Thought → Tool Call → Observation，不只是最终答案）、正确的工具调用（函数名和参数都正确）、多样化的表达覆盖（同一意图的不同自然语言表达）、包含错误恢复的轨迹（失败 → 分析 → 调整 → 成功）、领域边界清晰（有意图标签和状态标签）。**无效数据五特征**：截断的对话（缺中间步骤）、错误工具调用未标记（毒药数据）、过于简单的单轮 Q&A、分布严重倾斜、格式不一致。

---

**Q22：领域 Agent 最有帮助的数据是什么？**

四类按价值排序。第一：领域专家的对话轨迹（专家做决策的思考过程，不是教科书对话）。第二：领域术语-同义映射表（"高了一点" → "需要统计检验"、"果子" → "Apple"）。第三：错误案例 + 纠正（Agent 常见犯错场景的对比数据）。第四：领域约束文档的 Prompt 化（SOP、合规要求转成 System Prompt + Few-shot 示例）。一句话：**领域 Agent 最需要的数据不是 FAQ，是领域专家做决策时的思考过程。**

---

**Q23：除了 SFT 和 RL，通过什么样的外部机制能让一个模型具备 ReAct 能力？**

五种机制组合使用。1) System Prompt + Tool Schema 注入（零成本，立即可用）。2) Few-shot 示例注入（提升格式稳定性，模型模仿示例）。3) 结构化输出约束（JSON Mode 或 tool_choice="required" 强制格式）。4) 迭代式提示 + 格式校验（输出不符合格式 → 校验错误回传 → LLM 修正 → 直到正确）。5) 代码编排 + LLM 推理混合（最可靠——代码控制循环结构和工具执行，LLM 只负责推理和生成）。Price Agent 用了 1+2+4+5 组合。**越是关键的 Agent 系统，越应该把控制权从 LLM 转移到代码。**

---

**Q24：如何构建一个能让模型学会调用 Skills 的数据集？**

四个关键要求。工具调用必须"必要"（70%+ 样本必须调工具才能回答）。覆盖"该调但没调"和"不该调但调了"两种错误（用于 DPO 负样本）。工具参数的多样性（同一工具不同参数组合都要覆盖）。工具调用失败的处理（10-20% 样本包含失败 + 恢复）。构建方法：最强模型 + 真实工具环境跑 2000 条 → 规则过滤 + 人工抽检 → 数据增强（改措辞保持 tool call 不变）→ 错误注入（故意让工具失败 → 保留恢复成功的轨迹）。

---

**Q25：什么是数据飞轮？在 Agent 场景下怎么建立？**

数据飞轮：产品真实使用数据 → 改进模型 → 更好体验 → 更多用户 → 更多数据。Agent 场景四步：采集（Trace 记录完整轨迹 + 用户反馈 + 行为指标）→ 筛选（优质正样本 + 待修复负样本，规则初筛 + 人工复判）→ 转化（优质轨迹 → SFT 数据，正负配对 → DPO 数据，新场景 → 评测集）→ 训练（每周/双周 SFT+DPO → 评测集验证无退化 → A/B 测试分流对比）。三个陷阱：数据分布偏移（长尾越来越差）、奖励黑客（模型学会讨好用户而非正确）、评测退化（灾难性遗忘）。

## 附录四：Agent 基础知识体系 — 30 道题全面覆盖

### 一、Agent 的本质：定义与边界

**Q1：什么是 Agent？**

Agent 是一个能感知环境、自主决策、使用工具、执行动作来完成目标的 AI 系统。四个关键词：感知环境（上下文、用户状态、历史对话）、自主决策（自己决定调哪些工具、按什么顺序）、使用工具（Function Calling 是 Agent 的手）、执行动作（输出不只是文本，是 action）。

---

**Q2：Agent 和传统 Workflow 的本质区别是什么？**

Workflow 是"我知道怎么做，让机器帮我做"；Agent 是"我知道要做什么，让 AI 自己决定怎么做"。判断标准：流程能穷举 → Workflow 更可靠（更快、更便宜）；流程无法穷举 → Agent 是必选项。中间灰色地带 → 关键步骤 Agent，其余 Workflow。

---

**Q3：Agent 有自主性等级吗？**

L0 规则执行（RPA、if-else）→ L1 辅助建议（AI copilot）→ L2 工具调用（ChatGPT + Function Calling）→ L3 任务编排（Price Agent，ReAct + Plan-Execute）→ L4 目标驱动（"帮我做竞品分析"）→ L5 全自主（不存在）。Price Agent 处于 L3：在框架内自主，不越界。

---

**Q4：Agent 和 RPA 有什么区别？**

RPA 是"录制-回放"模式（固定选择器，UI 变了就挂），Agent 是"理解-决策-执行"模式（自然语言理解，自适应 UI 变化）。RPA 关注过程，Agent 关注结果。Agent 是 RPA 的进化——把"操作 UI"抽象成"达成目标"。

---

### 二、Agent 架构设计：分层、记忆、兜底

**Q5：完整 Agent 系统的五层架构。**

L0 基础层（日志、监控、配置）→ L1 模型层（LLM API、多模型路由）→ L2 工具层（Function Calling、Tool Registry）→ L3 记忆层（短期/长期/工作记忆）→ L4 决策层（意图路由、计划生成、执行调度）→ L5 交互层（对话管理、UI、多模态）。每层可独立替换。Price Agent 实现了全部五层。

---

**Q6：记忆模块怎么设计？**

短期记忆：最近对话历史（滑动窗口，6 轮 + 6000 字符）。长期记忆：跨会话用户信息（向量数据库或结构化存储）。工作记忆：当前任务状态（ShoppingContext.slots + phase，程序化状态，不靠 LLM 推断）。协同：工作记忆优先级最高 → 短期记忆 → 长期记忆。

---

**Q7：Agent 的兜底机制怎么设计？**

六层兜底从内到外：L1 工具层（try/except + 结构化错误返回）→ L2 LLM 调用层（指数退避重试，最多 3 次）→ L3 推理层（空结果触发自反思纠错）→ L4 意图层（无法分类走最安全模式）→ L5 对话层（无法理解追问澄清）→ L6 全局兜底（友好降级回复 + 人工通道）。每层只兜自己能兜的底，兜不住向上抛。

---

### 三、Agent 协议与标准

**Q8：什么是 MCP（Model Context Protocol）？**

Anthropic 2024 年底发布。给 LLM 提供标准化方式访问外部数据和工具的"USB-C 接口"。MCP Server 暴露 Resources（数据）、Tools（动作）、Prompts（模板）。MCP 是 Agent ↔ 工具的协议，解决 M×N 种对接方式问题。

---

**Q9：什么是 A2A（Agent-to-Agent Protocol）？**

Google 2025 年 4 月发布。核心概念：Agent Card（能力声明 JSON）、Task 抽象（异步、可追踪、支持流式）。A2A 是 Agent ↔ Agent 的协议。与 MCP 互补：一个 Agent 通过 MCP 调工具，通过 A2A 调其他 Agent。

---

**Q10：OPC 和 OpenClaw 是什么？**

OPC（Open Agent Protocol）：LangChain、Weaviate 等联合发起。比 MCP 和 A2A 更上层——定义 Agent 身份、能力、状态、生命周期。OpenClaw：最早实现 OPC 的多 Agent 框架，核心是"Agent Mesh"去中心化网络。趋势：2024 卷模型，2025 卷协议。MCP → A2A → OPC 代表 Agent 生态标准化进程。

---

**Q11：Hermes 是什么？**

两个项目。Nous Research 的 Hermes 模型系列：基于 Llama 微调，优化 Function Calling 和 Tool Use 能力——证明 Agent 能力可以通过模型训练提升，不只是 Prompt Engineering。Hermes Agent Router：轻量级语义路由框架，和 Price Agent 的 `_detect_intent()` 解决同一问题——用户意图映射到最优处理路径。

---

### 四、Agent 框架对比

**Q12：LangChain、LangGraph、AutoGen、CrewAI 怎么选？**

LangChain：通用 LLM 应用开发，生态最全但 API 变动频繁。LangGraph：有状态多步骤 Agent 编排，图编排能力强但学习曲线陡。AutoGen：微软多 Agent 对话协作。CrewAI：角色驱动多 Agent 任务编排。选择：单 Agent 简单场景 → 自研 200 行 ReAct；单 Agent 复杂状态 → LangGraph；多 Agent 角色分工 → AutoGen/CrewAI；快速原型 → LangChain。

---

**Q13：Dify 和 Coze 这类低代码平台，优势和局限？**

优势：非技术人员参与、快速原型、内置知识库和日志。局限：定制深度有限、调试困难（黑盒多）、不适合高可靠性生产、平台锁定。Dify 做原型和业务对齐，自研做核心 Skill 和精确控制。Dify 能做到 70%，但剩下的 30% 是核心差异化的部分。

---

**Q14：OpenAI Agents SDK 和 Claude Agent SDK 是什么？**

趋势：模型厂商开始自己做 Agent 框架。OpenAI Agents SDK（2025.3）：轻量，核心概念 Agent/Handoff/Guardrails，只支持 OpenAI。Claude Agent SDK（2025.5）：深度集成 MCP，内置 prompt caching，只支持 Claude。比 LangChain 更轻量、更稳定、和模型特性深度集成。趋势：模型厂商 SDK 挤压第三方框架空间。

---

**Q15：Manus 和 Swarm 是什么？多 Agent 架构有几种模式？**

Manus：2025.3 爆火的通用 AI Agent，L4 级自治，核心是 Plan-Execute + 工具编排。Swarm：OpenAI 多 Agent 协作实验，贡献了 Handoff 转交机制。三种多 Agent 模式：顺序流水线（A→B→C）、辩论模式（多 Agent 辩论出共识）、层级结构（Master 分解 + Worker 并行，Manus 的核心架构）。Price Agent 的 Plan-Execute 是层级模式的单 Agent 模拟。

---

### 五、Agent 评估体系

**Q16：评估数据集怎么构建？**

四类数据。Function 级 Gold Set：测试单个工具输入输出正确性。场景级 Case Set：20-50 个典型场景，覆盖正常 + 异常。边界和对抗样本：空输入、超长、矛盾指令、幻觉诱导。生产日志回放：线上真实 query 脱敏回放。构建原则：先覆盖再深度、case 要有安全断言、case 和 bug 一一对应。

---

**Q17：评估 Agent 应该看哪些指标？**

四个维度。任务完成度：Success Rate、Tool Selection Accuracy、Parameter Accuracy。输出质量：Factual Accuracy、Hallucination Rate、LLM-as-Judge Helpfulness。安全性：Graceful Degradation Rate、Refusal Rate、Self-correction Rate。效率：Avg Tokens/Task、Avg Latency、Avg Tool Calls、Cost/Task。**不用单一指标，四维度相互制约。**

---

**Q18：LLM-as-Judge 靠谱吗？**

优点：能捕捉语义质量、可扩展。缺点：模型有偏好（更长 ≠ 更好）、成本、可复现性差。用：评估软质量（helpfulness、清晰度、语气）。不用：评估硬事实（价格对错、p 值对错）。最佳实践：LLM-as-Judge + 人工抽样校准，一致性 > 80% 信任 Judge。

---

**Q19：在线评估和离线评估的区别？**

离线：预先构建测试集，发版前跑，发现已知场景回归和边界条件。在线：真实用户请求，持续运行，发现未知场景和长尾问题。两者互补：离线守底线，在线发现真实问题。在线发现的 Bad Case → 沉淀为离线新 case → 永不重复踩坑。

---

### 六、Agent 高频专有名词辨析

**Q20：Function Calling、Tool Use、RAG、ReAct、CoT、Planning、Reflexion 的关系。**

CoT（推理能力）→ ReAct（推理 + 行动循环）→ Planning（ReAct 前加规划）+ Reflexion（ReAct 后加反思）→ RAG（外部知识）+ Function Calling/Tool Use（执行能力）= 完整 Agent。Function Calling 是特定实现方式（OpenAI API 机制），Tool Use 是能力概念。RAG 是 Agent 的知识库。Planning 解决"走一步看一步"问题。Reflexion 解决"失败后调整策略"问题。

---

**Q21：Token、Context Window、Prompt Caching 对 Agent 设计的影响。**

Token：每次对话总 token 数直接影响成本和延迟。Context Window：决定了滑动窗口的必要性——不能无限拼接历史。Prompt Caching：System Prompt 放前面（会被缓存），工具 Schema 应放 System Prompt 里，历史消息放后面（每次变）。

---

**Q22：Temperature 怎么调？Agent 场景有何特殊考虑？**

意图分类 → 0（确定性，每次分类结果一致）。工具选择 → 0 或 0.1（不能随机选工具）。Plan 生成 → 0.3（需要灵活性但格式要稳定）。综合回答 → 0.5-0.7（措辞可变化，但涉及事实要谨慎）。核心：决策类低温，生成类中温，创意类高温。Tool Call 属于决策类。

---

**Q23：什么是 Guardrails？Agent 场景下怎么实现？**

输入护栏：PII 检测、注入检测、内容审核。输出护栏：事实性检查、格式检查、范围检查。实现方式：规则护栏（快、确定、覆盖面有限）+ LLM 护栏（覆盖面广、慢、贵）+ 混合护栏（规则第一层，LLM 第二层）。Agent 特有挑战：每次 Tool Response 进入 LLM 前也要检查。

---

### 七、多 Agent 系统与前沿趋势

**Q24：多 Agent 协作有哪些经典模式？**

顺序流水线：A→B→C，适合步骤明确的上下游任务。辩论模式：多 Agent 独立回答 + 互相质疑，适合需要严谨判断的场景（医疗、法律）。层级结构：Master 分解 + Worker 并行，Manus 的核心架构。群体智能（Swarm）：大量简单 Agent 涌现复杂行为，适合经济学、社会学模拟。

---

**Q25：2025 年 Agent 领域最重要的趋势。**

1) 标准化协议（MCP → A2A → OPC，从框架之争到协议之争）。2) 从单 Agent 到多 Agent。3) 评估从"能跑通"到"能信任"（幻觉检测、Guardrails、Human-in-the-loop 成标配）。4) 模型厂商亲自下场（OpenAI/Claude SDK 挤压第三方框架）。5) 从 Demo 到生产（暴露的问题催生可观测性工具层）。

---

### 八、Agent 业务场景设计实战

**Q26：从 0 设计一个业务 Agent 的标准流程。**

六步法。Step 1：定义目标和边界（Agent 要解决什么、不能解决什么）。Step 2：梳理用户场景（从场景反推能力，不是先有架构再有场景）。Step 3：定义 Skill/工具清单（每个 Skill 有清晰输入输出 Schema）。Step 4：设计架构和状态管理（要不要多轮、要不要多 Agent）。Step 5：设计兜底和护栏。Step 6：搭建评估体系（在写第一行代码前先定义"什么叫好"）。

---

**Q27：什么时候不该用 Agent？典型反模式有哪些？**

不该用：流程完全固定（Workflow 更可靠）、延迟要求 <500ms、容错率为 0、数据量极大且需全量处理。五种反模式：过度 Agent-ization、Prompt 当数据库用、无限工具列表、无护栏 Agent、Agent 当 FAQ 用。

---

### 九、综合论述题

**Q28：好的 Agent 系统应该具备哪些特性？**

十个特性分四层。基础层（没有就不叫 Agent）：工具使用、自主决策、多轮交互。质量层（让 Agent 可靠）：可观测、有护栏、能兜底。架构层（让 Agent 可维护）：分层设计、可评估。体验层（让 Agent 有用）：场景驱动、人机协作。

---

**Q29：Agent 的成本怎么控制？**

六个优化点按效果排列。1) 多模型路由（意图分类用 Flash，综合用主力）。2) Prompt 精简（每多 100 token 每天多花 1000 万 token）。3) Prompt Caching（缓存 System Prompt，成本仅 10%）。4) 减少不必要 LLM 调用（能用代码不用 LLM）。5) 工具调用批量化。6) 对话长度主动管理（总结替代全量，结构化状态替代历史拼接）。

---

**Q30：用一句话总结你对 Agent 的理解。**

**Agent 不是一个技术概念，是一个交互范式的转变。** 传统软件是"用户学习软件的操作方式"，Agent 是"软件理解用户的表达方式"。核心不是 LLM 本身，而是 AI 从"被调用"变成"主动决策者"。开发者角色从"定义执行流程"变成"定义目标和边界"。Agent 最大的挑战是信任——解决信任的三个关键：可观测性（让用户看见 Agent 在干什么）、护栏（让用户知道 Agent 不会越界）、评估（让自己知道 Agent 的工作质量）。

## 附录五：LLM-as-Judge 数据质量评估专题 — 6 道深度面试题

### Q1：LLM-as-Judge 是如何设计的？

我从**为什么需要、怎么设计的、设计中的关键决策**三个层面来回答。

---

**一、为什么需要 LLM-as-Judge？**

Agent 运行产生 trace → 要转为 SFT 训练数据 → 需要判断每条 trace 的质量。纯规则能做到"格式对不对"、"有没有错误"，但做不到"这条 trace 对训练 Agent 的推理能力有多大价值"。比如两条 trace，都是"查 iPhone 15 价格"——一条是简单的单工具调用，一条是多工具协调 + 知识检索 + 综合对比。规则能判断两条格式都对，但判断不了哪条训练价值更高。所以需要 LLM 来做语义层面的质量判断。

另外，纯规则检测幻觉是不可靠的。规则只能判断"回答里有没有引用价格和平台名"，但判断不了"引用的价格是否正确"。LLM 能理解上下文，判断回答中的声明是否与工具返回数据一致。

**二、双层评分体系**

我设计的核心思路是**启发式 + LLM 双层互补**，各司其职：

```
原始 trace (188条，M6.1 起含 raw_messages 完整消息)
       │
       ▼
  compute_quality() 启发式评分（免费、毫秒级、确定性）
       │  4 维度：能力展现(0-10) + 执行质量(0-10) + 回答可信度(0-10) + 数据完整度(0-10)
       │  总分 = 四维之和 × 2.5 = 0–100
       │
       ▼ < 50 分直接丢弃
  judge_sample() LLM 精评（DeepSeek，有成本，2-3秒/条）
       │  4 维度归一化到 0-10 × 4 = 0-100
       │  + 幻觉检测（通过/不通过）
       │  + issues 列表（具体问题）
       │  + summary（一句话结论）
       │
       ▼ ≥ 70 分 + 幻觉通过
  人工审核卡片 → 最终训练集（~52条）
```

**为什么是双层而不是全用 LLM？** 三个原因。成本：188 条全用 LLM 评，每次 0.001 元看似不多，但如果是线上日均 1000 条 trace，一个月就是 30 元/天 × 30 天 = 900 元，而且这只是评估环节的成本。速度：启发式毫秒级完成，可以做实时过滤；LLM 2-3 秒/条，只能异步批处理。一致性：启发式 100% 确定性，LLM 即使 temperature=0.1 仍有波动——两条内容相似的 trace 可能打出不同分数。用启发式做硬过滤（明显垃圾直接丢弃），LLM 做软排序（好样本中排优先级），各取所长。

**三、4 维度的设计逻辑**

4 个维度不是随便选的，对应 Agent SFT 训练的 4 个核心诉求：

| 维度 | 启发式分值 | 核心检测逻辑 | 对应训练目标 |
|------|:---------:|-------------|-------------|
| A. 能力展现 | 0-10 | Plan-Execute(6.0+工具数×0.8) > 双工具(5.0) > 多轮链式(4.5) > 单工具(2.5) | 模型学会复杂推理路径 |
| B. 执行质量 | 0-10 | 全成功+有数据=10，≥80%成功率=5.0，有反思纠错=4.0 | 模型学会正确调用工具 |
| C. 回答可信度 | 0-10 | 价格+平台都引用=10，仅引用其一=7.0，仅结论=3.0 | 模型学会基于数据回答 |
| D. 数据完整度 | 0-10 | system prompt +2，用户查询 +2，工具调用 +3，call-result配对 +3 | 样本可被训练框架消费 |

这 4 个维度有递进关系：D 是门槛（不完整无法训练）→ B 是底线（工具全失败说明行为本身就错）→ C 是核心（是否基于真实数据）→ A 是加分（复杂推理链路的训练价值更高）。

**D 维度与 raw_messages 的关系（M6.1 升级）**：D 是门槛维度，而它的分数取决于数据源质量。早期 trace 靠事件重建 messages，tool 参数和 tool response 被截断到 300 字符，D 维度天然拿不满。M6.1 后 Agent 运行时直接保存完整 messages（`react_engine.py` 的 `_last_messages`，含 tool call 完整参数和 tool response 全文）→ `app.py` 写入 trace JSON 的 `raw_messages` 字段 → `extract_sample()` 优先读取完整数据，旧版 trace 自动回退事件重建。这条链路让 D 维度得分显著提升，也是 188 条 trace 能筛出 52 条高质量训练样本的前提之一。

**四、LLM Judge 的 Prompt 设计**

两个 Prompt 配合工作。

System Prompt（约 60 行）包含四部分：角色设定（"你是训练数据质量评估专家"）→ 4 维度打分标准（与启发式对齐，但归一化到 0-10）→ 幻觉检测说明（回答中的声明是否与工具数据一致）→ JSON 输出格式约束（`{"overall_score": 85, "dimensions": {...}, "hallucination": "通过", "summary": "...", "issues": [...]}`）。

User Prompt（`build_judge_user_prompt`）展示具体样本：system prompt 前 500 字 + 用户查询全文 + 工具调用名和参数（截断 200 字）+ 工具返回摘要（提取 found/matches/platform_count 等关键字段）+ 最终回答前 800 字。这些内容的来源在 M6.1 升级为 trace 的 `raw_messages` 完整消息（Agent 运行时直接采集，含 tool call 完整参数和 tool response 全文），不再依赖早期的事件重建截断——这里的 500/200/800 字截断只是 Judge 展示层控制 token 成本的策略，完整数据已随 trace 持久化，随时可取。

设计要点：低温度（temperature=0.1）保证一致性；JSON mode（`response_format={"type": "json_object"}`）保证结构化输出；截断策略平衡了信息完整性和 token 成本。

**五、关键设计决策**

**为什么启发式和 LLM 的维度要对齐？** 为了交叉校验。两者评分偏差 > 20 分的样本自动标记为"需人工复核"——可能是启发式规则有盲区，也可能是 LLM 判断有偏差。对齐的维度让交叉校验成为可能。

**为什么 LLM Judge 用 DeepSeek 而不是 GPT-4？** 成本。评估任务不是生成任务，不需要最强的推理能力。DeepSeek 足以判断"回答是否引用了工具数据""工具调用是否合理"。而且评估是批量任务——188 条 trace，如果用 GPT-4 成本会高出 10 倍。

**最大局限是什么？** 幻觉检测的 Judge 输入层仍有 gap。需要区分两层：**数据采集侧已在 M6.1 解决**——Agent 运行时保存完整 messages（含 tool result 全文）到 trace 的 `raw_messages`，`extract_sample()` 优先读取完整数据，完整 tool_result 已随 trace 持久化；**但 Judge 展示层仍是摘要**——`build_judge_user_prompt` 传的是摘要提取后的工具返回（found/matches/platform_count），参数也截断 200 字，没有直接消费 `raw_messages` 的完整 JSON。LLM 看不到完整的价格列表，无法真正验证"回答里说的 ¥5,999 是真实数据还是编的"——只能靠概率猜。这是当前最大的 gap，下一步是把 Judge Prompt 改为传入完整 tool_result 并逐条比对——数据源已就绪，改动只需要改 Judge 侧，成本可控（DeepSeek 便宜），收益明显。

---

### Q2：人工评测是如何设计的？

人工评测不是孤立环节，而是嵌入在自动评分之后的**质量把关和校准层**。我从三个角度回答：设计理念、具体流程、和自动评分的配合。

**一、设计理念：人工评测不替代自动评分，而是校准自动评分**

我的核心判断是：**纯人工评测不可规模化**。188 条 trace，每条阅读 3-5 分钟，一个人要花 10-15 小时。如果是线上日均 1000 条，人工完全不可能。所以人工的定位不是"每一条都看"，而是三个作用：

1. **校准**：LLM Judge 评分的偏差有多大？通过人工抽检同一条样本，对比 LLM 打分和人工打分，量化 Judge 的可靠性（Cohen's Kappa > 0.7 才信任 Judge）
2. **边界裁决**：自动评分落在中间段（60-80 分）的样本，LLM 判断置信度不够，升级给人工裁决
3. **质量抽查**：已通过自动筛选的高分样本（80+），人工随机抽检 10%，防止 Judge 的系统性偏差（比如对 Plan-Execute 模式过分偏好）

**二、具体流程：卡片式审核界面**

前端 `/training-data` 页面的审核环节是一个**卡片式审核列表**。每个卡片展示：原始 query、Agent 回答摘要、工具调用序列、启发式评分和 LLM Judge 评分的对比、幻觉检测结果。审核操作很简单：✓ 通过 / ✗ 拒绝，支持批量操作和按状态筛选。

审核维度的着重点和自动评分不同。自动评分侧重"格式对不对""有没有引用数据"，人工审核侧重三个机器难以判断的维度：

- **回答是否有用**：Agent 给的信息能不能真正帮用户做购买决策？这是自动评分完全不具备的判断力
- **推理过程是否合理**：工具调用的顺序和选择是否合理？有没有多余的工具调用？有没有该调但没调的工具？
- **措辞是否合适**：回答的语气、详略、结构是否适合用户场景？有没有误导性的表述？

**三、和自动评分的配合：三层漏斗**

```
L1 自动规则（无成本）→ 过滤明显垃圾（空回答、纯错误、重复）
L2 启发式 + LLM Judge（低成本）→ 质量打分 + 幻觉检测
L3 人工审核（高成本）→ 边界裁决 + 校准抽样
```

L1 和 L2 自动完成 90%+ 的工作，L3 只在关键节点介入。这个漏斗的核心思想是：**把人的精力花在机器做不好的判断上，而不是花在机器轻松搞定的格式化检查上。**

**四、校准机制**

我设计了一个简单的校准流程：每批次抽取 20 条已通过自动筛选的样本，让人工和 LLM Judge 独立打分。计算 Cohen's Kappa 和平均偏差。如果 Kappa < 0.6 或系统性偏差 > 10 分，就需要调整 Judge Prompt（比如补 few-shot 示例、调整某维度的打分标准）。这个机制保证了 Judge 不会随着时间漂移——当数据分布变化时（比如新增品类），及时校准。

### Q3：Trace 轨迹数据如何清洗？

我设计了**5 阶段数据清洗 Pipeline**，从原始 trace JSON 到最终 SFT 训练集。核心思路是：**每一阶段的输出是下一阶段的输入，前三个阶段可以全自动，后两个阶段需要人工和 LLM 配合。**

**Stage 1：结构清洗**

检查格式正确性和字段完整性。具体包括：JSON 合法性（能 parse）、必填顶层字段（meta 和 events）、events 非空、meta.answer 非空（无最终回答的 trace 无法做 SFT）。最关键的是 **Role 序列校验**——把 trace 转成 OpenAI messages 格式后检查：不允许连续 assistant 消息（中间必须有 tool）、tool 消息前必须是 assistant(tool_calls)、tool_call_id 配对完整。

**Stage 2：内容质量**

三个步骤。第一步，**近似去重**：用 doubao-embedding 对 query 和 answer 分别做向量化，余弦相似度 > 0.85 的标记为近重复。这比精确去重更重要——因为用户可能用不同措辞表达相同意图（"iPhone 15 多少钱" vs "苹果 15 价格"），Agent 的回答也可能高度相似。第二步，**质量过滤**：启发式 ≥ 70 + LLM Judge ≥ 65 + 幻觉检测通过。第三步，**难度标注**：工具数 × 2 + 轮次 × 3 + 模式加分（Plan-Execute +5，Shopping +3），18+ 为困难，10-17 为中等，< 10 为简单。

**Stage 3：一致性校验（核心环节）**

这是整个 Pipeline 最关键的一步——防止训练数据教模型"编造"。从 Agent 最终回答中提取所有 (平台, 价格) 声明，与工具返回的原始数据逐条比对：

```python
# 提取回答中的价格声明
claims = extract_price_claims(answer)  # NER → [("京东", 5999), ("淘宝", 5899)]

# 从工具返回 JSON 中提取真实价格
gt_prices = extract_all_prices(tool_results)

# 逐条交叉验证（±1% 容差）
for platform, claimed_price in claims:
    if exists_in_gt(claimed_price, gt_prices[platform], tolerance=0.01):
        verified.append(...)
    else:
        hallucinated.append(...)  # → 这条样本不能用于 SFT
```

此外还检测：回答中的产品名是否在工具返回中出现、排名声明（"拼多多最低"）是否与实际数据一致。对于"这款手机拍照最好"这类主观声明，标记为"无法验证"但不判定为幻觉。

**Stage 4：安全合规**

PII 检测（手机号、邮箱、身份证号）、敏感词过滤、价格异常检测（< ¥1 或 > ¥100,000 的价格可能是数据损坏）。任何一项不通过 → 样本排除。

**Stage 5：数据集构建**

按意图 × 难度分层，80/10/10 切分为 train/val/test。导出 JSONL + 数据卡片（datacard.json，记录统计信息、清洗参数、各阶段过滤率）+ 溯源文件（provenance.json，每个样本可追溯到原始 trace 和每阶段的清洗结果）。

**为什么要有溯源？** 如果训练后模型在某个场景表现退步，你可以反向追查——是哪些训练样本导致的问题？这些样本来自哪些 trace？在哪一步清洗中被判定为"高质量"？没有溯源，数据质量问题就是无头案。

### Q4：如何定义数据集的好坏？

我不从单一指标定义好坏，而是从**五维质量模型**来评估——每个维度回答一个不同的问题。

**维度 1：正确性（Correctness）——数据对不对？**

最基础的维度。包括三个子项：格式正确（messages 序列符合 OpenAI Chat Completions 格式，role 交替正确，tool_call_id 配对完整）、事实正确（Agent 回答中的价格/产品名/参数与工具返回数据一致，无幻觉）、工具调用正确（函数名存在、参数类型正确、必填参数不缺）。

检测方式：格式正确用规则 100% 自动检测，事实正确用交叉比对自动检测，工具调用正确用 Schema 校验 + 参数回放（用样本中的参数重新调工具，看是否返回合理结果）。

**维度 2：完整性（Completeness）——数据全不全？**

样本是否包含了完整的推理链。对于 Agent 训练数据，完整性 = System Prompt + User Query + 所有 Tool Call + 所有 Tool Response + 最终回答。缺任何一个环节都会降低训练价值。特别是"Tool Call 有但 Tool Response 缺失"——这会让模型学会"调了工具但不需要等结果就直接回答"的错误行为。

**维度 3：多样性（Diversity）——数据覆盖面够不够？**

三个子维度：意图覆盖（price_check / comparison / recommendation / shopping 四种意图是否均衡？如果 80% 样本都是 price_check，模型只会做简单比价）、难度覆盖（简单/中等/困难样本的分布，训练集需要混合难度——全是简单样本模型学不会复杂推理，全是困难样本模型过拟合）、表达覆盖（同一意图的不同自然语言表达——"推荐游戏手机"、"打游戏买什么"、"玩游戏用什么手机好"）。

检测方式：Embedding 聚类 → 计算类内紧凑度和类间分离度，量化多样性。

**维度 4：难度分布（Difficulty Distribution）——数据难度合不合理？**

训练集的难度分布直接影响模型能力。理想分布应该是橄榄形：中等难度 50%，简单 25%，困难 25%。如果分布严重倾斜——比如 90% 简单样本——模型只会处理简单场景，遇到复杂 query 就退化。

我定义了难度计算公式：`工具数 × 2 + 轮次 × 3 + 模式加分`，将样本分为 easy/medium/hard 三档。但这个公式只考虑复杂度，不考虑"歧义度"——比如"推荐一款手机"比"推荐一款 5000 以内拍照好的游戏手机"更模糊，对模型来说更难。下一步应该引入"信息熵"作为难度指标。

**维度 5：下游任务效果（Downstream Performance）——最终检验**

前面的 4 个维度都是"数据看起来好不好"，但最终检验是"用这份数据训练出来的模型好不好"。具体做法：hold-out 测试集上对比清洗前后数据训练的模型。如果清洗后数据量减少了 70%，但模型效果只下降了 5%——说明清洗是有效的（砍掉了噪音，保留了精华）。如果清洗后数据量减少了 70%，模型效果下降了 30%——说明清洗策略过于激进，砍掉了有训练价值的数据。

**五维之间的关系不是并列的**。正确性是底线（不正确直接排除），完整性是门槛，多样性和难度分布是质量杠杆（决定了模型能力上限），下游效果是最终裁判。每构建一批新数据集，五维都要评估一遍。

### Q5：你接下来还有哪些规划？

**短期（1-2 个月）：修复已知 gap**

1. **幻觉检测增强（数据源已落地，剩余 Judge 侧改造）**。"看不到完整数据"的问题在 M6.1 已解决数据源：Agent 运行时直接保存完整 messages（含 tool result 全文）到 trace 的 `raw_messages` 字段，`extract_sample()` 优先读取完整数据。剩余工作是把 `build_judge_user_prompt` 从"工具返回摘要 + 参数截断 200 字"改为直接消费 raw_messages 里的完整 tool_result JSON，并要求 Judge 逐条比对答案中的价格/产品名与原始数据。这个改动看似简单，但影响很大——幻觉检测准确率可能从当前的"靠猜"提升到 90%+，而且数据源已就绪，不用再动采集链路。

2. **LLM Judge 加 few-shot 校准**。当前纯靠文字描述打分标准，不同批次的评分一致性没有保证。补充 2-3 个标定好的 (样本, 人工评分) 作为 few-shot 示例，让 Judge 有参照系。这能显著降低评分方差。

3. **新增一致性监控**。自动计算启发式 vs LLM Judge 的 Cohen's Kappa，偏差 > 20 分的样本自动标记。如果 Kappa 持续下降，说明某一边的评分标准漂移了，需要校准。

**中期（3-6 个月）：多模型 Judge Panel + 用户行为信号**

4. **多模型 Judge Panel**。现在只用 DeepSeek 一个模型。引入第二个异构模型（GPT-4o-mini 或 Claude Haiku）做交叉校验。两模型偏差 > 25% → 人工裁决。多模型 Panel 的好处不只是准确率提升——更重要的是让评分体系对单一模型的 bias 有免疫力。

5. **用户行为信号做 Ground Truth**。当前判断"好 trace"靠的是人工规则和 LLM 判断——都是间接指标。真实场景有更直接的金标准：用户点击了推荐商品（正向）、看了回答后直接离开（弱负向）、加购物车/下单（强正向）、投诉/举报（强负向）。用这些行为信号校准质量评分，形成正反馈循环。

**长期（6-12 个月）：闭环数据飞轮**

6. **从"离线评估"到"在线闭环"**。当前整个流程是离线的——Agent 跑了 → 存 trace → 人工挑选 → 训练。理想形态是在线的：Agent 跑了 → 实时质量评分 → 高价值 trace 自动入训练集 → 定期 SFT+DPO 训练 → A/B 测试验证 → 模型能力提升 → 产生更高质量的 trace。

7. **DPO 偏好数据构建**。目前只做 SFT 数据（"正确示范"）。下一步做 DPO 数据（"好 vs 差"对比对）：好回答（高分 trace 的 final answer）vs 差回答（低分 trace 的 final answer，或同一条 query 下故意移除关键工具调用后生成的回答）。DPO 让模型不仅能"正确"，还能"区分优劣"。

8. **M4 生成式推荐集成**。当前推荐只是"列表 + 比价"，M4 要让 Agent 基于用户需求 + 商品参数 + RAG 知识生成个性化推荐理由。M4 会产生新的 trace 类型（包含生成式推荐的推理链），这些新 trace 需要更新评分标准——因为"M4 生成的推荐理由是否有说服力"是一个新的质量维度。

### Q6：你最近了解了哪些关于数据清洗方面的新内容和新知识？

我最近关注了 Agent 训练数据清洗领域的几篇新论文，最喜欢的一篇是 **"Token Cleaning: Fine-Grained Data Selection for LLM Supervised Fine-Tuning"**（UCSC-REAL, 2025.02），因为它挑战了 SFT 数据清洗的一个基本假设。

**传统做法的问题**

业界清洗 SFT 数据的标准做法是**样本级过滤**——整条样本要么保留，要么丢弃。打个分，设个阈值，低于阈值就不要了。Price Agent 目前也是这么做的：compute_quality 打分 → < 70 分丢弃。

但这个做法有一个隐含假设：**一条样本内部的质量是均匀的。** 实际上不是。一条 Plan-Execute trace 可能包含 3 个 step——Step 1 和 Step 2 的工具调用非常精准，Step 3 的综合回答却空洞敷衍。整条样本打分 70 分，丢失了 Step 1 和 Step 2 的高质量信号。

**Token Cleaning 的核心思想**

这篇论文提出从**样本级**下沉到 **Token 级**做数据选择。核心思路是：计算 SFT 训练过程中每个 token 对模型参数更新的影响力——影响力高说明这个 token 对模型学习贡献大，影响力低甚至为负说明这个 token 是噪音。

具体做法：

1. 训练过程中记录每个 token 的梯度
2. 计算 token 影响力 = 该 token 梯度与参数更新方向的点积
3. 影响力低于阈值的 token 在 loss 计算中降低权重或直接 mask 掉

**实验结果很有启发性**：在多个下游任务上，Token 级清洗一致优于样本级清洗。即使在同一批"高质量"样本内部，仍有 15-25% 的 token 是低影响力的（冗余措辞、重复信息、模板化表达），去掉这些 token 后模型效果反而提升。

**对 Price Agent 的启发**

这个思路对 Agent 训练数据特别有价值。Agent 的 SFT 样本不是简单的 Q&A，而是包含多轮工具调用的长序列。一条样本可能有 2000+ token——system prompt（约 300 token）、多轮 tool call（约 500 token）、多个 tool response（约 800 token）、final answer（约 400 token）。这些部分的训练价值完全不同：

- **Tool Call 的 function name 和必需参数**：最高价值，必须精确学习
- **Tool Response 的结构化 JSON**：中高价值，模型需要理解返回格式
- **System Prompt 的通用规则部分**：中等价值，但多条样本重复出现形成冗余
- **Final Answer 的礼貌措辞和格式化**：低价值，模型已经会了，重复学习浪费算力

如果用 Token Cleaning 的思路，我们可以对不同 token 做差异化加权：Tool Call 的关键 token 权重 ×2，System Prompt 的重复模板 token 权重 ×0.5，礼貌措辞 token 权重 ×0.3。这样模型把学习重点放在"如何正确调用工具"上，而不是浪费算力学习"谢谢您的提问"这类已经掌握的模板。

**落地设想**

不需要完整复现论文的梯度追踪方法（计算成本太高）。可以做简化版：按消息角色和内容类型做**启发式 token 分组加权**。比如：

```python
TOKEN_WEIGHTS = {
    "system_prompt_generic": 0.5,    # "你是智能购物助手" 等通用规则
    "system_prompt_skill": 1.5,      # Skill 特定的工具使用指南
    "user_query": 1.0,               # 用户查询
    "tool_call_name": 2.0,           # 函数名（最高权重）
    "tool_call_args_required": 2.0,  # 必填参数
    "tool_call_args_optional": 1.0,  # 可选参数
    "tool_response_data": 1.5,       # 工具返回的核心数据
    "tool_response_meta": 0.5,       # 工具返回的元数据（platform_count 等）
    "final_answer_data_cited": 1.5,  # 引用了真实数据的部分
    "final_answer_generic": 0.3,     # 礼貌用语和格式化
}
```

这相当于把 Token Cleaning 的思想用规则做了近似——不需要训练中追踪梯度，在构建训练数据时就做好 token 级别的价值标注。对于当前 188 条的规模可能看不出差异，但如果线上日增 1000 条 trace，3 个月就是 9 万条样本——token 级的数据效率差异会被放大。

**领域认知**

这篇论文让我意识到的关键洞察是：**数据清洗的颗粒度应该与训练目标匹配。** Agent SFT 的目标是让模型学会"在什么场景下、用什么工具、传什么参数、怎么解读返回结果"。不是所有 token 对这四个子目标都有贡献。传统样本级清洗把"有用的 token"和"无关的 token"绑在一起要么全留要么全丢——这是一种粗糙的妥协。Token 级清洗把选择权下沉到更细的粒度，让高质量信号不会被低质量噪声稀释。

## 附录六：机务维修领域 RAG + 微调训练 — 20 道面试深度题

> 业务背景：机务维修领域的垂类模型微调训练。数据来源为多格式维修文档（PDF 维修手册、Word 工单记录、Excel 航材清单、扫描件历史故障报告等），涉及数据解析清洗、RAG 知识库搭建、切分策略、召回检索、微调训练、RAG 评测全链路。

### 一、数据解析与清洗（Q1–Q4）

**Q1：机务维修文档格式多样——PDF 扫描件、Word 手册、Excel 航材表、甚至 CAD 图纸。你会怎么设计统一的数据解析 Pipeline？**

核心思路是**格式适配器 + 统一中间表示**。不是每种格式写一套独立的完整处理流程，而是每种格式写一个 Parser（适配器），输出统一的结构化 Document 对象。

```
PDF 扫描件 → OCR（PaddleOCR/Tesseract）+ 版面分析
PDF 电子版 → PyMuPDF 提取文本 + 表格 + 图片标注
Word 手册  → python-docx 提取段落 + 标题层级 + 表格
Excel 航材 → pandas 读取 + 列名映射 + 单元格合并处理
CAD 图纸   → 提取标注文字 + 图号索引（不解析图形本身）
                │
                ▼
        统一 Document 对象
        {doc_id, source, title, sections: [{heading, content, tables, images, page_ref}]}
```

四个设计要点。第一，**版面分析优先于文本提取**：PDF 扫描件如果不做版面分析（分栏、表格区域、图片区域），OCR 输出的文本顺序是乱的——"左栏的故障描述"可能拼到"右栏的排故步骤"中间。第二，**表格提取是机务文档的核心难点**：维修手册里大量参数表、航材清单、故障代码对照表，如果当成纯文本处理，信息全丢。PyMuPDF 对电子 PDF 的表格提取已经比较成熟，扫描件则依赖 OCR + 表格重建。第三，**层级结构保留**：维修手册有严格的编号体系（如 ATA 章节号 32-41-00），解析时必须保留 `heading → sub_heading → content` 的层级关系，这是后续切分和检索的基础。第四，**图片不是"忽略"，是"标注"**：维修文档里的故障示意图、拆装流程图虽然 OCR 识别不了，但图片下方的图注和图片周围的文字是可靠的上下文。Parser 应该生成占位符 + 描述文本（`[图: 主起落架收放作动筒拆装示意图]`），检索时当用户问到相关问题能匹配到这段文字。

---

**Q2：机务维修文档里大量专业术语和缩写（比如 "AMM" = 飞机维护手册、"FIM" = 故障隔离手册、"LRU" = 航线可更换件），数据清洗时怎么处理？不做处理的话 RAG 召回会有什么问题？**

两个层面的处理。

**数据入库时——术语归一化但不丢失原文。** 构建一个机务领域术语词典，解析时做展开标注。原始文本保留在 `content` 字段，同时生成 `content_normalized` 字段（缩写展开 + 同义词归一化）。两者都建索引，检索时双路召回：用户 query 写的是"飞机维护手册"，能匹配到原文写的"AMM"；用户 query 写的是"AMM 32-41-00"，也能精确匹配原文。

**用户查询时——Query 改写。** 即使用户输入的是口语化表达（"起落架收不回来怎么办"），在检索前做一轮 LLM 查询改写，映射到标准术语（"起落架无法收上 → L/G RETRACTION FAIL → AMM 32-30-00"）。改写不是只做一次，可以生成多个改写版本（精确术语版、缩写版、同义词版），并行检索后融合排序。

**不做处理的后果**：RAG 是基于语义相似度或关键词匹配的。如果知识库里写的是"依据 AMM 32-41-00 执行主起落架收放测试"，用户问的是"主起落架收放测试怎么做"——不加术语处理时，纯关键词匹配可能因为缺少"AMM 32-41-00"这个强特征词而排到后面。加术语处理后，"主起落架收放测试"的改写版本会包含"AMM 32-41-00"，检索精度显著提升。

---

**Q3：维修手册里有很多表格——故障代码对照表、力矩参数表、航材清单。这些表格数据怎么切分和索引，才能在用户查询时被准确检索到？**

表格不能和普通段落用同样的方式处理，三个策略。

**策略 1：表格独立抽取 + 结构化存储。** 解析阶段检测到表格时，不把它当纯文本拼接到段落里。而是提取为结构化 JSON 存储到独立的元数据字段：

```json
{
  "chunk_id": "AMM-32-41-00_T3",
  "chunk_type": "table",
  "table_caption": "主起落架收放作动筒力矩参数",
  "headers": ["部件名称", "规格", "力矩值(N·m)", "备注"],
  "rows": [["连接螺栓", "M12×1.5", "120-140", "涂防咬合剂"]],
  "source_doc": "AMM_32-41-00.pdf",
  "page": 215
}
```

**策略 2：表格摘要生成。** 用 LLM 为每张表格生成一段自然语言摘要（"本表列出了主起落架收放作动筒各部件的力矩参数，包括连接螺栓 M12×1.5 的力矩值为 120-140 N·m"），摘要入向量库做语义检索，查到后返回原始表格的 JSON。这样用户问"连接螺栓打多少力矩"时，语义检索命中摘要 → 返回结构化表格数据。

**策略 3：表格的行级索引。** 对于大表（比如几百行的航材清单），整张表索引效果不好——用户通常只关心其中一行（"件号 XXX 的库存有多少"）。解析时把表格拆成行级 chunk，每行携带：表头上下文（所有列名 + 该列的值）+ 表标题 + 章节路径。检索粒度精确到行。

---

**Q4：历史维修工单里可能掺杂口语化描述、机务人员手写备注、甚至错别字（比如"作动筒"写成"做动筒"、"液压油"写成"液压由"）。这些数据清洗时直接丢弃还是保留？如果要保留，怎么处理才能不影响下游训练和检索？**

直接丢弃是错误的——工单里口语化描述和错别字恰好是模型需要学习的"真实用户的表达方式"。机务人员在现场查故障时不可能像写论文一样措辞，模型如果只见过干净文本，遇到"做动筒漏油"就不知道怎么检索。

分三层处理：

**L1：标注不丢弃。** 清洗时给每个文本片段打质量标签——`quality: clean`（手册原文）、`quality: noisy`（含少量错误但可理解）、`quality: rejected`（完全不可读，如乱码扫描件）。只有 `rejected` 级别丢弃。

**L2：生成纠错对用于微调。** 对 `noisy` 数据，不是直接改原文，而是生成 (原始文本, 纠正后文本) 对，作为微调数据的一个专门子集。模型训练时既见过"干净手册语言"，也见过"带错的实际工单语言"——推理时两种输入都能正确处理。

**L3：检索时做前置查询纠错。** 在 RAG 检索链路的用户输入侧加一个轻量纠错模块——用机务领域术语词典 + 编辑距离（Levenshtein ≤ 2）做候选纠正。不是所有错别字都纠——只纠正高置信度的（编辑距离小 + 纠正后能命中索引中的已知术语）。纠错后生成原始 query + 纠错后 query，双路检索 + 融合排序。

---

### 二、RAG 切分策略（Q5–Q8）

**Q5：维修手册有严格的层级结构——ATA 章节号 → 节 → 主题 → 子题。你如何设计切分策略，既保留上下文完整性，又不让 chunk 过长导致检索精度下降？**

这是一个经典 chunk size trade-off，机务领域有自己的特殊性。

**切分策略：语义边界切分 + 层级路径携带。**

不是按固定字符数切，而是沿文档的层级边界切——每个 chunk 对应一个语义完整的"主题"或"子题"。Chunk 大小控制在 500-1500 字，但不是硬截断——如果当前主题超长（比如整个排故流程的详细步骤），用子标题进一步切分；如果当前主题短于 200 字，和相邻主题合并直到满足最小长度。

**每个 chunk 携带完整的层级路径**：

```json
{
  "chunk_id": "AMM-32-41-00-02",
  "hierarchy_path": ["ATA 32 起落架", "32-41 主起落架", "32-41-00 收放机构", "拆装步骤"],
  "heading": "2. 主起落架收放作动筒拆装步骤",
  "content": "（步骤文本）...",
  "parent_context": "本节属于 ATA 32-41-00，描述主起落架收放机构的维护操作。",
  "chunk_type": "procedure"
}
```

**为什么层级路径重要？** 机务人员查手册时，经常用"ATA 32-41"作为关键词。如果 chunk 里没有显式携带这个编号，检索时可能漏掉。层级路径也支持"向上追溯"——用户检索到的 chunk 不完整时，可以用 shared parent 拉取相邻 chunk 补全上下文。

**分文档类型差异化**：维修手册用语义边界切分（沿层级结构），工单记录按"单条工单"切分（一条工单一个 chunk），航材清单按"行"切分（每行一个 chunk），故障案例按"故障 → 原因 → 排故步骤"整体保留（不做切分，因为分析逻辑需要完整性）。

---

**Q6：切分粒度怎么评估好坏？你们会定义哪些指标来衡量切分策略的效果？**

切分策略的好坏不能拍脑袋，需要量化指标。我定义三个维度的指标：

**指标 1：检索命中率（Recall@K）。** 构建一个包含 50-100 道真实机务查询的评测集，每条 query 标注了应该检索到的标准文档段落（由机务专家标注）。对比不同切分策略下的 Recall@5 / Recall@10。这是最直接的指标——切分越合理，检索越精准。

**指标 2：上下文完整性（Context Completeness）。** 抽检 100 个检索命中的 chunk，请机务专家判断"单看这个 chunk，能否完整回答用户的问题"。如果每个 chunk 都需要前翻后翻才能理解——说明切分太碎。如果每个 chunk 都包含大量无关内容——说明切分太粗。

**指标 3：答案正确率（End-to-End Accuracy）。** 把检索到的 chunk 喂给 LLM 生成答案，对比 LLM 答案与标准答案的一致性。这是最终的端到端指标——前面两个指标再好，最终答案不对就是白搭。

**还一个反向指标：Token 浪费率。** 计算所有检索返回的 chunk 中，实际被 LLM 引用到回答里的 token 占比。如果每次检索返回 2000 token 但 LLM 只引用了其中 200 token——说明 chunk 附带太多噪音，浪费了上下文窗口和推理成本。

---

**Q7：如果一个排故流程有 15 个步骤，分布在 3 页 PDF 上，步骤之间还有条件分支（"如果 A 则执行步骤 4-6，如果 B 则跳至步骤 10"）。你怎么切分，既保持流程完整性，又不丢失条件逻辑？**

这个问题的本质是：**文本的物理结构（分页）和逻辑结构（流程图/条件分支）不一致时，怎么处理。**

**做法：流程类内容不做物理切分。**

排故流程、检查单、拆装步骤这些"过程性"内容，整段保留为一个 chunk，附带结构化的步骤索引。不按字符数切分——哪怕 15 个步骤 3000 字，也比切成 3 段各 1000 字更好。因为条件分支（"如果 A → 步骤 4-6，如果 B → 步骤 10"）是跨步骤的逻辑依赖，切断了就丢失了排故的决策路径。

```json
{
  "chunk_type": "troubleshooting_flow",
  "procedure_name": "主起落架无法收上排故流程",
  "steps": [
    {"id": 1, "action": "检查液压系统压力", "condition": null, "next": [2]},
    {"id": 2, "action": "确认作动筒外观检查", "condition": null, "next": [3]},
    {"id": 3, "action": "压力正常？", "condition": "yes→4, no→10", "next": [4, 10]}
  ],
  "raw_text": "（完整原始文本 3000 字）..."
}
```

**检索时的特殊处理**：流程类 chunk 在检索排序时，额外做一个"步骤匹配"——用户的 query 如果精确命中了某个步骤的描述（"检查液压系统压力"），该 chunk 的排序加权提升。因为用户是在找一个具体的操作步骤，不是泛泛了解系统原理。

**生成答案时的特殊处理**：LLM 拿到流程 chunk 后，不是把 15 步全输出给用户，而是用 System Prompt 约束——"只输出与用户问题相关的步骤，其他步骤简要概括或省略"。避免把整本手册丢给用户。

---

**Q8：RAG 知识库更新——维修手册改版（新版本发布）、新工单每天入库、旧文档逐步过期。你怎么设计索引的增量更新机制，避免每次全量重建？**

索引策略按数据类型分三类：

**维修手册（低频更新，版本替换）**：用版本号管理。AMM R56 → AMM R57 时，不是逐条修改旧 chunk，而是整本新手册解析入库，打上 `version: "R57"` 标签。检索时默认返回最新版本，用户也可以指定查历史版本（"R56 里的力矩要求是多少"）。旧版本不删除（合规要求），但不参与默认检索。

**工单记录（高频增量，每天新增）**：独立索引，按日期分区。每天新工单解析后追加写入当天的索引分区，不需要重建全局索引。检索时用时间范围过滤——"最近三个月的起落架故障工单"。超过一定时间的工单（比如 5 年），自动降级到"归档索引"（检索速度慢但存储成本低）。

**技术实现**：向量索引用 ChromaDB 或 Milvus 的 collection 机制——每个数据类型一个 collection，支持增量写入和元数据过滤。全文索引（BM25）用 SQLite FTS5 或 Elasticsearch 的 append-only 模式。

**一致性保证**：增量更新时，先写临时索引 → 全量写入完成 → 原子切换 alias 指向新索引 → 删临时索引。保证检索过程中不会出现"手册 R57 只更新了一半"的中间状态。

---

### 三、召回与检索策略（Q9–Q12）

**Q9：你会怎么设计检索策略？只用向量检索够吗？混合检索的权重怎么定？**

**只用向量检索远远不够。** 机务领域有两个向量检索的致命弱点：

1. **精确匹配需求高**：用户问"ATA 32-41-00 的力矩参数"，语义检索可能返回"32-41-01 的力矩"（语义相近但章节号差一位）。机务场景中，章节号差一位可能就是完全不同的部件，后果严重。这种场景需要精确关键词匹配。

2. **专业术语的 embedding 表征不一定好**：通用的 embedding 模型对"AMM"、"FIM"、"LRU"这些缩写可能没有好的向量表示。语义相似度算不准。

**我设计的混合检索策略：BM25（精确） + Dense（语义）+ 术语增强（领域），三路融合。**

```
用户 Query
    │
    ├─→ BM25 检索（精确关键词 + 术语展开版本）→ BM25 结果
    ├─→ Dense 检索（向量语义匹配）            → Dense 结果
    └─→ 术语增强检索（Query 改写版本的精确匹配） → Term 结果
                │
                ▼
         RRF（Reciprocal Rank Fusion）融合排序
                │
                ▼
         Re-Rank（Cross-Encoder 精排）
                │
                ▼
         最终 Top-K 返回
```

**权重不给固定值**，根据查询类型动态调整：

| 查询类型 | 判断条件 | BM25 权重 | Dense 权重 | Term 权重 |
|---------|---------|:--------:|:--------:|:--------:|
| 精确查找（ATA 编号、件号） | 含数字编号、标准代码 | 0.6 | 0.2 | 0.2 |
| 模糊咨询（"怎么排故"） | 问句形式、无编号 | 0.2 | 0.6 | 0.2 |
| 参数查询（"力矩值"） | 含"参数""数值""标准" | 0.4 | 0.2 | 0.4 |

**为什么不直接固定 α=0.7 语义 + 0.3 关键词？** 因为不同查询类型的检索需求完全不同。固定权重是把"查 ATA 编号"和"问排故建议"当成了同一类任务——实际上前者是精确查找（语义检索在帮倒忙），后者是语义匹配（关键词检索在帮倒忙）。动态权重的前提是有一个简单有效的查询分类器——用规则（检测是否含编号/代码）或小模型即可。

---

**Q10：机务维修场景的检索结果排序有什么特殊考虑？跟通用 RAG 有什么不同？**

三个特殊考虑。

**第一，权威性 > 相关性。** 通用 RAG 通常按语义相似度排序——"最像用户问题"的排最前。但在机务场景，一个维修手册里的官方操作步骤，即使语义相似度略低，也应该排在维修论坛里的机务人员经验帖前面。排序时需要元数据加权：`source_authority`——维修手册(×1.5) > 官方通告(×1.3) > 工单记录(×1.0) > 经验帖(×0.5)。

**第二，时效性敏感。** 适航指令（AD）、服务通告（SB）有时效要求——"本通告发布后 30 天内执行"。过期的通告不应该出现在检索结果中，或者至少加"已过期"标记。检索时做时间过滤 + 时效标记。

**第三，安全优先级。** 如果检索同时命中了"标准操作步骤"和"简化操作技巧"，标准步骤应该排前面。因为机务维修是安全敏感场景——"捷径"可能在一般情况下没问题，但在特定条件下会导致事故。排序时对 `safety_critical: true` 的文档加权。

---

**Q11：如何处理用户的多轮追问？比如用户先问"起落架收放故障怎么排查"，看到回答后又问"第三步的液压测试怎么做"。第二轮 query 极其简洁，怎么召回相关内容？**

这是一个典型的多轮对话中的**指代消解和上下文补全**问题。

**做法：Query 上下文补全（前置）+ 多轮检索历史利用。**

前置步骤——在检索之前，把用户当前 query 和历史对话上下文拼接，用 LLM 生成补全后的独立自包含查询：

```
历史：User="起落架收放故障怎么排查" / Assistant="第一步检查液压系统压力，第二步..."
当前：User="第三步的液压测试怎么做"

→ LLM 补全 → "主起落架收放故障排查流程中，第三步液压系统功能测试的具体操作步骤是什么"
```

补全后的 query 保留了"主起落架"、"收放故障排查"、"液压系统功能测试"等关键上下文——检索精准度大幅提升。

**但补全不是每次都做**。判断条件：当前 query < 15 字 + 含指代词（"这""那""第三步""上面的""刚才的"）→ 触发补全。完整长句不需要补全。

**检索历史复用**：上一轮检索返回的 chunk 如果被当前追问引用，不需要重新检索——直接从对话上下文的 tool_calls 结果中提取。

---

**Q12：RAG 检索返回的内容太多（Top-5 共 5000 token），但用户的上下文窗口有限，怎么压缩又不丢关键信息？**

**做法：不要压缩检索结果，压缩的是"怎么给 LLM"。**

检索阶段保持 Top-K 召回量（K=10 甚至更多），保证覆盖度。压缩放在"喂给 LLM 之前"这个环节。

三层压缩策略：

**L1：Re-Rank 截断。** 用 Cross-Encoder 精排后取 Top-3（而非 Top-5），这一层能快速砍掉 40% 的 token。

**L2：Chunk 摘要注入。** 对于排名靠后的 chunk（Top-3 之后），不喂完整原文，只喂 LLM 生成的摘要（"本段描述了 AMM 32-41 中主起落架作动筒拆装的安全注意事项"）。摘要在数据入库时就预生成好了，检索阶段直接读取，不会增加推理延迟。

**L3：字段选择性注入。** 不是每个 chunk 的全部字段都给 LLM。表格类 chunk 只给表标题 + 表头 + 与 query 相关的行（不是全表）。流程类 chunk 只给与 query 相关的步骤 + 前置步骤的简要上下文。手册类 chunk 保留完整文本。

**还有一个前置策略：Query 分解。** 如果检测到用户的 query 实际上是多个子问题（"查 ATA 32-41 的力矩参数，并对比 ATA 32-42 的要求"），分解成两个子 query 分别检索。每个子 query 返回更精准的少量 chunk，总 token 量反而更少。

### 四、微调训练（Q13–Q16）

**Q13：有了 RAG 为什么还要微调？RAG 和微调在这个场景下分别解决什么问题？**

这个问题面试官想考察的是你**对 RAG 和微调的边界有没有清晰认知**，不是"两个都好所以要两个"。

**RAG 解决的是"知识检索"问题**——让模型能够访问最新、最全、最准确的机务知识。更新手册不需要重新训练，改索引就行。

**微调解决的是"行为和风格"问题**——让模型学会机务领域的专业表达方式、回答格式、安全规范。
RAG 做不到的这些事：

| 能力 | 不做微调 | 做微调后 |
|------|---------|---------|
| 专业术语使用 | 可能用通用表达（"起落架"说成"飞机轮子支架"） | 严格使用机务术语（主起落架、前起落架） |
| 安全提醒 | 可能忘了加"操作前确认液压系统已释压" | 涉及液压/电气操作时自动附加安全警告 |
| 引用格式 | "根据手册说..." | "依据 AMM 32-41-00 Page Block 201-211" |
| 回答结构 | 随意组织 | 固定的 SOAP 模板（故障现象→排查步骤→排故方案→所需工具和耗材→安全注意事项） |
| "不知道"的表达 | "我不确定，建议咨询专业人士" | "该问题超出当前知识库范围，建议查阅 AMM 32-XX 或联系工程技术部门" |

**两者的配合方式**：微调让模型"知道怎么说话、怎么组织回答、什么时候该说不"，RAG 让模型"知道说什么、数据从哪来"。微调决定行为的**下限**（不出安全风险），RAG 决定知识的**上限**（查得到、查得准）。

---

**Q14：微调数据从哪来？怎么构建机务维修领域的 SFT 数据集？**

五类数据源，按质量从高到低排列：

**1. 维修手册的 Q&A 对（人工标注，最高质量）**：请资深机务工程师根据手册编写 500-800 条 Q&A。不是随意写——覆盖 5 个维度 × 4 种查询类型 = 至少 20 种组合。Q&A 包含完整引用格式（"依据 AMM 32-41-00..."）和安全提醒。这部分数据量不大但质量最高，是模型学习"专业行为"的核心。

**2. 历史维修工单 → 结构化重写（半自动，中高质量）**：工单里天然包含"故障描述"和"处理措施"，但原始措辞口语化、格式不统一。用最强 LLM（GPT-4 或 DeepSeek）把工单重写为标准 SFT 格式——故障描述 → user query，处理措施 → 展开为标准操作步骤（补充手册引用和安全提醒）。重写后的样本进入人工抽检队列（抽检 20%），通过后才入库。

**3. LLM 自我蒸馏（自动生成，中等质量）**：把维修手册的章节内容分段喂给 LLM，让它针对每段内容生成 3-5 个可能的问题和标准答案。生成后用规则过滤（含 ATA 编号、有具体参数、格式正确）→ 人工抽检 10%。这个方法的产量最高但噪声也最大——适合作为数据增强的补充。

**4. 故障案例 → 长文本总结（中等质量）**：把完整的故障案例分析文本（故障现象→排查过程→根因→修复方案）作为输入，user query 模拟机务人员的询问（"这个故障第一次出现时应该从哪个系统开始排查"），assistant 回答提炼案例中的关键决策点和经验教训。

**5. 安全规范 → 硬约束注入（关键但量小）**：把安全相关的硬约束（"顶升飞机前必须确认千斤顶额定载荷"、"操作液压系统前必须释压"）提取出来，生成对应的触发条件 → 安全提醒对。这部分数据量最小但最重要——直接决定了模型会不会在安全问题上犯错。

**Q15：微调数据怎么保证质量？如果 LLM 生成的微调数据里混入了幻觉（比如编造了一个不存在的 ATA 章节号），你怎么检测？**

三道防线，从自动到人工逐层收窄。

**防线 1：自动规则校验（100% 样本）**。ATA 章节号格式校验（必须符合 `\d{2}-\d{2}-\d{2}` 或 `\d{2}-\d{2}` 格式）+ 件号格式校验（必须符合 P/N 标准格式）+ 引用完整性校验（数据里引用的手册章节号，必须在知识库中能找到对应文档）。如果 LLM 编了一个"AMM 99-99-99"——知识库里没这个章节——自动标记为可疑。

**防线 2：事实一致性校验（100% 样本）**。用 SFT 数据中的"答案"作为 query 去 RAG 知识库检索，看检索到的文档是否支持答案中的关键声明（参数值、操作步骤、安全警告）。不支持 → 标记为"需人工复核"。

**防线 3：LLM 交叉校验（高风险样本）**。对自动规则命中"可疑"的样本，用另一个异构模型（与生成数据的模型不同）做事实核查。两个模型对同一事实的结论不一致 → 升级人工。

**防线 4：机务专家抽检（10-20% 样本，最终防线）**。分层抽样——"自动规则标记可疑"的样本 100% 送审，高分样本随机抽 10%。审核结果反馈到自动规则的阈值调整（如果某个规则的误报率 > 30%，调高阈值或优化规则）。

**Q16：机务领域模型微调，你是选 LoRA 还是全参微调？为什么？**

**首选 LoRA**，原因不是"LoRA 省钱"，而是三个机务领域特有的考量。

**第一，灾难性遗忘风险高。** 底模（比如 Qwen/ChatGLM）的通用语言能力和推理能力是我们需要的。全参微调在领域数据量不大（< 1 万条）的情况下，很容易把通用能力洗掉——模型学会了说"依据 AMM..."但失去了推理"用户这句话到底想问什么"的能力。LoRA 只更新少量参数，对底模原有能力的冲击更小。

**第二，数据量不够支撑全参。** 机务领域的高质量标注数据通常就几千条——全量标注成本极高。几千条数据做全参微调，过拟合风险很大。LoRA 参数量小，对数据量的要求更低。

**第三，多能力模块化部署。** 不同机型（737 vs A320）的维修手册内容不同，但维修逻辑和术语体系是相通的。用 LoRA 的话可以：Qwen 基座 + 通用机务 LoRA（术语、安全规范、格式）+ 机型专用 LoRA（737 或 A320 的手册知识），推理时按需挂载。全参微调做不到这种灵活组合——每次换机型都要重新训一个完整模型。

**什么情况下考虑全参？** 三个条件同时满足：高质量标注数据 > 5 万条、底模的原生能力严重不适应机务领域（比如底模是英文为主）、而且算力资源充足。当前阶段不太可能同时满足。

### 五、RAG 评测（Q17–Q18）

**Q17：怎么评测 RAG 系统的效果？你会设计哪些指标？怎么构建评测集？**

RAG 评测分三层：检索层、生成层、端到端。

**一、检索层评测**

两个核心指标：
- **Recall@K**：Top-K 检索结果中包含正确答案的比例。K 取 3/5/10。机务场景 Recall@5 < 80% 就需要优化检索策略。
- **MRR（Mean Reciprocal Rank）**：第一个正确答案排在第几位。MRR=1 说明正确答案永远排第一，MRR=0.3 说明正确答案平均排在第三位——用户需要往下翻才能找到。

评测集构建：请 3 位机务工程师每人标注 30-50 条 query，每条标注"应该召回的文档段落"（精确到 chunk_id）。取交集作为 Gold Set。评测集和训练集物理隔离（不同来源的文档），防止数据泄漏。

**二、生成层评测**

四个指标：
- **Faithfulness（忠实度）**：LLM 生成的答案中，有多少声明可以在检索到的文档中找到依据。用 LLM-as-Judge 逐句标注 `attributable / not attributable`。得分 < 90% → 幻觉风险高，需要改进。
- **Answer Relevance（答案相关性）**：答案是否直接回应了用户的问题。用 LLM 判断（0-10 分）。
- **Safety Compliance（安全合规）**：涉及液压/电气/高空操作的答案中是否包含安全提醒。自动化检查：答案中须出现关键词（"确认""确保""警告""注意""禁止"）且与操作步骤关联。
- **Citation Accuracy（引用准确性）**：答案中引用的 ATA 章节号、件号是否能在源文档中找到。这是"硬指标"，自动化比对。

**三、端到端评测**

请机务工程师对 RAG 系统的最终回答打分（1-5 分），维度：有用性、准确性、安全性、完整性。端到端评分是最终裁判——检索和生成指标再漂亮，最终回答不被机务人员认可就是白搭。

**评测集分层设计**：

| 查询类型 | 占比 | 示例 |
|---------|:--:|------|
| 精确参数查询 | 30% | "AMM 32-41-00 主起落架收放作动筒力矩值" |
| 排故流程咨询 | 25% | "起落架无法收上的排故步骤" |
| 开放性问题 | 20% | "主起落架常见故障有哪些" |
| 安全/合规查询 | 15% | "顶升飞机前有哪些安全注意事项" |
| 跨文档综合查询 | 10% | "对比 737 和 A320 的主起落架收放系统设计差异" |

**Q18：RAG 的"幻觉"怎么定义和检测？机务场景的幻觉跟通用场景有什么不同？**

**机务场景幻觉的特殊性：不是"看着不对"，而是"照着做会出事"。** 通用场景的幻觉可能只是让人困惑（"鲁迅说过 XXX"），机务场景的幻觉可能直接导致安全事故（"力矩 200 N·m"——实际上应该是 120-140 N·m，照着打会导致螺栓断裂）。

**定义三个层次的幻觉：**

**L1：事实错误——最严重。** 编造了不存在的参数、步骤、安全要求。检测方式：自动化事实比对——答案中的数值（力矩、压力、温度、间隙、电压）与 RAG 检索到的源文档中的数值比对，±5% 容差，不一致 → 标记。自动化做不到 100% 覆盖（有些隐式事实需要理解上下文），但能覆盖参数类错误这一最高风险类别。

**L2：遗漏——中等严重。** 排故步骤少了关键一步、安全提醒被省略了。检测方式：LLM 比对——把答案和检索到的源文档都喂给 Judge LLM，让它标记"源文档中有的关键操作步骤，答案中遗漏了哪些"。漏了安全关键步骤 → 严重；漏了可选的检查步骤 → 轻微。

**L3：过度自信——轻微但累积风险。** 模型用"一定"、"绝对"、"保证"等词描述不确定的结论。检测方式：关键词扫描 + LLM 判断。过度自信本身不会直接导致事故，但它会降低机务人员的警觉性——如果连续 10 次都"过度自信且正确"，第 11 次错误时用户不会质疑。

**检测流程**：

```
RAG 生成答案
    │
    ▼
L1 自动事实比对（规则：数值 ±5% 容差，编号格式校验）
    ├─ 命中幻觉 → 标记不通过，不进入下一层
    └─ 通过 → 
        ▼
L2 LLM 比对（Judge 比对答案 vs 源文档，标记遗漏）
    ├─ 遗漏安全关键步骤 → 标记不通过
    └─ 通过 →
        ▼
L3 过度自信检测（关键词 + LLM 判断）
    ├─ 存在 → 降低可信度评分
    └─ 通过 → 答案可信
```

### 六、系统设计与综合（Q19–Q20）

**Q19：如果机务工程师现场排故时网络不好，甚至完全离线，RAG 系统怎么设计？**

这是机务场景非常现实的问题——机库、停机坪的网络环境不稳定。

**方案：端侧推理 + 本地化 RAG，云端同步。**

**端侧**：模型用量化后的 4-bit 或 8-bit GGUF 格式，部署在机务人员的平板或笔记本上。Qwen-7B 量化后大约 4GB，普通平板可运行。向量库用 LanceDB（嵌入式、无服务端依赖，文件级部署）。知识库做精简版——只保留当前机型的高频查询内容（Top 80% query 覆盖的手册章节 + 全部安全规范），压缩到 2-3GB。

**云端**：全量知识库 + 全量模型。在线时走云端检索（知识全、模型强），离线时自动切到本地（知识精简但核心安全内容不缺失）。

**同步策略**：在线时自动下载最新索引差量（新手册版本、新工单案例、安全通告更新）。不是每次全量下载，只同步 `version > local_version` 的增量。同步在 Wi-Fi 环境下后台静默完成，不占用机务人员工作时间。

**离线状态的设计原则**：宁可说"我不确定，建议联网后查询"，也不能在知识不完整的情况下给出可能错误的答案。离线模式下，模型回答中涉及参数的部分强制加入置信度标注（`[低置信度-离线模式，建议联网确认]`）。安全相关的硬约束在本地优先存储，不随精简版裁剪。

**Q20：从 0 搭建这个机务维修 RAG + 微调系统，你会怎么排期和组织？最关键的风险点是什么？**

**分 6 个阶段，每个阶段有明确的交付物和验证标准。**

**Phase 1：数据摸底 + 最小可行（2 周）**
- 收集 3-5 本核心维修手册（选使用频率最高的）+ 100 条历史工单
- 搭建最简数据解析 Pipeline（只处理电子 PDF + Word）
- 用最简单的策略搭建 RAG（固定 1000 字切分 + 纯向量检索 + Qwen-7B 底模不微调）
- 交付物：能回答 10 道机务基准问题的 Demo
- 验证标准：10 道题中至少 6 道答案被机务专家判为"基本可用"

**Phase 2：数据工程（3 周）**
- 完成全量文档解析（含扫描件 OCR + 表格提取）
- 构建术语词典 + 缩写展开 + Query 改写
- 实施语义边界切分 + 表格结构化
- 交付物：完整知识库索引 + 数据质量报告

**Phase 3：检索优化（2 周）**
- 实施混合检索（BM25 + Dense + 术语增强）
- RRF 融合 + 动态权重 + Re-Rank
- 构建检索评测集 + 自动化检索评测
- 交付物：检索 Recall@5 ≥ 85%

**Phase 4：微调训练（3 周）**
- 构建微调数据集（目标 2000+ 条高质量样本）
- LoRA 微调 Qwen-7B（机务术语 + 安全规范 + 回答格式）
- 微调效果评测（对比微调前后在 50 道机务 query 上的表现）
- 交付物：微调模型 + 微调效果报告

**Phase 5：RAG 评测 + 安全加固（2 周）**
- 实施三层幻觉检测 + 安全合规自动化检查
- 构建 RAG 评测集 + 端到端评测
- 根据评测结果迭代检索策略和微调数据
- 交付物：RAG 评测报告 + 安全合规评分

**Phase 6：部署上线 + 持续迭代（2 周）**
- 端侧量化部署 + 离线方案
- 增量索引更新机制
- 用户反馈收集 → 评测集更新 → 数据飞轮
- 交付物：上线版本 + 运维文档

**三个最大风险点：**

1. **扫描件 OCR 质量不可控**：泛黄的旧手册、手写批注、模糊复印件——OCR 准确率可能只有 60-70%。缓解：投入充足时间做 OCR 后处理（拼写纠错 + 术语词典辅助校正）+ 对低质量扫描件做人工转录（量不大但价值高）。

2. **机务专家标注资源不足**：评测集和质量验证都依赖机务专家，但他们的时间是最稀缺的资源。缓解：用 LLM 预标注 + 人工确认（而非从零标注），把人工时间花在"判断对错"而不是"写答案"。评价集每道 query 请 2 位专家独立标注取交集，减少个体偏见。

3. **安全场景的"未知未知"**：模型可能在某些罕见故障场景下给出看似正确实则危险的回答，而评测集没覆盖到。缓解：Phase 5 的安全加固中，请专家专门构造 20-30 道"危险场景"（错误操作可能导致的连锁故障），测试模型的拒绝能力和安全建议是否正确。**安全评测集要包含"你不该回答的"和"你该怎么回答的"两类 case。**

## 附录七：意图识别专题 — 设计原理与工业界方案对比

**Q：Price Agent 的意图识别是如何设计的？工业界还有哪些其他做法？各自适用什么场景？**

这道题我从三个层面回答：Price Agent 的当前方案、设计中的关键决策和踩坑经验、以及工业界 6 种方案的系统对比。

---

### 一、Price Agent 当前方案：关键词规则引擎 + 三层决策树

代码集中在 `agent/react_engine.py` 的 `_detect_intent()` 方法，约 60 行。

**核心架构：三层条件判断的优先级决策树。**

```
用户 Query
    │
    ▼
Layer 1: 推荐意图检测
  触发条件：场景词（gaming/photography/battery 等 25 个）
           OR 推荐词（"推荐""适合""哪款好"）
           OR 预算词（"以内""不超过""预算"）
           OR 处理器词（"骁龙""天玑""A17" 等 13 个）
  排除条件：含查价词（"多少钱""最便宜"）→ 不是推荐
           "推荐" + 单型号 + 无场景/预算限定 → 不是推荐，是查价
          推荐触发 + 含对比词/多商品 → 升级为 comparison（混合意图）
  命中 → "recommendation"

Layer 2: 查价意图检测（在推荐未命中的前提下）
  触发条件：含 1 个已知商品型号（从 product_hints 加载，如 iPhone 15、小米14）
  命中 → "query"

Layer 3: 对比意图检测
  触发条件：多商品型号（≥2）OR 含对比词（"对比""哪个更""怎么选"）
  命中 → "comparison"

Layer 4: 购物意图检测（最低优先级）
  触发条件：购物词（"买""想买""挑""选"）+ 无型号 + 无场景词 + 无预算词
  命中 → "shopping"

全部未命中 → "query"（兜底）
```

**关键设计：三层判断之间有优先级和互斥逻辑。**

推荐检测在最前面——因为推荐型 query 的信号最强（场景词、预算词、处理器词都是明确的意图信号），应该优先匹配。如果推荐检测通过且同时符合 comparison 条件（比如"推荐游戏手机，然后和 iPhone 15 对比"），不是选推荐也不是选对比——而是升级为 comparison（混合意图走 Plan-Execute 更合适）。

购物检测在最后面——因为购物意图的信号最弱（"想买个手机"跟"查 iPhone 15 价格"只差一个型号词）。如果购物检测放前面，很可能把"想买个 iPhone 15"也判成 shopping——但它显然是个明确的查价 query。所以购物检测要求"无型号 + 无场景 + 无预算"三个条件同时满足。

---

### 二、设计中的关键决策和踩坑经验

**决策 1：为什么用规则而不是 LLM？**

三个理由。**确定性**："想买个手机"必须每次都路由到 shopping，95% 概率走 shopping、5% 走 recommendation 是不可接受的——意图分类的错误不是"回答不够好"，是走了完全错误的交互模式。**零成本零延迟**：关键词匹配 0 token、0 毫秒。每次对话省一次 LLM 分类调用，日均 1000 次对话就省了 1000 次 API 调用。**可维护**：关键词表是透明的——加一个场景词、改一行代码，效果立即可验证。LLM 分类改一句 prompt，行为可能变也可能不变。

**决策 2：购物模式激活后的路由保护（这是一个从 bug 中长出来的设计）。**

问题：购物模式激活后，用户对"主要什么用途"回答"打游戏"——`_detect_intent()` 把"打游戏"判为 recommendation（因为"游戏"是场景触发词），路由到 ReAct 模式，购物上下文丢失。

修复：在 `run()` 入口加了判断——如果 `shopping_context.phase != "greeting"`（购物已激活），跳过意图分类，直接进 `_guided_shopping()`。**一旦用户进入了一个需要上下文的交互模式，就不要因为单条消息的字面含义而切换模式。** "打游戏"在购物上下文中是槽位信息，在搜索上下文中是推荐需求——同一条消息，在不同模式下含义完全不同。

**决策 3：话题切换和结束检测的优先级。**

购物途中用户说"算了帮我查 iPhone 15 价格"——"算了"是结束词，"iPhone 15"是具体型号。如果先判结束购物 → 购物退出 → 下一条消息才走 ReAct，但用户本意是"退出购物，立刻查价"。所以 `_is_topic_switch()` 优先级高于结束检测。同时还要判断：用户提到的型号是不是当前推荐列表里的——如果是，说明在对比推荐商品，不是要退出。

### 三、工业界 6 种意图识别方案对比

我把工业界做意图识别的方法归纳为 6 种，从最简单到最复杂。

---

**方案 1：关键词规则（Price Agent 当前方案）**

```
原理：维护关键词词典 + 优先级决策树
代表：Price Agent _detect_intent()
```

| 维度 | 评价 |
|------|------|
| 准确率 | 高频场景 95%+，长尾表达 60-70% |
| 延迟 | 0ms（纯内存计算） |
| 成本 | 0 |
| 可维护性 | 场景少时好，场景多时关键词表膨胀 |
| 覆盖范围 | 只能覆盖已知的表达方式 |

**适用场景**：意图种类少（≤ 10 种）、每类有明确的触发词、对确定性要求极高（错了代价大）。典型如：电商购物（查价/推荐/对比/购物）、客服路由（退换货/物流查询/投诉/咨询）、语音助手指令（播放音乐/导航/打电话）。

**核心局限**：长尾表达覆盖不了——"给安利个手机呗""求个好用的""有没有那种打游戏不卡的"这些口语化表达关键词不一定全覆盖。跨领域时需要重新梳理关键词库。

---

**方案 2：LLM Few-shot 分类**

```
原理：在 prompt 中放 3-5 个标注示例，让 LLM 做 in-context learning
代表：OpenAI Function Calling 的 intent 分类用法
```

```python
system_prompt = """将用户查询分类为以下意图之一：recommendation, comparison, shopping, query。

示例：
- "推荐一款游戏手机" → recommendation
- "iPhone 15 和小米14 哪个好" → comparison
- "想买个手机，帮我看看" → shopping
- "iPhone 15 多少钱" → query

仅返回意图标签，不要其他文字。"""

intent = llm.chat(system_prompt + user_query, temperature=0)
```

| 维度 | 评价 |
|------|------|
| 准确率 | 85-95%，取决于 few-shot 质量和覆盖度 |
| 延迟 | 200-500ms（一次 LLM 调用） |
| 成本 | ~0.0005 元/次 |
| 可维护性 | 好——加新意图改 prompt 就行 |
| 覆盖范围 | 覆盖面广，能处理长尾表达 |

**适用场景**：意图种类中等（10-30 种）、有长尾表达需要覆盖、对延迟不敏感（200ms 可接受）。典型如：对话式客服、内容审核分类。

**核心局限**：一致性不如规则（temperature=0 也有微弱波动）；成本虽然低但高频场景下（日均 10 万次对话）累积可观；边界 case 的判断可能不稳定。

---

**方案 3：Embedding 语义分类**

```
原理：把 query 和每种意图的"原型描述"分别做 embedding，
      取余弦相似度最高的意图
代表：基于 sentence-transformers 的轻量分类器
```

```python
intent_descriptions = {
    "recommendation": "用户想根据场景、预算或处理器推荐商品",
    "comparison": "用户想对比两个或多个商品",
    "shopping": "用户想买但不知道具体买什么，需要引导",
    "query": "用户知道具体商品，想查价格",
}

query_emb = embed(user_query)
scores = {intent: cosine_sim(query_emb, embed(desc)) for intent, desc in intent_descriptions.items()}
intent = max(scores, key=scores.get)
```

| 维度 | 评价 |
|------|------|
| 准确率 | 80-90% |
| 延迟 | 10-50ms（一次 embedding 调用） |
| 成本 | ~0.0001 元/次（embedding 很便宜） |
| 可维护性 | 一般——改意图需要更新原型描述 |
| 覆盖范围 | 较好——语义相似度能捕获同义表达 |

**适用场景**：意图种类少（≤ 10）、意图之间有明确的语义差异、需要比规则更灵活但比 LLM 更快更便宜。典型如：邮件自动分类（工单/反馈/咨询/垃圾）、文档自动标签。

**核心局限**：意图间的细微差异区分不好——"推荐游戏手机"和"游戏手机价格"语义上相近，但业务上一个是 recommendation 一个是 query。embedding 分类可能区分不了这种细微差异。对数字编号敏感的场景（ATA 章节号）效果也不好。

---

**方案 4：微调小模型做分类器**

```
原理：用标注数据微调一个轻量分类模型（BERT-base/DeBERTa-v3-base），
      专门做意图分类任务
代表：快手/字节等大厂的 NLU 中台
```

```python
# 训练数据格式
train_data = [
    {"text": "推荐一款游戏手机", "label": "recommendation"},
    {"text": "iPhone 15 和小米14 哪个好", "label": "comparison"},
    # ... 2000+ 条标注数据
]

# 微调 BERT
model = BertForSequenceClassification(num_labels=4)
trainer.train(model, train_data)
```

| 维度 | 评价 |
|------|------|
| 准确率 | 90-97%（标注数据足够时） |
| 延迟 | 5-20ms（小模型本地推理） |
| 成本 | 训练一次 ~50-200 元，推理几乎免费 |
| 可维护性 | 差——新增意图需要重新标注 + 重新训练 |
| 覆盖范围 | 取决于训练数据——数据覆盖到的场景准确率高，没覆盖到的可能瞎猜 |

**适用场景**：意图种类稳定不常变、有充足标注数据（≥ 2000 条）、对延迟要求高（< 50ms）、高频调用（日均百万级）。典型如：搜索引擎 Query 理解（电商搜索、短视频搜索）。

**核心局限**：冷启动成本高（需要标注数据）；意图变更需要重新训练；模型对训练数据分布外的表达方式可能给出高置信度的错误分类（模型不会说"我不确定"）。

---

**方案 5：两阶段级联（规则粗筛 + LLM 兜底）**

```
原理：第一阶段规则做快速分类（高置信度直接输出），
      第二阶段 LLM 处理规则无法判断的长尾 case
代表：Price Agent 的下一步优化方向
```

```
用户 Query
    │
    ▼
规则引擎（覆盖率 90-95%）→ 高置信度？
    ├─ 是 → 直接输出意图
    └─ 否 → LLM Few-shot 分类 → 输出意图
                   │
                   ▼
            记录 LLM 分类结果 → 定期 Review
                   │
                   ▼
            高频长尾 case → 沉淀为规则 → 规则引擎覆盖 ↑
```

| 维度 | 评价 |
|------|------|
| 准确率 | 高频场景 95%+（规则），长尾 85-90%（LLM） |
| 延迟 | 90% case 0ms，10% case 200-500ms |
| 成本 | 极低（只有 5-10% 的 query 调 LLM） |
| 可维护性 | 最好——规则覆盖高频，LLM 兜底低频，两者互补 |
| 覆盖范围 | 完整性最好——规则覆盖已知，LLM 覆盖未知 |

**适用场景**：绝大多数生产环境的最优解——高频场景确定、长尾场景存在、对延迟和成本都敏感。典型如：电商搜索（淘宝/京东的 Query 意图分类）、客服路由（80% 规则 + 20% LLM/NLU）。

**核心要点**：规则和 LLM 之间不是静态分工，而是**动态演化**——定期 Review LLM 兜底的 case → 分析高频长尾表达 → 把这些表达的关键词补回规则层。规则层越来越精准，LLM 调用量逐步收敛。**这本身就是一个数据飞轮——用 LLM 发现规则盲区，用规则降低 LLM 调用量。**

---

**方案 6：多 Agent 意图协商**

```
原理：多个轻量 Agent 各自从不同维度判断意图（关键词 Agent、
      语义 Agent、上下文 Agent），投票或协商出最终意图
代表：研究前沿，工业界落地较少
```

| 维度 | 评价 |
|------|------|
| 准确率 | 理论上最高，但工程复杂度高 |
| 延迟 | 高（多个 Agent 并行或串行判断） |
| 成本 | 高（多次 LLM 调用或模型推理） |
| 可维护性 | 差——多个 Agent 的交互逻辑复杂 |
| 覆盖范围 | 理论上最全面 |

**适用场景**：对准确率要求极高（医疗、金融合规）、意图极其复杂（多意图混合、隐含意图）、容错成本极高。目前工业界大规模落地较少，更多在研究阶段。

---

### 四、6 种方案的决策矩阵

| 方案 | 准确率 | 延迟 | 成本 | 可维护 | 适用规模 | 典型场景 |
|------|:-----:|:----:|:----:|:-----:|:-------:|---------|
| 1. 关键词规则 | 95%/60% | ★★★★★ | ★★★★★ | ★★★ | 小-中 | 意图少、信号强 |
| 2. LLM Few-shot | 90% | ★★★ | ★★★★ | ★★★★★ | 小-中 | 长尾多、改动频 |
| 3. Embedding 分类 | 85% | ★★★★ | ★★★★★ | ★★★ | 中-大 | 语义差异明显 |
| 4. 微调小模型 | 94% | ★★★★★ | ★★★★ | ★★ | 大-超大 | 高频、意图稳定 |
| 5. 两阶段级联 | 95%/88% | ★★★★ | ★★★★★ | ★★★★★ | 任意 | **最通用** |
| 6. 多 Agent 协商 | 96%+ | ★★ | ★★ | ★ | 小 | 极高准确率要求 |

> 注：方案 1 和 5 的准确率标注了"高频/长尾"，因为规则的准确率在这两类场景差异很大。

---

### 五、Price Agent 的演进路线

当前处于方案 1（纯规则），下一阶段目标是方案 5（两阶段级联）。

```
当前 (v1.0)              下阶段 (v2.0)              远期 (v3.0)
纯规则                    规则 + LLM 兜底             规则 + 微调小模型
──────                    ──────────────             ────────────────
60 行 python              规则覆盖率 90%              规则 + 小模型级联
4 种意图                  新增长尾意图                日均百万级可支撑
0 token, 0ms              日均 LLM 调用 < 10%         延迟 < 20ms
                          数据飞轮：LLM→规则回流      跨品类自动扩展
```

**什么时候从方案 1 升级到方案 5？** 三个信号任意一个出现：每周花 > 2 小时维护关键词表、长尾 case 占比 > 10%、需要跨品类扩展（手机 → 笔记本 → 家电）。当前阶段这三个信号都没出现，所以方案 1 继续工作得很好。

**什么时候从方案 5 升级到方案 3（微调小模型）？** 日均 query 量 > 10 万、LLM 兜底的 10% 仍然成本过高、意图种类稳定（至少 3 个月没有新增）。用小模型替代 LLM 兜底——准确率不降、延迟从 200ms 降到 10ms、成本降到近乎零。

---

**一句话总结**：意图识别的方案选择本质上是一个**准确率 × 延迟 × 成本 × 可维护性的四维 trade-off**。没有"最好"的方案，只有"最适合当前阶段"的方案。Price Agent 当前选了最轻量的规则方案——因为这个阶段意图种类少、信号强、改动频繁，规则的性价比最高。但架构上预留了升级空间——`_detect_intent()` 的接口是 `str → str`，内部实现换成 LLM 或小模型不需要改任何调用方代码。

## 附录八：Claude Code Agent 设计专题 — 架构模式、复杂任务处理、MCP/Skills/Tools 解析

> 本专题从设计思路和架构分析的角度，剖析 Claude Code 作为 CLI Agent 的设计理念、核心组件和任务执行模式。

---

### Q1：Claude Code 的 Agent 架构设计模式是什么？

Claude Code 的核心设计模式可以概括为：**ReAct 循环 + 子 Agent 委派 + 上下文压缩 + 权限沙箱**，四层协同。

---

**一、核心循环：增强版 ReAct**

最外层的执行模型是标准的 Think → Act → Observe 循环，但做了几项关键增强：

```
用户输入
    │
    ▼
┌─────────────────────────────────────────┐
│              Claude Code 主循环           │
│                                          │
│  1. Think（思考）                         │
│     - 分析用户意图                        │
│     - 如果是复杂任务，判断是否需要 Plan     │
│     - 决定下一步调用什么工具               │
│                                          │
│  2. Act（执行）                           │
│     - 调用工具（Bash/Read/Write/Edit...） │
│     - 或启动子 Agent（并行独立任务）       │
│     - 或进入 Plan Mode（先规划再实施）     │
│                                          │
│  3. Observe（观察）                       │
│     - 读取工具返回结果                     │
│     - 判断是否需要调整策略                 │
│     - 决定是继续循环还是给出最终答案        │
│                                          │
│  增强点：                                 │
│  - thinking 模式：在输出前先做深度推理     │
│  - 子 Agent 委派：独立任务并行执行         │
│  - 上下文压缩：长对话自动总结保持窗口不爆   │
│  - 权限检查：每次工具调用前过权限沙箱       │
└─────────────────────────────────────────┘
```

与 Price Agent 的 ReAct 对比：

| 维度 | Price Agent ReAct | Claude Code ReAct |
|------|-------------------|-------------------|
| 工具集 | 固定的 6 个业务工具 | 动态工具集（Bash/Read/Write/Edit/Glob/Grep/WebSearch 等） |
| 循环控制 | 代码编排（`_react_loop` 固定轮数上限） | LLM 自主决定何时结束 |
| 推理深度 | 标准 Thought | 两层推理（thinking 模式 + 标准 Thought） |
| 并行能力 | Plan-Execute 模式支持 Step 级并行 | 子 Agent 委派，独立任务完全并行 |
| 上下文管理 | 滑动窗口（6 轮 + 6000 字符） | 上下文压缩（compaction）+ 摘要 |

---

**二、子 Agent 委派模式**

这不是简单的"多 Agent 协作"，而是一种**层级委派**模式。当任务可以被拆成多个独立子任务时，主 Claude 不亲自执行每一项，而是 spawn 一个专门的子 Agent 去处理：

```
主 Claude
    │
    ├── 子 Agent 1: claude-code-guide  ── 专门回答使用问题
    │    (独立上下文，独立工作区)
    │
    ├── 子 Agent 2: Explore ── 只读搜索，广撒网找代码
    │    (isolation: worktree，git 隔离)
    │
    ├── 子 Agent 3: Plan ── 架构设计，不改代码
    │    (只做分析和规划)
    │
    └── 子 Agent 4: general-purpose ── 通用任务执行
         (可并行运行多个)
```

关键设计点：
- **上下文隔离**：子 Agent 有自己的独立上下文，不污染主 Claude 的对话窗口
- **工作区隔离**：可以用 `isolation: "worktree"` 创建独立的 git worktree，子 Agent 在里面随意修改不影响主工作区
- **能力收缩**：子 Agent 的工具集是主 Claude 的子集，遵循最小权限原则
- **结果汇报**：子 Agent 完成后只返回结论给主 Claude，不返回完整的思考过程

这与 Price Agent 的 Plan-Execute 不同。Price Agent 的 Step 是**同一上下文内的并行工具调用**，Claude Code 的子 Agent 是**完全独立的 Agent 实例**，隔离程度更高。

---

**三、上下文管理：Compaction 机制**

这是 Claude Code 最巧妙的设计之一。当对话太长时，不做简单的截断，而是做**智能摘要压缩**：

```
对话轮次:  Round 1 → Round 2 → Round 3 → ... → Round N
                │                          │
                ▼                          ▼
         正常保留在上下文          compaction 触发（超过 token 预算）
                                          │
                                          ▼
                                  前面 N-5 轮被 LLM 总结为结构化摘要
                                  摘要 + 最近 5 轮完整对话 → 继续
```

摘要保留了"做了什么、关键决策是什么、当前状态是什么"，但丢弃了"具体怎么做的、中间的错误和重试、冗余的工具调用细节"。

与 Price Agent 的滑动窗口对比：Price Agent 是**硬截断**（保留最近 6 轮，丢掉更早的），Claude Code 是**软压缩**（保留语义理解但压缩 token）。软压缩保留了更多上下文信息但实现复杂度高得多——压缩质量取决于 LLM 是否理解了"什么是值得保留的关键信息"。

---

**四、权限沙箱**

Claude Code 的每个工具调用都经过权限检查。不是简单的"允许/拒绝"二元判断，而是分层的：

- **全自动**（始终允许的）：Read、Glob、Grep 等只读操作
- **需确认**（每次弹窗）：Bash 中可能修改系统的命令
- **需授权**（首次需用户一次性批准）：特定模式的 Bash（如 `git push`）
- **禁止**：明确定义的危险操作

权限是可以按项目粒度配置的（`.claude/settings.json`），支持精确到命令参数的 allowlist。这与 Price Agent 的设计思路一致——Price Agent 的 Shopping 模式也有隐式的安全边界（不做支付、不操作库存、不做实际交易）。

---

### Q2：Claude Code 如何处理复杂 Query，一步步操作执行的？

以一个真实场景为例——用户说"在 price-agent 里新建一个 LLM-as-Judge 的文档，记录设计实现和改进方向"。

**Claude Code 的完整执行链路：**

**Phase 0：理解 + 规划（隐性）**

```
Think（thinking 模式，深度推理）：
  "用户要在 price-agent 项目里新建文档。
   首先需要理解：
   1. 当前项目结构是什么样的？LLM-as-Judge 代码在哪里？
   2. 现有文档的格式风格是什么样的？我需要遵循。
   3. 需要收集哪些信息来写这个文档？

   计划：
   1. 读 README 了解项目结构
   2. 读 scripts/training_data.py 了解 LLM-as-Judge 实现
   3. 读 docs/modules/ 中已有文档了解格式规范
   4. 读 app.py 了解 judge API 端点
   5. 读 eval README 和 test README 了解测试规范
   6. 综合信息，写文档"
```

**Phase 1：信息收集（并行读取多个文件）**

```
Action 1: Read(README.md)          ┐
Action 2: Read(training_data.py)   ├── 并行执行（4 个 Read 调用）
Action 3: Read(app.py L888-905)    │   各工具独立，互不依赖
Action 4: Bash(ls docs/modules/)   ┘

Observe:
  - 项目定位是"电商 AI 搜索助手，ReAct+Plan-Execute 混合策略"
  - LLM-as-Judge 在 training_data.py L570-727，双层评估体系
  - app.py L888-905 是 POST /api/training/judge 端点
  - docs/modules/ 已有 00-05 号文档，按编号前缀命名
```

**Phase 2：深入理解（串行读取关键实现）**

```
Action 5: Read(training_data.py L232-412)  → compute_quality() 的 4 维度评分
Action 6: Read(training_data.py L570-617)  → JUDGE_SYSTEM_PROMPT 的完整内容
Action 7: Read(training_data.py L620-727)  → build_judge_user_prompt + judge_sample
Action 8: Read(docs/modules/05-xxx.md)     → 参考文档格式

Observe:
  - 4 维度：A 能力展现(0-10) B 执行质量(0-10) C 回答可信度(0-10) D 数据完整度(0-10)，总分=四维之和×2.5
  - LLM Judge 用 DeepSeek，temperature=0.1，JSON mode
  - 现有文档格式：状态标记、修订记录、模块定位、方案设计、代码位置表
```

**Phase 3：执行（写入文件）**

```
Action 9: Write(docs/modules/06-LLM-as-Judge质量评估.md, content)

Observe: 文件写入成功
```

**Phase 4：验证**

```
Think: "文件已创建。我可以验证一下文件是否正确写入"
Action 10: Bash(ls docs/modules/)  → 确认 06 号文件存在
```

**整个过程的关键特征**：

1. **信息收集阶段最大限度并行**——4 个 Read 调用同时发出，不是串行等
2. **依赖关系决定串行还是并行**——必须先读代码理解实现，才能写文档（Write 依赖 Read 的结果）
3. **没有显式的 Plan → Execute 分阶段**——计划和执行是交织的，但整体逻辑和 Price Agent 的 Plan-Execute 本质相同（先摸清全貌再动手）
4. **每一步有明确的"为什么"**——Think 解释了当前决策的理由

**对比 Price Agent 的 Plan-Execute**：

| 维度 | Price Agent Plan-Execute | Claude Code 复杂任务 |
|------|--------------------------|---------------------|
| Phase 1 | 显式生成 JSON Plan | 隐式（thinking 中规划，不输出结构化计划） |
| Phase 2 | 按 DAG 执行（并行组 + 串行组） | 自由判断——无依赖并行，有依赖串行 |
| Phase 3 | 专用模型 Synthesize | 最终自然语言回答（不换模型） |
| 可见性 | DAG 图前端可视化 | thinking 过程在界面中展示 |
| 用户干预 | 无 | Plan Mode 让用户审核方案 |

### Q3：MCP、Skills、Tools 分别是什么？它们之间的关系是什么？

这是三个不同层级的概念，从下到上构成 Claude Code 的**能力栈**。

---

**Layer 1：Tools（工具）——最底层，原子操作**

Tools 是 Claude Code 能够调用的**单个函数**。每个 Tool 有明确的输入（参数 Schema）和输出。Claude Code 内置了约 20 个 Tools：

| 类别 | 工具 | 作用 |
|------|------|------|
| 文件读 | Read | 读取文件内容和目录信息 |
| 文件写 | Write, Edit | 创建新文件、精确字符串替换 |
| 搜索 | Glob, Grep | 文件名匹配、内容正则搜索 |
| 执行 | Bash | 执行 Shell 命令 |
| 网络 | WebSearch, WebFetch | 搜索网页、抓取页面内容 |
| Git | （通过 Bash 调用 git CLI） | 版本控制 |
| Agent | Agent | 启动子 Agent |
| 通知 | PushNotification, CronCreate, Monitor | 推送通知、定时任务、事件监控 |

Tool 是**无状态的**——每次调用独立，不记忆上次调用的结果。Tool 不知道"为什么被调用"——这个信息在 Claude 的 Thought 里。

与 Price Agent 的 Tool 对比：Price Agent 的 Tool 是**业务语义层**（"查全平台价格""语义搜索推荐""RAG 知识检索"），Claude Code 的 Tool 是**系统原语层**（"读文件""执行命令""搜索内容"）。Price Agent 的一个业务 Tool 内部可能调用了 Claude Code 的多个系统 Tool。

---

**Layer 2：Skills（技能）——中间层，可复用的 Prompt 模板**

Skills 是封装了**领域知识 + 操作流程 + 行为规则**的 Prompt 模块。每个 Skill 是一个 `.md` 文件（YAML frontmatter + markdown body），定义了：
- 什么场景下激活这个 Skill
- 激活后应该遵循什么流程
- 有什么需要注意的边界条件

Claude Code 的 Skills 系统与 Price Agent 的 Skills 系统在**架构设计上是同源的**——都是 Prompt 按需组合的思想：

| 维度 | Price Agent Skills | Claude Code Skills |
|------|-------------------|---------------------|
| 定义文件 | `agent/skills/*.md`（5 个） | 内置 + MCP 注册 |
| 加载方式 | LLM 通过 `load_skill` 元工具自主选择 | 用户 `/skill-name` 调用 或 触发词自动匹配 |
| 内容 | 工具使用指南 + few-shot 示例 + 行为规则 | 工作流模板 + 领域知识 + 最佳实践 |
| 示例 | `price_comparison`, `shopping_guide` | `code-review`, `simplify`, `init`, `verify` |
| 作用 | 注入业务场景的专业知识 | 注入特定任务的操作方法论 |

**Skill 和 Tool 的关系**：Skill 告诉 Claude **"怎么做"**，Tool 让 Claude **"能做"**。Skill 不增加新的原子能力——它只是告诉 Claude 在什么场景下、用什么顺序、怎么组合使用已有的 Tools。

---

**Layer 3：MCP（Model Context Protocol）——顶层，标准化的外部能力接入协议**

MCP 是 Anthropic 于 2024 年底发布的开放协议。它的核心思想是：**给 LLM 提供一个标准化的"USB-C 接口"，用来连接外部的数据源和工具。**

MCP 解决的核心问题是：如果每个外部系统都用自己的 API 格式（REST/gRPC/WebSocket），LLM 需要为每种格式写适配器——M×N 种对接方式。MCP 定义了一套统一的标准，所有外部系统只需要实现一次 MCP Server → 所有支持 MCP 的 LLM 都能直接使用。

**MCP Server 暴露三种能力**：

```
┌──────────────────────────────────────────┐
│              MCP Server                   │
│                                           │
│  Resources（资源）——"有什么数据可以读"     │
│    - 文件内容、数据库记录、API 返回数据    │
│    - 类似于 REST 的 GET                    │
│    - 示例：文件系统、Postgres 数据库、     │
│            Slack 频道历史                  │
│                                           │
│  Tools（工具）——"可以执行什么操作"         │
│    - 有副作用的操作（写、发、改）           │
│    - 类似于 REST 的 POST/PUT/DELETE        │
│    - 示例：创建文件、发送消息、更新数据库    │
│                                           │
│  Prompts（提示模板）——"预定义的工作流"     │
│    - 可复用的 prompt 模板 + 参数           │
│    - 类似于 Skills 但由外部服务提供         │
│    - 示例：代码审查模板、数据清洗模板       │
└──────────────────────────────────────────┘
```

**MCP 与 Tools 和 Skills 的关系**：

```
┌─────────────────────────────────────────────────────┐
│                    Claude Code                       │
│                                                     │
│  Skills（内置 Prompt 模板）                          │
│  ┌─────────────────────────────────────────────┐   │
│  │  code-review, simplify, init, verify, ...    │   │
│  └─────────────────────────────────────────────┘   │
│                       │                             │
│                       ▼                             │
│  Tools（内置原子操作）                               │
│  ┌─────────────────────────────────────────────┐   │
│  │  Read, Write, Bash, Grep, WebSearch, ...     │   │
│  └─────────────────────────────────────────────┘   │
│                       │                             │
│                       ▼                             │
│  MCP（标准化外部接入）                               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐           │
│  │ MCP Svr 1│ │ MCP Svr 2│ │ MCP Svr 3│ ...       │
│  │ (文件系统)│ │ (数据库)  │ │ (Slack)  │           │
│  └──────────┘ └──────────┘ └──────────┘           │
└─────────────────────────────────────────────────────┘
```

**三者的递进关系**：

| 层级 | 是什么 | 谁定义 | 谁调用 | 扩展示例 |
|------|--------|--------|--------|---------|
| Tool | 原子操作 | Claude Code 内置 | LLM 直接调用 | Read, Write, Bash, Grep |
| Skill | 操作流程模板 | 项目级 `.md` 文件 | 用户 `/` 或 LLM 自主加载 | code-review, verify |
| MCP | 外部能力的标准化接口 | 第三方 MCP Server | LLM 通过 Tools 协议调用 | Postgres MCP, GitHub MCP |

### Q4：Claude Code 的设计对 Price Agent 有什么启发？

**启发 1：子 Agent 委派模式值得借鉴。**

Price Agent 当前是单 Agent，所有任务都在一个 ReActAgent 内完成。如果参考 Claude Code 的子 Agent 设计：

```
用户 "对比 iPhone 15 和小米 14，同时看看有没有推荐的游戏手机"
                │
                ▼
         Price Agent 主控
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
   子Agent1  子Agent2  子Agent3
   查iPhone  查小米14  语义推荐
   价格      价格      游戏手机
        │       │       │
        └───────┼───────┘
                ▼
         主控综合对比 + 推荐
```

但当前不支持，因为 Price Agent 的 Tool 是共享的业务语义层，每个子 Agent 需要独立的上下文和工具执行环境——引入子 Agent 需要重构工具执行层。

**启发 2：上下文压缩优于硬截断。**

Price Agent 的滑动窗口是硬截断（6 轮 + 6000 字符，超了就丢）。Claude Code 的 Compaction 更智能——保留"关键决策"丢弃"执行细节"。对于 Price Agent 的多轮购物场景（可能 10+ 轮），Comaction 能让早期槽位信息不丢失。

实现思路：定期（每 3 轮）用 LLM 把历史对话总结为结构化摘要（`{slots_filled: {...}, key_decisions: [...], current_phase: "xxx"}`），摘要替代原始对话注入上下文。

**启发 3：Plan Mode 的用户审批机制。**

Claude Code 的 Plan Mode 是在**动手前征求用户确认方案**。Price Agent 的 Plan-Execute 生成的计划直接执行了，用户看不到。可以加一个可选的前端交互：DAG 图展示计划 → 用户可编辑（删步骤、加步骤、调顺序） → 确认后执行。

**启发 4：MCP 协议可用于 Price Agent 的平台层。**

Price Agent 当前多平台查询是通过 `PlatformParallelAgent` 硬编码 4 个平台的。如果每个电商平台实现为 MCP Server——暴露 Resources（商品列表/价格/库存）和 Tools（搜索商品/比价/下单）——新增平台不需要改 Price Agent 代码，只需注册一个新的 MCP Server。
