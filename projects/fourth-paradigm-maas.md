## 一、项目概览

### 业务背景

航空工业客户需要行业大模型能力，但存在三大核心痛点：

```text
① 涉密合规要求高：航空数据不能出域，必须私有化部署
② 行业微调门槛高：客户无算法团队，无法自己微调领域模型
③ 多源文档分散：维修手册、技术参数、安全规范等格式多样、分散存储
```

### 产品定位

面向航空机务领域的企业级私有化 MaaS 平台——客户在私有化环境中完成领域模型的微调、知识库构建与场景化问答。

### 你的角色

负责核心模块的产品设计与落地推进：LoRA 微调产品化、多源文档 RAG、意图识别分流架构、RAG 评测体系。

### 项目成果

```text
├── LoRA 微调与 RAG 问答助手核心模块可行性验证并推动上线
├── 意图识别分流架构覆盖 5 类机务专用场景（故障排查/维修方案/
│   手册检索/参数查询/安全规范）
└── 显著提升维修文档查询效率，赋能航空机务业务数字化转型
```

### 工作 1：LoRA 微调产品化设计

```text

├── 降低行业用户的微调门槛（选择模板 + 上传数据即可）
└── 设计基于机务专家标注测试集的 SFT 模型评估流程
    └── 支撑模型迭代效果验证与上线决策
```

### 工作 2：多源文档 RAG 方案设计

```text
痛点：维修手册 / 技术参数 / 安全规范多类型文档，检索混乱
设计：
├── 分类知识库构建方案（按文档类型分库）
├── 文档处理流程（解析 → 清洗 → 入库）
└── 语义 + 关键词 + 结构化元数据 多路混合检索策略的产品化落地
```

### 工作 3：意图识别与分流架构设计

```text
痛点：用户问题混杂，单一助手无法覆盖多类场景
设计：
├── 基于意图识别的多智能体路由架构

│   ├── 故障排查 / 维修方案 / 手册检索 / 参数查询 / 安全规范
```

```text
设计：「自动化测试集 + 机务专家校验」双模评估方案
├── 自动化测试集：覆盖召回准确性、答案相关性等核心指标
├── 机务专家校验：领域正确性的人工把关
├── 输出评测报告 → 支撑产品迭代决策
└── 推动问答质量持续优化
```

## 三、Technical Anatomy

### 主题 1：私有化 MaaS —— 合规约束如何塑造产品架构

```text
涉密合规 → 一切能力必须私有化部署
├── 模型部署形态：本地 GPU 集群，数据不出域
├── 微调能力：私有化环境内的 LoRA 微调（而非调用外部 API）
├── RAG 知识库：本地向量库 + 文档管理
└── 产品架构影响：
    ├── 无外部 API 依赖（网络隔离）
    ├── 全流程本地化（数据 → 训练 → 推理 → 评测闭环）
    └── 交付形态 = 整体解决方案而非 API 服务

面试洞察："私有化"不是部署细节，而是产品架构的第一约束——
所有设计决策（微调模板化、本地 RAG、评测闭环）都由它推导
```

### 主题 2：微调产品化 —— 把训练能力封装成模板

```text
本质：将"算法工程师的微调流程"产品化为"业务用户的操作步骤"

产品化拆解：
├── 场景模板：预置机务场景的指令模板（故障排查/维修方案）
│   └── 用户不用理解 prompt，选场景即可
├── 数据流程：用户上传文档 → 自动转 QA 对 → 校验 → 微调
└── 评估闭环：专家标注测试集 → 自动评估 → 上线决策

为什么能产品化：
├── LoRA 使微调成本从"全量训练"降到"小资源可做"
├── 机务场景的问答模式相对固定（模板可复用）
└── 与字节经历的连接：模板化 = 数据格式标准化，同一思想

面试价值：这是"把技术能力变成产品能力"的典型案例，
能讲清楚"为什么 LoRA 是产品化的前提"
```

### 主题 3：多路混合检索 —— 为什么单一检索不够

```text
三类检索的互补性：
├── 语义检索（Embedding 向量）：理解意图，召回语义相关
│   └── 弱点：对精确术语/编号召回差
├── 关键词检索（BM25）：精确匹配专业术语、编号
│   └── 弱点：无法理解语义变形
└── 结构化元数据检索：机型、章节、文档类型过滤
    └── 弱点：依赖数据被正确结构化

混合策略 = 多路召回 + 重排：
├── 三路并行召回 → 合并 → 按相关性重排
└── 覆盖"语义模糊查询"和"精确编号查询"两类真实场景

面试价值：能解释"为什么生产级 RAG 很少用单路检索"
```

### 主题 4：多智能体路由 vs 单一 Agent

```text
单一 Agent 的问题：
├── 知识库混杂 → 检索信噪比低
├── 能力边界不清 → 行为不可预期
└── 迭代风险：改一处影响全部

多智能体路由的优点：
├── 职责隔离：每个助手只管一个场景
├── 知识库解耦：差异化 RAG，检索更精准
├── 可演进：新增场景 = 新增助手，不动已有架构
└── 代价：意图识别准确性成为系统瓶颈（分流错了全错）

面试洞察：路由架构的价值前提是"意图可分"——
机务场景的 5 类问题边界清晰，所以路由是合理设计
```

### 主题 5：双模评测 —— 自动化 + 专家校验

```text
为什么自动化不够：
├── 召回准确性、答案相关性是"可自动化度量"的
├── 但机务领域的"专业正确性"无法用规则/模型完全判定
└── 涉密领域：答案错了可能造成维修事故

双模设计：
├── 自动化层：低成本、全量、快速反馈（迭代用）
├── 专家层：高成本、抽样、权威判定（上线用）
└── 与字节 CoT 质检的 Cascading Classification 同构：
    确定性 → 概率性 → 人类，三层漏斗

面试价值：跨项目复用"人机分层评估"模式，
证明你理解"自动化评测的边界在哪"
```

### 主题 6：LoRA 原理深挖 —— 微调产品化的技术前提

```text
是什么：W' = W + A×B（原权重冻结，只训练低秩增量 A×B）

为什么出现：
├── 全量微调太贵：7B 模型全量微调 ~60GB 显存 / 数小时~数天
├── LoRA：~16GB / 数十分钟~数小时 / 存储仅 ~10MB
└── LoRA 让"每个客户一个模型"经济可行（私有化多客户场景的关键）

数学原理（低秩近似）：
├── 1000×1000 矩阵全量更新 100 万参数
├── LoRA：A(1000×8) + B(8×1000) = 1.6 万参数（1.6%）
└── 为什么 rank=8 够：微调 = 小幅调整 = 参数空间低秩移动，
    只需要少数关键方向

替代方案对比：
├── 全量微调：上限最高，但贵、慢、灾难性遗忘风险
├── Adapter：灵活，但增加推理延迟
├── Prefix Tuning：参数少，但占用 context window
└── LoRA：不增延迟、可插拔、多个 LoRA 可切换 ← 私有化多客户最优

工业界：PEFT 库/各家平台标配 LoRA
```

### 主题 7：RAG vs 微调 —— 方案选择框架

```text
LoRA 微调方案：                 RAG 方案：
甲方文档 → QA 对 → 微调        甲方文档 → 向量化入库
        → 垂类模型              → 提问时检索 → 生成

区别：
├── 微调：知识刻进参数（不可更新、不可追溯、需要足够数据）
└── RAG：知识挂在外部（随时更新、可追溯来源、数据量要求低）

选择框架：
├── 知识频繁更新 → RAG
├── 需要可追溯性（涉密/合规）→ RAG
├── 需要模型内化推理模式 → 微调
└── 数据量充足 + 知识稳定 → 微调

行业现实（ToB）：
├── "训练专属模型"的叙事比"搭检索系统"更好卖
├── 所以商业动机可能压倒技术最优
└── 面试洞察：能说出"技术选型会被商业叙事影响"
    = 产品思维的成熟度
```

### 主题 8：Evals 缺失的教训 —— 为什么评测体系不可或缺

```text
类比：
├── 有 Evals = 体检 + 复诊（知道 baseline、知道提升多少、可追踪）
└── 无 Evals = 盲人摸象（不知道模型好不好，甚至不知道有没有变好）

实际交付 vs 合格交付：
├── 模型 ✅ vs 模型 ✅
├── loss 曲线 ❌ vs ✅
├── 准确率评测 ❌ vs ✅（测试集上答对多少）
├── Badcase 分析 ❌ vs ✅（答错的原因）
├── baseline 对比 ❌ vs ✅（比直接用基座模型好多少）
└── 数据质量报告 ❌ vs ✅（QA 对正确率与覆盖度）

为什么行业会这样：
├── 预算制（今年用不完明年砍）
├── 追风口（领导要求"我们也要搞 AI"）
├── 验收标准模糊（合同无准确率指标）
└── 信息不对称（甲方不懂，你说训练好了他们就信）

面试价值（最重要的教训故事）：
├── 我亲眼见过"没有评测的交付 = 卖空气"
├── 所以我在字节主动做质量验证、建 Eval Set
└── 这让我比没经历过的人更理解评测体系的价值
```

## 六、面试官追问准备

**Q1：为什么选 LoRA 而不是全量微调？**
私有化环境 GPU 资源有限 + 客户数据量小（几千条 QA）+ 需要快速交付。LoRA 显存需求低（约 16GB vs 全量 60GB），且可插拔，适合多客户多模型的私有化交付形态。

**Q2：多路混合检索的三路权重怎么定？**
按场景调：精确编号查询（如机型、件号）关键词权重高；语义模糊查询（"发动机异响怎么排查"）语义权重高。用评测集做 A/B 验证权重组合。

**Q3：意图识别分流错了会怎样？兜底是什么？**
路由错误 = 用户问题进错助手 = 检索错误知识库 = 答案质量下降。兜底设计：置信度低于阈值时走通用检索而非硬路由；后续迭代可加"路由失败反馈回路"。

**Q4：双模评测的专家校验怎么保证效率？**
自动化全量跑（低成本快速反馈），专家抽样跑（只验收关键变更/上线前）。抽样比例按变更风险动态调整。

**Q5：私有化部署遇到最大的工程挑战是什么？**
客户环境的 GPU 资源差异 + 数据不出域的传输链路 + 模型更新机制（私有化环境如何发新版模型）。这决定了交付形态必须是"可独立运行的整体包"。

**Q6：这个项目你重新做会改什么？**
加三层：① 更系统的评测基线（微调前 vs 微调后 vs RAG 的对比）；② 路由失败的 badcase 分析闭环；③ 数据质量报告（QA 对的正确率和覆盖度）——这些我后来在字节都补上了。

**Q7：5 类场景为什么是这些？**
从客户高频问题聚类而来：故障排查（最高频）、维修方案、手册检索、参数查询、安全规范（合规刚需）。场景边界清晰是路由架构成立的前提。

**Q8：这个项目的核心指标是什么？**
问答准确率（专家评测）、检索召回准确率（自动化评测）、维修文档查询效率（业务指标，如单次查询时间下降比例）、客户采纳率。

**Q9：怎么衡量 QA 对的质量？**
两个维度：正确性（答案对不对）和可学习性（这条 QA 能不能让模型学到东西）。第二条是后来才意识到的——当时只关注了正确性。QA 对的坑：格式转换丢信息、覆盖度不足（100 个知识点只覆盖 40 个）、难度单一（都是"XX 是什么"）。

**Q10：微调和 RAG 怎么选？**
看四个因素：知识更新频率（更新频繁选 RAG）、可追溯性需求（涉密合规选 RAG）、是否需内化推理模式（选微调）、数据量是否充足。ToB 场景里商业叙事也会影响选型——"训练专属模型"比"搭检索系统"更好卖，这是行业现实。

**Q11：你觉得 ToB AI 交付最大的问题是什么？**
很多交付没有评测体系——没有 baseline、没有测试集、没有 badcase 分析，模型效果无法量化也无法迭代。我亲眼见过这种"卖空气"式的交付，这直接塑造了我后来的方向：在字节主动做质量验证和 Eval Set 建设。
