## 二、深度剖析

### 剖析 1：LoRA 微调到底在做什么？

这是你接触的第一个 AI 技术概念，值得从原理层彻底搞懂。

#### ① 它是什么？

**LoRA（Low-Rank Adaptation）** 是一种参数高效微调（PEFT）方法。它不修改原始大模型的所有参数，而是在模型旁边挂两个小矩阵，只训练这两个小矩阵。

```text
全量微调（Full Fine-tuning）：
├── 修改模型全部参数（如 LLaMA-7B 的 70 亿个参数）
├── 需要大量 GPU 显存
└── 训练慢、成本高

LoRA 微调：
├── 原模型参数冻结（不动）
├── 在每个需要微调的层旁边挂两个小矩阵 A 和 B
│   W' = W + A × B
│    ↑     ↑     ↑
│   新权重  原权重   低秩增量（只训练这个）
├── 参数量级：原模型的 0.1% ~ 1%
└── 训练快、显存需求小、可以存很多个 LoRA 切换用
```

#### ② 为什么出现？

全量微调大模型太贵了。以一个 7B 模型为例：

| 方式 | 需要显存 | 训练时间 | 存储一个领域模型 |
|------|---------|---------|----------------|
| 全量微调 | ~60GB | 数小时~数天 | ~14GB |
| LoRA | ~16GB | 数十分钟~数小时 | ~10MB |

**LoRA 让"每个客户一个模型"变得经济可行。**

#### ③ 数学原理

核心思想来自一个线性代数的事实：**很多大矩阵可以用低秩矩阵近似。**

```text
假设原权重矩阵 W 是 1000×1000（100万个参数）
全量微调要更新全部 100万个参数

LoRA 的做法：
W' = W + A × B
其中 A 是 1000×8，B 是 8×1000
A×B 也是 1000×1000，但只需要训练 1000×8 + 8×1000 = 16,000 个参数
是原来的 1.6%
```

**为什么 rank=8 就够了？**

因为微调的本质是在原模型上做"小幅调整"。这种调整在参数空间里是低秩的——模型不需要在每个方向上都改变，只需要在少数几个关键方向上调整。

#### ④ 工程实现

```python
# LoRA 的核心代码（简化伪代码）
class LoRALayer:
    def __init__(self, original_weight, rank=8, alpha=16):
        self.W = original_weight  # 冻结，不训练
        self.A = nn.Parameter(torch.randn(original_weight.shape[0], rank))
        self.B = nn.Parameter(torch.zeros(rank, original_weight.shape[1]))
        self.scale = alpha / rank  # 控制 LoRA 的影响力
    
    def forward(self, x):
        # W'x = Wx + (alpha/r) * A * B * x
        return x @ self.W.T + self.scale * (x @ self.A.T @ self.B.T)
```

#### ⑤ 为什么有效？

两点原因：
1. **预训练模型已经很强了**——它已经学会了语言、推理、知识。微调只是在上面做小幅修正。小幅修正恰好是低秩的。
2. **过参数化的模型有大量冗余**——并不是所有参数方向都在实际推理中被使用。LoRA 只调整被任务"激活"的那些方向。

#### ⑥ 为什么不用别的方法？

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **全量微调** | 训练所有参数 | 上限最高 | 贵、慢、灾难性遗忘风险 |
| **Adapter** | 在层之间插入小网络 | 灵活 | 增加推理延迟 |
| **Prefix Tuning** | 在输入前加可训练的虚拟 token | 参数更少 | 占用 context window |
| **Prompt Tuning** | 只训练 soft prompt | 最简单 | 效果上限低 |
| **LoRA** | 权重矩阵的低秩增量 | 不增加推理延迟、可插拔 | rank 选择需要经验 |

**为什么 LoRA 在你那个场景下是合理选择：**
- 甲方数据量少（文档 → QA 对，可能就几千条）
- 需要快速交付（不是追求极致效果）
- 成本敏感（ToB 项目的利润来自低成本交付）

#### ⑦ 工业界实践

LoRA 是目前最主流的 PEFT 方法，几乎所有大模型微调平台都支持：
- HuggingFace PEFT 库：内置 LoRA
- OpenAI：虽未公开使用，但 GPT 的微调 API 内部可能用了类似技术
- 国内：智谱、百川、Qwen 都支持 LoRA 微调
- 你当时用的平台应该也是基于类似的技术封装

### 剖析 2：没有 Evals 的微调，问题出在哪里？

这是你行至经历中**最有价值的教训**。

#### 用医学类比

```text
有 Evals 的微调 = 体检 + 复诊
├── 微调前：知道模型的 baseline（体检）
├── 微调后：知道模型在目标领域提升了多少（复诊）
└── 持续：知道每次改动是变好还是变坏（追踪）

没有 Evals 的微调 = 盲人摸象
├── 不知道模型 baseline 是什么
├── 不知道微调后好了多少（甚至不知道有没有变好）
├── 不知道和直接用基座模型 prompt 的效果差多少
└── 甲方问"这个模型效果怎么样？" → 你只能答"我们训练过了"
```

#### 行至的交付物 vs 应该交付的

|| 行至实际交付 | 合格的 AI 交付应该包含 |
||---|------------|----------------------|
| 模型 | ✅ | ✅ |
| 训练过程的 loss 曲线 | ❌ | ✅（至少表面上看起来训练了） |
| 准确率评测 | ❌ | ✅（在测试集上答对多少） |
| Badcase 分析 | ❌ | ✅（哪些问题答错了、为什么） |
| 与 baseline 对比 | ❌ | ✅（比直接问基座模型好在哪） |
| 数据质量报告 | ❌ | ✅（QA 对的正确率和覆盖率） |
| 部署和运维方案 | ❌ | ✅（模型怎么用、怎么更新） |

**这不全是你的问题。** 这是一个典型的 ToB AI 行业通病：甲方只要交付物，不要交付质量。但没有 Evals 的交付，本质上和"卖空气"没有区别——你无法证明自己交付的东西有用。

#### 这个教训对你的价值

现在你在字节做 AI Data，你每天都在做 Evals 建设（质检 = Eval Set 的质量保证）。行至的经历让你**亲眼见过没有 Evals 的后果**——这让你比别人更理解为什么质检规则重要。

### 剖析 3：RAG（检索增强生成）— 你接触过但没深挖的概念

#### ① 它是什么？

RAG（Retrieval-Augmented Generation）是一种架构模式：**不让模型记住所有知识，而是让模型在回答问题时先去知识库检索相关内容，再基于检索结果生成回答**。

```text
没有 RAG：
用户问题 → 模型 → 回答
             ↑
         模型自己"记住"的知识（有限、可能过时、可能编造）

有 RAG：
用户问题 → 检索系统（从文档库找相关内容）→ 找到相关文档片段
                                               ↓
                              模型（基于文档片段回答问题）→ 回答
```

#### ② 为什么出现？

LLM 有两个根本性的限制：
1. **知识截止日期**：训练完成后，模型的知识就冻结了
2. **幻觉**：模型被问到不知道的事，会编造——而且编造得很自信

RAG 解决了这两个问题：检索到的文档是最新的，模型被"锚定"在真实文档上，幻觉大幅减少。

#### ③ 在行至的场景中

RAG 本可以是一个更好的替代方案：

```text
LoRA 微调方案（行至用的）：            RAG 方案（可以做的）：
甲方文档                             甲方文档
  ↓                                    ↓
QA 对生成                              文档入库（向量化）
  ↓                                    ↓
LoRA 微调                              用户提问 → 检索相关文档 → 生成回答
  ↓
垂类模型

区别：
├── 微调：把知识"刻进"模型参数 → 不可更新、不可追溯
└── RAG：把知识"挂在外面" → 随时更新文档、可追溯来源
```

**为什么选了微调而不是 RAG？**

说实话，当年（可能）是：RAG 是一个更好的工程方案（便宜、可维护、可更新），但"微调一个模型"听起来更厉害、更好卖、更有 AI 感。"我们给你们训练了一个专属模型"比"我们搭了一个检索系统"更能让甲方买单。

## 三、深度 Q&A

**Q1: 几千条 QA 对够不够微调出一个好模型？**

A: 取决于"好"的标准。如果只是让模型学会回答特定格式的问题（比如"XX 公司的退款政策是什么？"），几千条可能够。但如果想让模型真正理解领域知识并灵活应用，远远不够。LoRA 只是微调的效率工具，它不能替代数据质量和数据量的基本要求。

**Q2: 如果我重新做行至的项目，我会加什么？**

A: 至少加三样东西：
1. **测试集（Eval Set）**：从 QA 对中留出 20% 不参与训练，用来测试微调后的模型效果
2. **Baseline 对比**：用同样的测试集去问基座模型（不微调），对比微调前后的准确率
3. **Badcase 分类**：把答错的 case 分类，判断是"数据标注错了"还是"模型没学会"

**Q3: "QA 对生成"这一步有什么坑？**

A: 你可能没注意到的坑：
- **格式转换丢失信息**：原始文档有很多结构化信息（标题、段落、表格关系），转成 QA 对后全部丢失
- **QA 对的覆盖度**：文档里 100 个知识点，QA 对只覆盖了 40 个 → 模型学不到另一半
- **QA 对的难度**：如果都是"XX 是什么？"这类简单问题，模型学不到深层理解
- **噪音引入**：文档 → QA 对的转换过程本身会引入错误（理解偏差、格式错误）

**Q4: 为什么 ToB AI 项目甲方不在意效果？**

A: 这是中国 AI 行业的一个真实现象。原因很复杂：
- 预算制：今年不用完明年经费被砍
- 追风口：领导要求"我们也要搞 AI"，中层执行
- 验收标准模糊：合同里没有明确的准确率指标
- 信息不对称：甲方不懂 AI，你说"训练好了"他们就信

但这也意味着：**在未来真正能交付"有效果"的 AI 项目的人，会稀缺**。因为你见过"敷衍的交付"，你就知道"真正的交付"该怎么做。

### 面试官可能的追问及你的回答准备

**追问：你觉得微调和 RAG 怎么选？**

> "这取决于场景。如果领域知识频繁更新、需要可追溯性、数据量小——选 RAG。如果领域知识稳定、需要模型内化推理模式、数据量充足——选微调。在行至的场景下，甲方文档持续更新，RAG 可能比微调更合适，但从商业化角度，'训练专属模型'的叙事比'搭检索系统'更好卖。"

**追问：怎么衡量一个 QA 对的质量？**

> "从两个维度：正确性——答案对不对；可学习性——这条 QA 对能不能让模型学到东西。第二条是我后来才意识到的，当时只关注了正确性。"
