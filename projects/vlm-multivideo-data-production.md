## 一、项目概览

### 背景

多视频理解是 VLM 能力公认短板（Video-MME 等 benchmark 上所有前沿模型丢分的场景）。数据收集存在三大痛点：

```text
① 无统一标准：样本难度不一致、证据不足、格式不规范
② 采集低效：依赖人工按关键词搜索视频，反爬与配对困难
③ 交付低效：prompt/CoT/response 依赖人工撰写与手动填表
```

### 目标

```text
主线目标：让《VLM视频-多视频理解数据收集-标准文档》落地为可执行要点，
        统一"选视频—出题—写 CoT—交付"全流程
自动化目标：视频资源爬取 + 离线飞书文档串联自动填写
```

### 你的角色

- 标准文档拆解：标准 → 可执行工作要点（能力维度、生产流程、交付格式）
- 自动化探索：关键词爬取 → TOS 入库 → 去重 → 自动生成 prompt 与初版 CoT

## 二、核心工作内容

### 工作 1：标准文档拆解（已交付）

**① 核心目标抽取**

```text
├── 选材：可构建多视频问答的视频（可拆分单视频 / 组合多视频）
├── 出题：围绕多段视频构建中高难度 QA
└── CoT：写清跨视频证据与对应关系
```

**② 能力维度体系（L1/L2/L3 三层）**

```text
L1 跨视频感知：空间方位 / 计数统计 / 事件定位 / 行为理解
L2 跨视频对比：过程错误检测 / 时间交叉引用 / 实体匹配·状态差异 /
               模式对比 / 功能步骤对齐
L3 跨视频推理：因果推理 / 假设·操作迁移 / 综合理解
暂不做：叙事理解 / 时序排列
```

**③ 操作流程**

```text
网络按关键词获取可配对视频 → 按维度构造问题与答案
→ CoT 写成"逐视频、逐证据段落 + 汇总结论"
```

**④ 交付格式（JSON 对象）**

```text
sample_id / video_tos_link_1..n / question / answer / cot
+ 剪辑与去信息干扰（打码）要求
+ 视频多样性要求
```

→ 离线飞书文档串联自动填写 → 人工终版 → 交付

## 三、Technical Anatomy

### 主题 1：L1/L2/L3 能力维度体系 —— 为什么这样分层

```text
分层逻辑 = 多视频理解的复杂度递进

L1 跨视频感知（基础层）
├── 问题形态：单个视频内就能回答，但需要跨视频采集样本
├── 例：两个视频里各有什么物体？两个场景的方位关系？
└── 复杂度：低（信息提取即可）

L2 跨视频对比（对应层）
├── 问题形态：必须在 ≥2 个视频之间建立"对应关系"才能回答
├── 例：左视频里球是红的，右视频里变成蓝的了吗？
├── 本质：跨视频实体/状态/时间对齐
└── 复杂度：中（需要对齐 + 差异判断）

L3 跨视频推理（融合层）
├── 问题形态：跨视频证据融合后做因果/迁移/综合判断
├── 例：A 视频的步骤在 B 视频的场景下会产生什么结果？
├── 本质：多源证据 → 推理 → 结论
└── 复杂度：高（证据筛选 + 推理链条）

面试洞察：
"感知 → 对比 → 推理" 的分层和人类视觉认知的复杂度递进一致，
也和模型能力评测的难度分层一致（能力评测需要难度梯度）
```

### 主题 2：可配对视频 —— 多视频数据采集的核心约束

```text
定义：能构建多视频问答的视频组合
├── 同实体不同状态（同一物体/场景的两个时刻）
├── 同过程不同视角（同一事件的两个拍摄角度）
├── 同场景不同时间（白天 vs 夜晚）
└── 同任务不同做法（做菜步骤 A vs 步骤 B，用于步骤对齐/错误检测）

为什么是核心约束：
├── 多视频理解的本质 = 跨视频对应关系的建立
├── 没有可配对性 → L2/L3 维度无从构造
└── 所以选材标准从"单个好视频"变成"成对的好视频"

对关键词设计的影响：
├── 不是搜"一个有意思的视频"
├── 而是搜"能形成对比/对应的一组视频"
├── 例：计数类 → "同一货架 前后两个时间"
│   步骤对齐 → "同一道菜 两种做法"
└── 验证方法：召回后人工抽检配对率，迭代关键词
```

### 主题 3：CoT 证据结构 —— "逐视频、逐证据段落 + 汇总结论"

```text
为什么这样要求（vs 单视频 CoT）：
├── 单视频 CoT：时间线内的推理链
├── 多视频 CoT：必须显式声明"证据来自哪个视频"
└── 目的：证据可追溯 → 模型学会"引用"而非"编造"

标准结构：
├── 段落 1：视频 A 证据（时间点 + 画面内容 + 观察结论）
├── 段落 2：视频 B 证据（同上）
├── 段落 3：对应关系（A 的 X 与 B 的 Y 之间存在什么关系）
└── 汇总结论：基于证据的回答

与 Learnability 的连接：
├── 教模型的是"证据组织方式"（先定位、再比较、后结论）
├── 而不是"这道题的答案"
└── 跨场景泛化的关键：新场景能复用"证据组织框架"
```

### 主题 4：JSON 交付格式与数据治理

```text
为什么用 video_tos_link 而非网络 URL：
├── 网络 URL：可能失效（404）、无权限控制、无法统一管理
├── TOS（对象存储）：持久化、权限可控、入库后可去重/质检
└── 交付的是"存储引用"，保证数据可追溯可复现

为什么 sample_id 在首位：
├── 数据治理的锚点：每个样本唯一标识
├── 支持后续问题追踪（哪批数据质量差 → 通过 sample_id 定位）
└── 是数据管线可观测性的基础

打码（去信息干扰）：
├── 隐私类：人脸、车牌、门牌
├── 干扰类：水印、字幕（可能泄漏答案）
└── 目的：保证模型只能从"画面内容"推理，不被干扰信息误导

视频多样性要求：
├── 场景多样性 / 实体多样性 / 时长分布 / 拍摄视角
└── 避免能力集中在少数模式（对应训练数据的覆盖度）
```

### 主题 5：视频去重 —— 多模态去重难点

```text
文本去重（MinHash）：字符层面的 Jaccard 近似，成熟
视频去重：
├── 帧级去重：视频 A 和视频 B 内容相同但编码/分辨率不同
│   → 需要感知哈希（Perceptual Hash）或帧相似度
├── 转场/裁剪变体：同一素材的不同剪辑版本
├── 成本：视频解码 + 抽帧 + 特征提取 = 计算密集
└── 难点：重复定义不清晰（多相似算重复？）

面试价值：能说清"视频去重比文本去重难在哪"
```

## 六、面试官追问准备

**Q1：为什么多视频理解比单视频理解难？**
跨视频对应关系的建立——单视频是时间线内推理，多视频要在不同视频间对齐实体、状态、时间，还要判断差异和因果。L2/L3 维度都依赖这种对应能力，这是当前所有 VLM 的短板。

**Q2：L1/L2/L3 的划分依据是什么？**
复杂度递进：L1 单视频信息提取即可回答（感知）；L2 必须建立跨视频对应关系（对比）；L3 在跨视频证据上做推理融合。每一层需要的模型能力不同，评测难度也不同。

**Q3：什么叫"可配对视频"？怎么找到它们？**
同实体不同状态、同过程不同视角、同场景不同时间、同任务不同做法。寻找方式：关键词设计围绕"能形成对比/对应的组合"（如"同一道菜两种做法"），召回后人工抽检配对率。

**Q4：为什么 CoT 要求"逐视频、逐证据段落 + 汇总结论"？**
保证证据可追溯——模型学会引用具体视频的具体内容，而不是编造。这也决定数据的 Learnability：教的是证据组织框架，可以跨场景复用。

**Q5：为什么用 video_tos_link 而不是网络 URL？**
网络 URL 会失效、无权限控制、无法统一治理；TOS 入库保证持久化、权限可控、可去重可质检，交付的是存储引用。

**Q6：视频去重怎么做？**
帧级/感知哈希：不同编码但内容相同的视频要识别为重复。比文本 MinHash 难在"重复定义"模糊 + 计算成本高（解码、抽帧、特征提取）。

**Q7：自动生成的初版 CoT 质量怎么保证？**
人机分工：初版自动生成，人工终版审核；可以加 LLM 自评 + 规则校验做前置过滤（复用我 CoT 质检的 Gate 思路）。

**Q8：怎么验证关键词召回的有效性？**
抽样人工标注"是否真是目标类型 + 是否可配对"，算类型准确率和配对率，迭代关键词矩阵。

**Q9：反爬怎么处理？**
合法路径优先（官方 API/公开数据集），技术路径（UA/代理/频率控制/渲染服务），合规边界先确认。

**Q10：这个项目的 KPI 是什么？**
短期：交付数据的 JSON 字段合规率、人工审核通过率；中期：自动生成初版 CoT 的采纳率（节省人力比例）；长期：多视频数据喂入后模型在相关评测上的提升（Ablation）。

## 九、Evals 落地 1：自动生成 CoT 质量评估方案（2026-08-05）

> 目标：让"自动生成初版 CoT"有质量闭环。生成 → 评估 → 迭代，缺一不可。
> 方法论来源：Anthropic Agent Evals（Task + Trial + Grader）+ 自身质检经验。

### 9.1 为什么需要评估（现状问题）

```text
自动生成初版 CoT 的三大风险：
├── 结构不合规：没有按"逐视频段落 + 汇总结论"组织
├── 证据虚构：CoT 引用了视频里不存在的内容（LLM 幻觉）
└── 答案错误：answer 与视频内容不一致
没有评估 → 这些错误直接流到人工终审 → 人工成本没降、
    错误还可能漏过 → "自动化"反而引入新质量风险
```

### 9.2 评估任务定义（Task）

```text
评估对象：自动生成的 JSON（video_tos_link + question + answer + cot）
评估维度（对应交付标准）：
├── D1 结构合规性：JSON schema 完整 + CoT 段落结构（逐视频标记）
├── D2 证据真实性：CoT 引用的视频内容（时间点/画面/实体）真实存在
├── D3 证据对应性：跨视频关系（L2 对比/L3 推理的证据链）成立
└── D4 答案正确性：answer 与视频内容一致
```

### 9.3 三层 Grader 设计

```text
Grader 1：规则/代码评分器（零成本，全量跑）
├── JSON schema 校验（字段完整、类型正确）
├── CoT 结构规则检查（是否有"视频1：.../视频2：.../结论"段落标记）
├── answer 格式检查（数字/选项/语句类型符合 question 类型）
└── 输出：pass / fail（fail 直接标记原因）

Grader 2：LLM 评分器（LLM-as-Judge，全量或抽样）
├── D2 证据真实性：抽取 CoT 中的证据声明（时间点+内容），
│   让评测模型对照视频帧验证描述是否成立
├── D3 证据对应性：L2/L3 维度检查"视频 A 的 X 与视频 B 的 Y"
│   的对应关系是否被 CoT 正确建立
├── 输出：pass / fail + 原因（结构化）
└── 注意：评测模型与生成模型分离（避免自评偏差）

Grader 3：人工抽检（权威层）
├── 抽检比例：如 10%（或按 Grader 2 置信度分层抽样）
├── 双人标注一致率（评估 Grader 1/2 的校准）
└── 用途：校准 Grader 2 的阈值 + 建立人工通过率基线
```

### 9.4 指标设计

```text
核心指标：
├── 初版 CoT 通过率（Grader 1+2 通过比例）—— 生成质量主指标
├── 各维度失败分布（结构/证据/答案各占多少）—— 定位修哪
└── 人工通过率（抽检样本中终审通过比例）—— 权威校准

校准指标：
├── LLM 评分器 vs 人工一致率（Grader 2 的可信度）
├── 误杀率（Grader 判 fail 但人工认为 pass）
└── 漏放率（Grader 判 pass 但人工认为 fail）
```

### 9.5 Pipeline 集成位置

```text
[生成初版 CoT] → [Grader 1 规则] → 通过 → [Grader 2 LLM] → 通过
   │                    │                     │
   │                   fail                  fail
   ▼                    ▼                     ▼
[重新生成/模板修正] ←  [规则修复（如结构补全）]  [人工修复或废弃]
                                        │
                                        ▼
                              [Grader 3 人工抽检 10%]
                                        │
                                        ▼
                                   [交付/入库]
```

### 9.6 迭代闭环（评估结果驱动生成改进）

```text
失败案例归因 → 修生成 prompt：
├── D2 证据虚构高发 → prompt 加约束"只引用画面中实际出现的内容"
├── D1 结构不合规高发 → 模板示例（few-shot）强化
├── D3 对应关系薄弱 → 针对 L2/L3 维度的专门 prompt 模板
└── 评分器自身迭代：Grader 2 通过率趋近 100% → 加难度（评测饱和）
```

### 9.7 落地时间线

```text
第 1 周：方案评审 + Grader 1 规则实现（纯代码，无模型成本）
第 2 周：Grader 2 LLM 评分器试点（50 条样本 + 人工校准）
第 3 周：全量跑通 + 指标基线（通过率/失败分布）
第 4 周：第一轮生成 prompt 迭代（按失败分布优先级）
```

## 十、Evals 落地 2：交付数据 → 多视频理解评测集（2026-08-05）

### 10.1 为什么可以（数据即评测素材）

```text
交付 JSON（question + answer + cot）本身是评测集的标准形态：
├── question = 评测题目
├── answer = Ground Truth（对错判定）
└── cot = 证据链（可做证据质量评分——比普通评测集多一层）

升级视角：
├── 现状：交付数据 → 入库 → 训练/评测用（下游不可见）
├── 升级：主动定义"这批数据作为多视频理解评测集的形态"
└── 数据从"原材料"变成"评测基础设施"
```

### 10.2 评测集设计（Task/Trial/Grader）

```text
Task 定义：L1 跨视频感知 / L2 跨视频对比 / L3 跨视频推理
├── 与交付标准共用同一套维度 → 评测难度天然分层
└── 比通用 benchmark 的优势：题型可追溯（有 cot 证据链）

Trial 设计：视频（多段）+ question → 模型输出
├── 视频侧：可配对视频组合（同一组视频可出多题）
├── 问题侧：中高难度（与交付标准一致）
└── 用例数：首批 200-500 条（按维度分层抽样）

Grader 设计（双评分）：
├── 答案对错：answer 对比（确定性评分）
├── 证据质量：模型是否给出可追溯的跨视频证据（LLM 评分）
└── 分级输出：完全正确 / 答案对证据弱 / 错误
```

### 10.3 与算法团队的沟通要点（proposal 三句话）

```text
① "我们的交付数据除了进训练集，可以直接抽 200-500 条
   构成多视频理解评测集，维度分层现成（L1/L2/L3）。"
② "比通用 benchmark 强的地方：每道题自带证据链（cot），
   能做证据质量评分，不只是对错判定。"
③ "评测集防泄漏：这批数据不进入训练集（或先评测后训练），
   可以支撑模型版本迭代的回归验证。"
→ 主动提出这个 = 从"交付数据的人"变成"设计评测体系的人"
```

### 10.4 面试价值

```text
面试表达：
"我把交付数据主动设计成了评测集素材——因为交付标准里
本来就有 question/answer/cot，cot 让每道题自带证据链，
可以做证据质量评分。我向算法团队提出了用 L1/L2/L3 分层
构建多视频评测集的方案。"
→ 证明你不仅生产数据，还理解数据在评测体系中的价值
```

## 十一、Evals 落地 3：暂不做方向的评测边界判断（2026-08-05）

### 11.1 决策框架（三问）

```text
一个能力方向"做不做"，用评测可行性前置判断：
├── ① Grader 可设计性：这个能力的正确答案能稳定判定吗？
│   ├── 能 → 评测可自动化/半自动化
│   └── 不能（主观/多解）→ 评测成本极高
├── ② Trial 可构造性：能稳定获取这类数据吗？
│   ├── 可配对视频是否可得？
│   └── 构造难度和成本
└── ③ 价值优先级：是不是模型当前的能力瓶颈？
    └── 不是瓶颈 → 数据做了也测不出提升 → 资源浪费
```

### 11.2 应用：为什么"叙事理解/时序排列"暂不做

```text
用三问验证标准文档的决策：
├── Grader 可设计性：❌ 弱
│   └── "叙事讲得好不好"主观性强，Ground Truth 难稳定判定
├── Trial 可构造性：❌ 弱
│   └── 需长视频 + 完整叙事结构，可配对/可分段的素材稀缺
└── 价值优先级：🟡 中
    └── 当前模型瓶颈在感知/对比/推理，叙事理解非最高优先级

结论：三问中两问不过 → "暂不做"是评测可行性驱动的决策，
不是随意取舍——这本身就是 Evals 方法论在数据策略层的应用
```

### 11.3 面试表达

```text
面试官："你们为什么不做叙事理解？"
你："方向取舍我用评测可行性前置判断：第一，叙事理解的
Ground Truth 难稳定判定，Grader 设计成本极高；第二，可配对
的长叙事视频素材稀缺，Trial 构造困难；第三，当前模型瓶颈
在感知、对比、推理，叙事不是最高优先级。三问中两问不过，
所以暂不做。这个框架也可以反着用——L1/L2/L3 能做，
就是因为这三问都成立。"
```

## 十二、Evals 落地 4：采集环节评测 —— 覆盖度与多样性评测（2026-08-05）

> 目标：让「关键词爬取」这个环节有质量闭环。采集 → 评测 → 关键词策略迭代。
> 背景：评测链三环节（采集 → 质检 → 应用）中，采集是唯一缺评测的环节——补上它，评测链闭环。

### 12.1 为什么采集需要评测（现状问题）

```text
关键词爬取目前无衡量，三个盲区：
├── 分布未知：采到的视频是否对齐标准拆解的目标分布？
│   类型 × 场景 × 关键词的覆盖情况不可见 → 不知道缺哪个格子
├── 配对率未知：L2/L3 维度能构造多少样本？
│   采了一堆单条好视频，但"可配对"的没几条 → 能力维度覆盖失败
└── 冗余未知：去重后剩多少？
    爬取投入多少浪费在重复素材上 → 采集效率无归因

没有评测 → 采集策略靠感觉，关键词迭代无法归因：
"换了关键词，覆盖是变好了还是变差了？"——答不上来
```

### 12.2 评测对象：批次/集合，不是单条（与质检的本质区别）

```text
CoT 质检（数据评测）：判断单条数据 → 通过/修复/废弃（确定性高）
采集评测（覆盖度评测）：统计一个批次的分布（确定性低）

区别的含义：
├── 单条判断 → 规则可全量自动化（Gate 系统）
├── 批次统计 → 需要抽样 + 统计推断（人工标注一小批 → 推整体配对率）
└── 判断确定性越低 → 依赖 LLM/人工的 Grader 比例越高
```

### 12.3 指标设计（核心：4 个指标）

```text
M1 覆盖度矩阵：类型(L1/L2/L3) × 场景 × 关键词 → 目标量 vs 实际量
├── 目标定义来源：标准文档拆解（每格目标量来自能力维度需求）
├── 输出：覆盖度差距表 → 缺哪个格子补哪个关键词
└── 作用：评测驱动采集（采集策略的归因锚点）

M2 可配对率：抽样标注"是否可配对"
├── 判定标准：同实体不同状态 / 同过程不同视角 / 同场景不同时间 / 同任务不同做法
├── 抽样方法：按关键词分层抽样 30-50 条人工标注
└── 作用：L2/L3 样本可构造性的量化指标（连接主题 2）

M3 去重有效量：去重后有效样本 / 原始采集量
├── 全量自动统计（规则层）
└── 作用：采集冗余度指标，驱动去重前置/检索策略优化（连接主题 5）

M4 类型准确率：抽样标注"是否真是目标类型"
├── 判定标准：是否属于该关键词声称的类型（计数/对比/步骤...）
└── 作用：关键词召回质量（"词 → 视频"的映射精度）
```

### 12.4 三层 Grader 映射（延续 Evals 方法论）

```text
Grader 1 规则/统计（零成本，全量跑）
├── M3 去重有效量：去重后的样本数统计
├── M1 覆盖度格子：按视频元数据/文件名归类，统计每格实际量
└── 输出：覆盖度差距表 + 冗余率

Grader 2 LLM 评分器（抽样或全量）
├── M4 类型判定：视频是否属于目标类型（VLM 分类）
├── M2 可配对性预筛：两两视频候选的配对判定（VLM + 标题/元数据）
└── 输出：候选配对列表（人工只需确认，降人工成本）

Grader 3 人工抽检（权威层，抽样）
├── M2 配对率最终判定：30-50 条抽样标注
├── M4 类型准确率校准：验证 Grader 2 的准确度
└── 用途：建立基线 + 校准 Grader 2 阈值
```

### 12.5 Pipeline 集成位置

```text
[关键词爬取] → [TOS 入库] → [去重] → [采集评测 M1-M4]
                                   │
                                   ▼
                           [覆盖度报告（周粒度）]
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
              [缺格 → 补关键词]  [配对率低 → 换词]  [冗余高 → 去重前置]
                    └──────────────┼──────────────┘
                                   ▼
                      [下一轮采集策略（评测驱动）]
```

### 12.6 迭代闭环（评测结果驱动采集策略）

```text
归因 → 动作：
├── M1 某格缺口大 → 该类型×场景新增关键词（评测驱动采集）
├── M2 配对率低 → 关键词设计从"搜单个视频"转向"搜配对组合"
│   （连接主题 2："同一道菜两种做法"式关键词）
├── M3 冗余率高 → 去重前置到爬取环节 / 检索策略优化
└── M4 类型准确率低 → 换关键词或加负例过滤规则

与落地 1 的同构性：CoT 评估失败分布 → 修生成 prompt；
这里采集失败分布 → 修关键词策略。同一套「归因 → 迭代」闭环
```

### 12.7 评测链闭环：三环节三种评测类型（面试叙事）

```text
数据链路三环节，每个环节一种评测类型，同一套方法论：

采集（VLM）    →  质检（CoT）        →  应用（Price-Agent）
覆盖度评测      数据质量评测           Agent 能力评测
└── 批次统计   └── 单条门控          └── 维度化任务
    (确定性低)     (确定性高)            (维度化打分)
    M1-M4 指标    5 层 Gate            7 阶段分层

成长叙事：
"我用同一套 Evals 方法论贯穿数据链路三环节——每个环节
定义「好」、量化「好」、用数据驱动迭代。评测的确定性
从低到高逐个啃下：采集（覆盖度）→ 应用（Agent 行为）
→ 质检（单条数据）。"
```

### 12.8 面试表达

```text
面试官："你的采集环节怎么保证数据质量？"
你："采集环节我补了覆盖度评测——这是评测链三环节里
最后一块拼图。四个指标：覆盖度矩阵（类型×场景×关键词
对齐标准拆解的目标分布，缺格补格）、可配对率（L2/L3
样本可构造性的量化，抽样人工标注）、去重有效量（冗余度）
、类型准确率（关键词召回质量）。前两个统计指标全量自动，
配对判定用 LLM 预筛 + 人工抽样校准。结果回流到关键词策略：
配对率低就换'搜配对组合'式的关键词。"
→ 证明采集不是"爬取执行"，而是"有评测驱动的数据策略"
```
