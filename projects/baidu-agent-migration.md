## 二、核心技术解剖

### 2.1 Function Calling 到底是什么？

本项目最核心的技术概念。

#### ① 它是什么？

**Function Calling（函数调用）** 是一种让 LLM 调用外部工具/API 的机制。模型不再只输出文本，而是输出一个结构化的"函数调用请求"，然后外部系统执行这个函数，把结果返回给模型。

```text
没有 Function Calling：
用户: "帮我把这笔物料从品专旧体系迁移到百看资产"
模型: "好的，我已经帮你迁移了" ← 幻觉！模型没法真的操作平台

有 Function Calling：
用户: "帮我把这笔物料从品专旧体系迁移到百看资产"
模型: 分析意图 → 决定需要调用 migrate_material 函数
     ↓
模型输出（不要文本，要 JSON）:
{
  "function": "migrate_material",
  "parameters": {
    "material_id": "M12345",
    "source": "pinzhuan_legacy",
    "target": "baikan_asset"
  }
}
     ↓
外部系统执行迁移，返回结果: {"status": "success", "new_id": "M67890"}
     ↓
模型: "迁移成功！新物料 ID 是 M67890，你可以在这里查看..."
```

> 注：以上对话为机制示意；实际产品中迁移请求通过固定表单提交（见 2.5）。

#### ② 为什么出现？

LLM 有两个根本限制：
1. **不能执行操作**：模型只能"说"，不能"做"
2. **知识不是实时的**：模型不知道当前数据库里有什么数据

Function Calling 解决了这两个问题：模型通过调用外部函数获得"动手能力"和"实时信息"。

#### ③ 数学/工程原理

Function Calling 不是魔法。它是这样工作的：

```text
Step 1: 定义函数声明
你告诉模型有哪些函数可用，每个函数的参数结构是什么。

{
  "name": "migrate_material",
  "description": "将一个品专物料从旧体系迁移到百看资产模型",
  "parameters": {
    "type": "object",
    "properties": {
      "material_id": {"type": "string", "description": "物料ID"},
      "source": {"type": "string", "enum": ["pinzhuan_legacy"]},
      "target": {"type": "string", "enum": ["baikan_asset"]}
    },
    "required": ["material_id", "source", "target"]
  }
}

Step 2: 模型推理
模型根据用户输入 + 函数声明，判断：
- 要不要调用函数？
- 调用哪个函数？
- 填什么参数？

Step 3: 约束采样（Constrained Decoding）
模型生成时，不再是自由生成文本，而是在你定义的 Schema 约束下生成。
这就保证了输出的 JSON 结构一定合法。
```

#### ④ 工程实现

```python
# Function Calling Agent 的核心循环（伪代码）

# 1. 定义你有的工具
tools = [
    {
        "name": "migrate_material",
        "description": "物料迁移",
        "parameters": {...}  # JSON Schema
    },
    {
        "name": "check_migration_status",
        "description": "查询迁移状态",
        "parameters": {...}
    },
    {
        "name": "rollback_migration",
        "description": "回滚失败的迁移",
        "parameters": {...}
    }
]

# 2. Agent 循环
def agent_loop(user_input):
    messages = [{"role": "user", "content": user_input}]
    
    while True:
        # 调用 LLM，传入工具定义
        response = llm.chat(messages, tools=tools)
        
        # 如果模型要调用函数
        if response.has_tool_call():
            tool_call = response.tool_call
            # 执行函数
            result = execute_function(
                tool_call.function_name, 
                tool_call.parameters
            )
            # 把结果追加到对话历史
            messages.append({
                "role": "tool", 
                "content": result
            })
            # 继续循环 → 模型看到结果后决定下一步
        else:
            # 模型返回最终文本 → 结束
            return response.text
```

#### ⑤ 为什么你的 Schema 设计那么重要？

你定义了输入 Schema 字段，这决定了 Agent 能做什么、做得多准。

```text
Schema 定义得好的效果：
├── 模型知道每个字段的类型 → 不会传错格式
├── 字段 description 写得好 → 模型填参数时更准确
├── required 字段标记清楚 → 模型不会漏关键参数
└── enum 约束 → 模型只能在预定义选项中选，不会编造

Schema 定义得差的效果：
├── 模型猜参数含义 → 填错
├── 漏掉非 required 但实际必要的参数 → 函数执行失败
├── 没有 description → 模型乱填
```

**Schema 设计本质上是 Prompt Engineering 的结构化版本**。这是 Agent 工程质量的决定性因素。

#### ⑥ 为什么不用别的方法？

替代方案对比：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **硬编码 if-else** | 手写所有迁移规则的代码 | 100% 确定 | 两个体系100+字段，规则爆炸 |
| **纯 Prompt** | 让 LLM 输出文本，自己解析 | 简单 | 格式不稳定，解析易出错 |
| **Function Calling** | LLM 输出结构化 JSON，外部执行 | 兼顾灵活性和可靠性 | 需要仔细设计 Schema |
| **Workflow (Dify/n8n)** | 可视化编排固定流程 | 行为确定 | 难以应对边界 case |

在你的场景下，Function Calling 是对的：品专旧体系与百看资产模型之间的字段映射有规律但不够规则化，硬编码不够灵活，纯 Prompt 不够可靠。

#### ⑦ 工业界实践

几乎所有主流 LLM 平台都支持 Function Calling：
- OpenAI：原生 Function Calling（2023 年 6 月发布）
- Anthropic：Claude Tool Use
- Google：Gemini Function Calling
- 国内：通义千问、文心一言、GLM 都支持

OpenAI 的 GPT-4 Function Calling 准确率约 85-95%（取决于任务的复杂度和 Schema 设计质量）——这个数字很重要：**Function Calling 不是 100% 可靠的，你需要 Badcase 处理机制**。你在百度做的 Badcase 分类处理，正是这个准确率上限的现实体现。

本项目实际使用的是百度内部部署的 DeepSeek-V3.1 模型——开源模型在 Function Calling 方面表现良好，能够处理复杂任务。

#### ⑧ 与 AI 系统的连接

```text
Function Calling 在 AI Agent 系统中的位置

[用户输入]
    ↓
[Agent Loop] ← 模型决定"下一步做什么"
    ↓
[Function Calling] ← 本主题：模型调用外部工具
    ↓
[外部系统/API] ← 你的物料迁移平台
    ↓
[结果返回] → Agent Loop 继续 → ... → 最终输出给用户
```

### 2.2 Schema Mapping 的本质

你做物料迁移时，核心问题其实是 **Schema Mapping（模式映射）**——两个不同数据体系之间的字段对应关系。

#### 品专旧体系 vs 百看资产模型

```text
品专历史物料结构            百看资产模型
──────────────            ──────────────
material_name: str        asset_title: str      ← 字段名不同
material_type: str        asset_type: enum      ← 类型不同
targeting: json           audience: json        ← 结构不同
budget: float             daily_budget: int     ← 单位不同（元 vs 分）
image_url: str            asset_image: str      ← 同样含义，完全不同的名字
```

**Schema Mapping 不是技术问题，是理解问题：**

> 你需要理解两个体系的业务语义，才能写出正确的映射规则。这是 PM 比纯工程师有优势的地方——你理解业务。

**PM 视角**：Schema Mapping 是整个迁移 Agent 的设计核心——映射规则错了，后面每一步都白做。
**算法视角**：映射规则的覆盖率直接影响迁移成功率，这是 Badcase 分类中最大的一类根因（见 2.4）。
**工程视角**：100+ 字段的映射规则需要维护机制——新增字段、字段变更时，规则如何同步更新？

### 2.3 Plan-Execute Agent 模式

你在百度接触了 Plan-Execute 这种 Agent 模式。这是 Agent 设计中最经典的两种模式之一。

#### Plan-Execute vs ReAct

```text
Plan-Execute：
用户: "把 M123 从品专旧体系迁移到百看资产"
    ↓
Plan 阶段：
├── Step 1: 读取物料 M123 在旧体系的数据
├── Step 2: 检查百看资产模型的字段要求
├── Step 3: 生成 Schema 映射
├── Step 4: 执行迁移
└── Step 5: 验证迁移结果
    ↓
Execute 阶段：按计划逐步执行
    ↓
如果某步失败 → 重新 Plan → Execute

ReAct（Reasoning + Acting，另一种经典模式）：
用户: "把 M123 从品专旧体系迁移到百看资产"
    ↓
Thought: "我需要先查 M123 的数据"
Action: read_material("M123")
Observation: "M123 是一个图片素材，size 是 1200×800..."
    ↓
Thought: "百看资产要求 size 不超过 1000×1000，需要先压缩"
Action: resize_image("M123", width=1000)
Observation: "压缩完成"
    ↓
Thought: "现在可以迁移了"
Action: migrate("M123", target="baikan_asset")
Observation: "迁移成功，新 ID 是 M456"
```

| | Plan-Execute | ReAct |
|---|---|---|
| 思考方式 | 先想好全盘 → 再执行 | 边想边做，每步都观察 |
| 适用场景 | 任务复杂度已知、步骤可预判 | 环境不确定、需要灵活调整 |
| 优点 | Token 效率高（不用每步都输出完整思考） | 灵活、能应对意外 |
| 缺点 | 计划错了全盘重来 | Token 消耗大（每步都输出"思考"） |
| 你的场景 | ✅ 物料迁移的步骤相对确定 | — |

**你在百度的工作用 Plan-Execute 是合理的**——迁移一个物料的流程大致固定（读取 → 映射 → 写入 → 校验），不需要每一步都"重新思考"。

### 2.4 Badcase 分类到成功率提升 — 迁移结果评测与数据驱动的迭代方法论

这是你在百度做得最 Product Manager 的事情，但同时也是最 Engineering 的事情。

#### 迁移失败的可能原因分类

```text
物料迁移失败原因树
│
├── Schema 层面（字段不匹配）
│   ├── 源体系有字段 X，百看资产模型没有
│   ├── 字段类型不一致（如源体系文本 vs 百看枚举）
│   └── 必填字段在源体系缺数据
│
├── 数据层面（数据质量问题）
│   ├── 源数据格式错误（如 URL 拼写）
│   ├── 源数据超长（百看字段长度限制）
│   └── 源数据语义冲突（如定向条件互相矛盾）
│
├── 业务规则层面（体系逻辑差异）
│   ├── 百看的审核规则与旧体系不同
│   ├── 行业资质要求不同
│   └── 投放策略在不同体系有不同的限制
│
└── 系统层面（技术问题）
    ├── API 超时 / 限流
    ├── 并发冲突
    └── 目标平台暂时不可用
```

> 失败树中没有"意图识别/参数抽取"分支——因为迁移输入是固定表单，输入空间被产品形态约束住，query 理解错误被设计消除（见 2.5）。

#### Badcase 驱动的迭代流程

> 以下轮次数字为演示迭代方法的**示意值**；真实数据：最终迁移成功率 92%（见 1.4）。

```text
第 1 轮：初始 Agent（V1）
    ├── 迁移成功率：60%（示意）
    ├── Badcase 采集：收集所有失败的 case
    │
    ↓ 分类分析
    │
发现：40% 的失败是因为 Schema 字段映射错误
    │
    ↓ 修复
    │
第 2 轮：优化 Schema 映射规则（V2）
    ├── 迁移成功率：75%（示意）
    ├── Badcase 采集
    │
    ↓ 分类分析
    │
发现：15% 的失败是因为百看审核规则拦截
    │
    ↓ 修复
    │
第 3 轮：增加预检逻辑——迁移前先检查百看规则（V3）
    ├── 迁移成功率：85%（示意）
    └── ...以此类推，持续双周迭代，最终收敛到 92%
```

**这本质上就是一个 ML 训练循环，不过是人驱动的而不是梯度下降驱动的：**

```text
ML 训练循环              你的 Badcase 循环
───────────              ────────────────
Forward pass →           执行迁移 →
Loss 计算 →              发现失败 →
Backprop →               分析原因 →
参数更新 →               修改规则/Schema →
下一轮                   下一轮
```

#### 策略思维的体现

百度项目本身是**中台工作**，但「Badcase 分类 → 定位根因 → 修改策略 → 验证成功率提升」的这个循环，恰好是**策略思维的体现**——不是因为你做了策略 PM 的工作，而是因为你用数据驱动的方式做了中台 PM 的工作。

### 2.5 输入约束设计：固定表单的选择与取舍

为保证迁移执行的准确性，迁移入口定义为**固定输入表单**：用户按表单字段填写，而不是自由自然语言输入。query 理解错误不是"被评测发现的"，而是"被设计消除的"。

**为什么这样设计（当时的决策逻辑）：**

```text
├── 表单字段 = Schema 的人机界面：填写过程就把用户约束在合法输入空间内
├── 从根上消除 query 理解错误：没有自由文本 → 不存在意图识别/参数抽取问题
└── 准确性优先：B 端批量迁移场景，宁可多一步填写，不能迁移错
```

**代价（反刍后看清的）：**

```text
├── 灵活性差：场景扩展要改表单 → 每次扩展依赖产品迭代排期
├── 用户学习成本：用户必须理解表单字段含义，长表单体验差
└── 天花板：表单约束的是"输入形态"，不解决"决策质量"（见 3.2）
```

**四视角解读：**

- **PM 视角**：输入表单是把 Harness 约束做在了产品层——用产品形态替代模型能力，是当时成本最低的可靠性方案
- **算法视角**：约束输入空间 = 缩小模型的决策空间，错误概率随空间收缩而下降
- **工程视角**：表单字段与 API Schema 一一对应，天然的前置校验，实现成本极低
- **策略视角**：这是"确定性约束 vs 模型能力"的权衡——放开约束的前提是评测兜底（query 评测集，见 3.3）

**放开约束的三阶段演进（反刍）：**

```text
阶段 1（当时的事实）：智能助手 → 选择迁移 → 输入必填字段
    → 执行迁移 → 返回结果
├── 自主性：入口菜单式选择，输入零自主（表单）
├── 评测需求：平台层断言校验（92% 在这一层）
└── 用户只能做单任务、结构化的迁移

阶段 2（可扩展的下一步）：智能助手 → query「把 XX 物料迁移到百看」
    → 执行迁移
├── 自主性：输入自由化——意图识别 + 参数抽取解锁
├── 评测需求：+ query 评测集
└── 前提：管线成功率高且稳定（92% 已达标）

阶段 3（融入营销 Agent 的愿景）：多任务复杂 query，
    迁移只是其中一步（「迁移并生成资产卡，匹配买词后投放」）
├── 自主性：编排自主——多工具选择、多步调度、跨平台补偿
├── 评测需求：+ 任务级评测（编排层）
└── 迁移成为营销 Agent 工具集的一个节点，Agent 的价值
    随工具数增长（入口-平台架构，见 1.2.1）
```

每放开一层自主性，前置条件是多一层评测兜底——「放开多少自主性 = 多强的评测兜底」的三阶段落地版（与三层评测的对应关系见 3.3）。

## 三、架构局限与升级路线

> 背景：百度 Agent 背后使用内部部署的开源模型（Qwen / DeepSeek，主用 DeepSeek-V3.1；API 调用），**未做业务后训练**，仅靠工程化 Harness 约束 + Prompt 规则约束。受限于业务成本与条件。

### 3.1 架构选择的合理性（为什么这样是对的）

```text
为什么可以不做后训练：
├── Agent 任务的难点不在"语言能力"，在"工具调用的正确性"
│   ├── 开源模型通用能力 + Function Calling 已足够强
│   └── Harness 约束解决 90% 可靠性问题
│       （输入侧：固定表单约束输入空间，见 2.5；
│        输出侧：Schema 约束、格式校验、流程编排、重试、回滚）
├── 后训练的真实成本：
│   ├── 高质量业务数据（标注+清洗+配比）
│   ├── GPU 训练资源 + 训练工程师排期
│   └── 评测验证闭环（训练完怎么证明变好了）
└── 渐进式投资原则：业务价值未验证时不预支训练成本
    92% 成功率 + 98% 人力降本已让业务跑起来
    → 剩余 8% 人工兜底，比训练便宜得多

定性："先验证业务价值，再投入模型优化"的教科书路径；
     "剩余 8% 人工兜底" = 是否值得后训练的决策缓冲
```

### 3.2 天花板（局限性精确表述）

```text
Harness + Prompt 的天花板：
├── 模型不"懂"业务，靠 Prompt 描述规则
│   ├── Prompt 覆盖到的场景 → 成功
│   └── 未覆盖的 edge case → 失败（规则爆炸）
├── 决策质量不随使用次数积累（无内化）
│   ├── 人工做 1000 次迁移越来越熟练
│   └── 模型做 1000 次还是同一水平
├── Prompt 越长越贵、越难维护
└── 换业务场景 → 从头调 Prompt（经验不沉淀）

本质：Harness 解决"输出形态正确"（确定性），
     后训练解决"决策质量提升"（内化）——本项目只做了前者
→ 92% 可能是 Prompt+Harness 架构的收敛极限，
  突破上限必须靠参数层变化
```

### 3.3 三步升级路线（如果重新做）

```text
第一步：评测闭环先补齐（零训练成本，收益最大）——评测三层，对应架构三层（见 1.2.1、2.5 三阶段演进）
├── 平台层：断言式校验评测集（当时项目的真实缺口）
│   ├── 字段映射抽查 / 入库条数对比 / 物料缺失清单
│   ├── 双重用途：质量评测 + 研发交付的验收标准
│   └── 可全量跑脚本，不需要 LLM judge（92% 在这一层）
├── 入口层：query 评测集（阶段 2 放开直接 query 的前置）
│   ├── 各种输入方式 × 预期标注 {intent, params, action}
│   ├── 指标：意图识别准确率 / 参数抽取准确率 / 任务完成率
│   └── 固定表单时代不需要它——放开约束必须先有评测兜底
├── 编排层：任务级评测（阶段 3 融入多任务 query 的前置）
│   ├── 多步任务集：迁移 + 生成 + 匹配 + 投放的复合需求
│   ├── 指标：tool selection 正确率 / 端到端任务成功率
│   └── 对应 τ-bench 类 benchmark 思路——入口的价值在这一层
├── 每次改动跑评测集 → 避免"修好一类引入另一类"
├── 系统层失败（API 超时）自动重试 → 零成本救回部分 case
└── 模型对比评测：Qwen vs DeepSeek 在迁移任务上的表现
    （可能不训练就白嫖几个点）

第二步：LoRA 轻量后训练（低成本业务适配）
├── LoRA 只训练 1-2% 参数：1-2 张 A100，几小时到一天
├── 训练数据来自 Agent 自己的运行日志 ⭐（数据飞轮）
│   ├── 成功迁移案例 → 正样本
│   ├── 失败 + 人工修正案例 → 修正样本（比人工写数据便宜十倍）
│   └── Badcase 分类体系直接变成训练数据管道
├── 收益：模型"内化"Schema 映射 + 平台规则
│   → Prompt 从"教规则"瘦身成"提示"
└── 数据飞轮：Agent 越用 → 数据越多 → 模型越好

第三步：评测驱动的持续迭代
├── 后训练前后 A/B 对比（成功率 + Badcase 分布）
├── 持续收集运行数据 → 定期增量微调
└── 目标：92% → 96%+（兜底 8% → 4%）
```

### 3.4 后训练决策判断公式

```text
后训练收益 =（成功率提升 × 单次失败成本 × 业务量）− 训练成本

值得做的信号：
├── 业务价值已验证（采纳率 75% → 规模化在即）
├── 失败成本高（迁移失败 → 客户投诉/投放事故）
├── 数据量足够（Badcase + 成功案例 ≥ 几百条）
└── 成功率逼近 Prompt 架构极限（优化边际递减）

不值得的信号：
├── 业务还在验证期、场景频繁变
├── 训练数据量不足（<100 条高质量样本）
└── 人工兜底成本 < 训练成本

关键判断：当年不做是"对的决策"；业务规模化后继续不做
        = "错的决策"——决策要跟着业务阶段走
```

### 4.5 MCP（Model Context Protocol）Technical Anatomy

```text
① 它是什么：模型上下文协议，标准化 LLM 与外部数据/工具的
   连接方式（2024 年 11 月 Anthropic 发布，2025-2026 生态化）

② 为什么出现：Agent 需要接工具/数据，但每个应用一套 API
   （N×M 集成爆炸）；MCP 统一接入标准——写一次 server，
   可被任意支持 MCP 的 Agent 调用

③ 原理：Client-Server 架构
   ├── MCP Host（LLM 应用，如文心助手）
   ├── MCP Client（连接器）
   └── MCP Server（暴露 capabilities：tools / resources / prompts）
   传输：JSON-RPC 2.0

④ 工程实现：Server 声明工具与资源；LLM 通过 tool call 调用；
   与 Function Calling 同构，但标准化了"声明 + 发现 + 调用"

⑤ 为什么有效：协议统一 → 集成成本降一个数量级；
   Agent 生态互通（品牌写一个 server，全网 Agent 都能用）

⑥ 为什么不用别的方法：
   ├── API 直连：一对一集成，N 个 Agent × M 个品牌 = N×M
   ├── Plugin 生态（ChatGPT Plugin）：平台绑定，跨模型不通
   └── 原生 Function Calling：每模型一套 schema，迁移成本高
   → MCP 是跨模型、跨平台的中间层标准

⑦ 工业界怎么做：
   ├── Anthropic 提出；OpenAI/Google 跟进（2025-2026 标准化）
   ├── Claude Code / Cursor 等 Agent 工具原生支持 MCP
   └── 百度品牌 MCP = 垂直行业应用：品牌资产作为 MCP server
       向营销 Agent 开放（AI 品专的资产接入层）

⑧ 与 AI 系统的连接：
   ├── ↔ Function Calling（MCP = Function Calling 的标准化+生态化）
   ├── ↔ Agent Tool Calling（知识树 System / Agent Runtime 节点）
   └── ↔ 你的百度项目：品牌 MCP 背后的资产库 = ①+② 的产出
```


### 5.4 算法/工程视角话术（补齐后可以说）

> 我设计了一个基于 Plan-Execute 模式的物料迁移 Agent。核心设计包括：固定输入表单（约束输入空间，从根上消除意图理解错误）、输入 Schema 的字段定义（确保模型参数填充准确）、Badcase 分类体系（Schema 层/数据层/规则层/系统层四类）、以及基于 Badcase 数据的迭代优化循环。我遇到的一个关键 case 是 Schema Mapping 引起的迁移失败——两个体系的字段语义相同但类型不同，通过增加类型转换的预处理逻辑解决。最终迁移成功率达到 92%（测试覆盖 462 家客户）。

### 5.5 面试官追问及准备

**Q1：迁移成功率 92% 怎么做到的？**

Badcase 驱动的迭代循环：收集失败 case → 按根因分类（Schema 层/数据层/规则层/系统层）→ 优先修影响面最大的类 → 双周迭代验证。92% 是持续优化的结果，剩余 8% 走人工兜底。

**Q2：98% 的人力成本降低是怎么算的？**

人工迁移单物料小时级（多步手工操作），Agent 分钟级（含人工审核）。自动化覆盖 + 时效压缩 → 按单物料处理人力折算。计算口径要能说清楚：人工处理单价 × 物料量 vs Agent 处理单价 × 物料量 + 人工兜底成本。

**Q3：多级回源策略是什么？**

Logo 来源优先级：先物料自身供给，缺失则平台供给，再缺失官网抓取。回源策略保证数据完整性——每级回源有成功率统计，决定下一级是否触发。

**Q4：为什么用 Agent 而不是硬编码？**

两个体系间字段映射有规律但不够规则化：100+ 字段、边界 case 多。硬编码规则爆炸且难维护；Agent + Schema 兼顾灵活性和可靠性，Badcase 迭代让可靠性持续收敛。

**Q5：任务编排框架的"指令式交互"是什么？**

用户用自然语言表达需求（"把这批客户的活动物料都迁移并生成百看卡"），框架解析为任务节点序列，按依赖关系调度执行——这是 Agentic Workflow 的产品化表达。

**Q6：这个项目你重新做会改什么？**

补三步，核心是评测先行：①建两层评测集——管线层断言校验（字段/入库/缺失），每次改动跑回归；若开放自由输入，再加 query 评测集兜底；系统层失败（API 超时）加自动重试；②从运行日志沉淀 SFT 数据，用 LoRA 做轻量业务适配，让模型内化映射规则；③评测驱动的持续迭代，目标 92% → 96%+。详见"三、架构局限与升级路线"。

**Q7：你的 Agent 做了业务微调吗？**

> 没有，用的是内部部署的开源模型（Qwen/DeepSeek，主用 DeepSeek-V3.1），只有 Harness 和 Prompt 约束。这是成本约束下的正确选择——92% 成功率已带来 98% 人力降本，业务价值未验证时不值得投入后训练。但我清楚上限：Prompt 覆盖不到的 edge case 就失败，经验不沉淀。如果重新做，三步走：①Badcase 评测集驱动 Prompt 迭代 ②从运行日志沉淀 SFT 数据，用 LoRA 做轻量业务适配，Prompt 从"教规则"瘦身成"提示" ③评测驱动持续迭代。核心洞察：训练数据可以来自 Agent 自己的运行日志——这是数据飞轮。

```text
四视角覆盖：
├── PM：成本-收益、渐进式投资
├── 算法：LoRA / SFT 数据 / 评测集
├── 工程：Harness 边界、数据飞轮
└── 策略：后训练决策公式、A/B 验证
```

**Q8：Plan-Execute 和 ReAct 怎么选？**

取决于任务的不确定性。物料迁移的步骤相对固定，Plan-Execute 更合适——先读源数据、再做映射、再写入、再校验，计划在第一步就确定了。但如果场景是"帮我优化这个广告投放方案"——目标不确定、中间可能需要多次调整——ReAct 更合适，因为每一步的结果都可能改变下一步的决策。

**Q9：为什么当时用固定输入表单而不是自由自然语言输入？**

准确性优先。迁移是 B 端批量操作，错一条的代价高——固定表单把输入空间约束在合法范围内，从根上消除意图理解错误，是当时成本最低的可靠性方案。代价是灵活性：场景扩展要改表单。反刍后的演进分三阶段：①表单链路（现状，92% 管线成功率已达标）②开放直接 query 执行迁移（前置：query 评测集）③融入营销 Agent 的多任务复杂 query，迁移成为其中一步（前置：任务级评测）。每放开一层自主性，前置条件是多一层评测兜底。

**Q10：固定表单的输入形式算 Agent 吗？感觉更像中台功能能力，字段在后端接口完全 ok，没体现出 Agent 的规划性和自主性。**

（本项目的含金量攻击题——面试官挑战的是"Agent"这个说法本身）

> 这个问题问得很准，我反刍这个项目的时候也问过自己同样的问题。我的结论分三层：
>
> 第一层，我承认：迁移执行这一环，严格说不算强 Agent。输入被固定表单约束之后，模型的决策空间很小——"迁移什么"由表单定死，"怎么迁移"的字段映射也被 Schema 约束住。从自主性判据看，它更像"LLM 增强的工具调用"，您说它是中台功能能力，我不反驳。
>
> 但它和纯后端接口有一个本质差别：**表单约束的是输入，不是执行。** 执行环节里模型真正在做决策的地方是：100+ 字段的映射消歧、跨字段语义冲突的处理、某一步失败后的重新规划（Plan-Execute 的 replan）、以及回滚决策。这些规则硬编码就是规则爆炸——我当时对比 if-else / 纯 Prompt / Function Calling 三个方案后选的 Function Calling，依据就在这里。所以准确的说法是：输入自主性为零（产品选择），执行自主性中等（模型处理长尾）——它不全是 Agent，但也不是纯接口。
>
> 第二层，这个项目里真正有自主性的部分在哪：任务编排层。④ 任务管理框架的"指令式交互"——用户自然语言表达"把这批客户的活动物料都迁移并生成百看卡"，系统解析意图、分解任务节点、按依赖调度——这才是规划性所在。再到产品化后的 AI 品专，按每个用户实时意图组装内容，那是完整的营销 Agent。所以自主性在这个项目里是分层的：迁移层在自动化端，编排层和品专层在 Agent 端。当时我们笼统地叫 Agent，现在我能把每一段的自主性强度说清楚。
>
> 第三层，为什么输入自主性低是个设计决策，而不是能力缺失。B 端批量迁移错一条就是投放事故，代价远高于多填一个表单——自主性和可靠性是一对 trade-off，我当时选了可靠性。代价我也清楚：灵活性差，场景扩展要改表单。所以反刍后的升级路径是：保留表单做存量场景，建 query 评测集兜底，再逐步放开自由输入——**放开多少自主性，取决于你有多强的评测兜底**。这个公式是我从这个项目带走的最重要的东西。
>
> 简历上叫不叫 Agent：公司立项名和产品形态就叫 Agent，但我面试时一定主动把自主性分层讲清楚，就像刚才这样。如果您觉得"Agent"这个词被业界用宽了，我同意——这也是我后来学评测体系之后，才有能力做这种精确表达的原因。

```text
自主性分层（这个项目里的 Agent-ness 分层，可复用的分析框架）：
├── 输入自主性：零（固定表单，产品层约束）
├── 执行自主性：中（LLM 处理长尾映射、失败重规划、回滚决策）
├── 编排自主性：高（指令式交互 → 任务分解 → 依赖调度）
└── 产品化后：AI 品专 = 完整营销 Agent（按意图实时组装）
```

**Q11：那为什么不一开始就做自由输入 + 评测集？**

> 资源约束和业务节奏：评测集建设需要时间和样本积累，业务要先把 462 家存量客户跑起来（渐进式投资原则）。先用表单换确定性上线，再补评测换灵活性——这是"先验证业务价值，再投入能力建设"的路径。反过来先建评测再做产品，业务等不起。

**Q12：你负责的整条链路是什么？迁移模块和营销 Agent 是什么关系？**

> 品牌广告投放平台的智能助手是营销 Agent 入口——支持回答各种问题 + 智能执行营销操作。我负责的是其中迁移这条链路：智能助手 → 选择迁移 → 输入必填字段 → 执行迁移 → 返回结果，从入口接入到结果返回整条链路由我完成。迁移是营销 Agent 背后众多业务平台中的一个能力节点：Agent 是入口层（意图 + 编排），各业务平台是能力层，各自有功能与链路。我做的迁移节点贡献"品专 → 百看"这条链路，通过标准化 tool schema 接入入口。这个位置让我看清了两点：①Agent 的价值在编排层，随工具数增长——一个工具时像功能，N 个工具时编排本身才是 Agent；②评测必须分层（平台断言 / 入口 query / 编排任务级），否则跨层归因无解。

## 六、深度 Q&A

**Q1: Function Calling 和 API 调用有什么区别？**

A: API 调用是人写的代码调用 API。Function Calling 是**模型决定**要不要调用、调用哪个、填什么参数。关键区别在于"谁做的决定"——人决定 vs 模型决定。这回到了 Workflow vs Agent 的根本区分。

**Q2: Schema 设计得好不好怎么衡量？**

A: 两个核心指标：
1. **调用成功率**：模型能成功生成合法 Function Call 的比例。Schema 设计得好 → 模型不会生成不合法的参数
2. **参数准确率**：生成的参数中，真正正确的比例。这和 description 写得好不好直接相关

**Q3: Badcase 分类有什么方法论？**

A: 一个简单的框架：
```text
1. 收集足够多的 badcase（至少 50-100 个才能看到 pattern）
2. 先不急着归类，逐个读一遍，找感觉
3. 用"根因分析"归类（不是按表面现象，而是按根本原因）
   ❌ 表面分类："迁移失败"分为"API 报错"和"数据格式错"
   ✅ 根因分类："Schema 映射错误" vs "源数据质量问题" vs "平台规则冲突"
4. 按影响面排序（不是按数量，是按"修复这个类型能救回多少条"）
5. 优先修复影响面最大的那一类
```

**Q4: 你的 Agent 迁移成功率和人工迁移有什么区别？**

A: 假设人工迁移一个物料需要 5 分钟（300 秒），Agent 处理需要 10 秒。Agent 成功率是 92%，意味着：
- 92% 的物料完全自动化，每个 10 秒
- 8% 失败后人工兜底，每个仍 300 秒
- 单物料平均耗时：0.92×10 + 0.08×300 ≈ 33 秒 → 效率提升约 9 倍

但关键不是"快了多少"，而是：**8% 的失败 case 是持续优化的素材**。每次优化提升 1% 的成功率，乘以物料总量，就是巨大的效率收益。
