## 一、核心认知：现有评测缺的两块

```text
现有体系（已强）：
├── 分层故障域隔离（tests/ 秒级 + eval/ 分钟级）
├── Ground Truth 自动计算（SQL 直查，零人工标注）
├── Session 跨 run 对比（"这次改了路由，P2 通过率降了 6%"）
└── 7 维度指标拆分（拒绝单一通过率掩盖问题）

缺的两块：
├── ① 评测系统本身的稳定性验证（AA 校验思维）
│   → 现在"P2 降 6%"无法判断是真退化还是 LLM 随机波动
│   → 美团：AA 校验通过才读实验差异——先验无偏，再读差异
└── ② "能力 vs 稳定性"的判别指标（pass@k）
    → 现在只有单次通过率（≈ pass@1），无法区分
      "偶尔能对（方差问题，修 prompt）" vs "根本不会（能力缺失，加工具）"
```

## 二、动作 1：Baseline 双跑（AA 校验）——第一步做这个

### 怎么做

```bash
# eval/ 全量跑两遍 baseline（同代码、同数据、同配置）
python eval/run.py --session baseline-AA-1
python eval/run.py --session baseline-AA-2

# 对比两遍结果，生成稳定性报告
```

### 报告内容（每个 case 的通过/失败一致性）

```text
稳定性报告字段：
├── case 级一致率：两遍结果相同的 case 占比
│   └── P0 层（无 LLM）应 = 100%（确定性代码，不一致就是评测 bug）
│   └── P1/P2 层（有 LLM）允许波动，阈值建议 ≤ 10%
├── 通过率波动：P4 7 维度指标的 run 间差值
└── 失败集合差异：两遍失败的 case 是否同一批
    ├── 是 → 稳定失败（真实问题）
    └── 否 → 随机失败（LLM 波动，需要多跑取众数）
```

### 判定标准与后续用法

```text
建立基线波动带：
├── 每层通过率的 run 间波动（如 P2: 94% ± 4%）
├── 之后每次实验：差异 > 波动带 → 真信号，值得归因
│              差异 < 波动带 → 噪声，不折腾
└── 面试说法："我给评测体系加了 AA 校验——先量化评测系统
    自身的波动，再读实验差异，避免把 LLM 随机性当能力变化"
```

### 工程实现提示

```text
├── 复用现有 Session 机制：两遍 = 两个 session，P4 报告天然可对比
├── 稳定性报告脚本：parse 两个 session 的 JSON 结果，算一致率矩阵
├── 成本：全量 166 case × 2 = 332 次运行，分钟级（可接受，发版前跑）
└── 关键：双跑必须在同代码同配置下，否则测的不是稳定性
```

## 三、动作 2：Trace 指标体系（含 pass@k）

### 为什么 trace 里要有指标

现有 trace 是"数据采集 + 质量评分"视角（M6），缺"评测指标"视角。trace 的 17 种事件已经记录了全部过程数据——指标只是对这些数据做统计，**零额外采集成本**。

### 指标体系（三层设计，每个指标配改进动作）

```text
① 结果层（任务级——判断"做没做到"）
├── pass@1：单次运行任务成功率（≈ 现有 eval 通过率）
├── pass@k：同一 case 跑 k 次，至少一次成功的概率
│   ├── 数学：pass@k = 1 - C(n-c, k) / C(n, k)（n=采样次数，c=成功数）
│   └── 无偏估计器（Chen et al. Codex 论文），k 通常取 3/5
├── 完成率方差：同一 case 多次运行的通过率波动
└── 用户采纳率：推荐被接受的比例（真实场景指标，demo 阶段可先不做）

② 过程层（会话级漏斗——判断"哪一步断了"）
├── 意图识别准确率（intent 事件 vs Ground Truth 标签）
├── 模式路由准确率（是否路由到最优执行模式）
├── 工具调用成功率（按工具分：检索命中率 / 对比完成率）
├── 无效/冗余工具调用率（效率：绕路次数）
└── 引导式购物漏斗（GREETING→SLOT_FILLING→SEARCHING→
    RECOMMENDING→FOLLOW_UP 每阶段完成率）

③ 稳定性层（评测系统本身——动作 1 的产物）
├── baseline 双跑一致率（AA 校验）
└── 失败归因分布：失败 case 的失败环节分布（哪层最脆弱）
```

### pass@k 在 price-agent 的正确用法（重点）

```text
pass@k 是"能力 vs 稳定性"的判别器：

pass@k 高 + pass@1 低 → 方差问题（能力有，不稳定）
    → 改进：修 prompt 确定性 / 温度 / 路由规则 / 增加验证兜底
pass@k 低 → 能力缺失（真的不会）
    → 改进：加工具 / 加知识库 / 加训练数据
pass@1 高 + pass@k 高 → 稳定强（理想态）

⚠️ 使用注意（搜索类 Agent 特有）：
├── "不成功"必须先归因：商品不存在 / 需求矛盾（P3 能力边界 case）
│   不是 agent 的错——计算 pass@k 前过滤"不可完成任务"，
│   否则分母被无解任务稀释
├── k 的取值：k=3 成本可控，k=5 更稳（按预算取舍）
└── 采样注意：pass@k 要求同一 case 重复采样，跑 k 次时
    温度固定（测能力）vs 温度变化（测鲁棒）是两种意图
```

### 落地方式

```text
├── 在 M6 工坊或独立脚本里加指标计算层（trace JSON 已够）
├── 输出：每 session 一份指标报告（结果层 + 过程层）
├── 困难集 case 自动跑 k 次统计 pass@k（见动作 3）
└── 面试说法："我给 trace 补了结果层指标——pass@k 区分
    '能力缺失'和'稳定性差'，失败归因分布告诉算法团队修哪里"
```

## 四、动作 3：困难集评测（难负样本思维）

### 做法

```text
挑 20 条"语义 Gap"query——词面不匹配但语义相关（3C 场景）：
├── "办公本" → 商务轻薄本（意图：按场景找）
├── "学生党" → 性价比机型（意图：按人群找）
├── "打游戏" → 游戏手机（意图：按用途找）
├── "续航王" → 大电池机型（意图：按卖点找）
└── 与美团案例同构："宠物 SPA+洗澡" ↔ "萌宠清洁护理套餐"

对每条 query 测三件事：
├── 意图路由是否命中正确模式（语义推荐 vs 查价 vs 对比）
├── 向量召回是否返回相关候选（检索命中率）
└── 推荐结果是否相关（用现有 LLM-Judge 或人工打标）
```

### 为什么有意义

```text
├── 普通 query（"小米15价格"）词面匹配就能过——测不出语义能力
├── 困难集是"语义能力"的定向体检——对应美团难负样本思维
│   （负样本/困难样本的判别力 > 随机样本）
├── 困难集还顺带驱动 pass@k：20 条 × k=3 次，看语义能力上限
└── 面试说法："我建了 20 条语义 Gap 困难集，定向测向量召回的
    跨词面匹配能力——词面零重叠但语义相关的场景"
```

## 五、动作 4：覆盖率统计

### 做法

```text
对评测 query 集合（全量 + 困难集）统计：
├── query 语义覆盖率：多少 query 的向量召回能返回非空候选
│   （兜底率——向量召回失效时规则能否接住）
├── 工具调用覆盖率：各工具被调用的 query 占比
└── 候选充足率：返回候选数 < N 的 query 占比（检索稀疏预警）
```

### 为什么有意义

```text
├── 美团三期第一道关卡就是覆盖率（73.61% → 89.81%）
│   "复用 ≠ 直接可用"——你的向量召回对冷门 query 的兜底
│   能力必须量化，否则不知道边界在哪
├── 覆盖率低 → 加规则兜底 / 扩充商品知识 / 调 embedding
└── 面试说法："我给评测加了覆盖率维度——多少 query 能拿到
    有效候选，量化语义召回的兜底边界"
```
