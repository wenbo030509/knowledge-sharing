# 心法（一）"算法"这个岗位的定义和理解

## 图片内容（11 张连续总结，按顺序忠实还原）

面了一家公司，这个技术负责人有很多有意思的 insights，但是有一个感觉特别有意思，我称之为其大概为是什么"做算法定义"，下面我放一些总结的内容。

说话人１对"算法岗位"的理解其实非常明确，而且不是传统意义上的"会训练模型、会复现论文的人"。他的核心定义可以浓缩成一句话：

> 算法工程师的价值，不在于"做算法相关的工作"，而在于能够持续发现值得研究的问题，并通过算法研究创造出明显且具有稀缺性的业务/技术价值。

我把他的完整逻辑拆成几个层次。

### 1. 算法岗不是"纯研究"，而是「深入应用 + 算法研究」

在他的团队里，算法工程师首先必须真正参与业务和 Agent 开发。他特别强调："必须得懂 agent 开发，并且要亲自做，做得很深才行，否则提出来的改进方法可能都是空中楼阁。"

原因是，如果没有深入真实系统，你甚至不知道：
- 真正的问题是什么；
- 哪些问题值得解决；
- 当前方法为什么失败；
- 算法究竟应该优化什么。

所以这里的研究不是脱离业务的 academic research，而更接近：

> 深入系统 → 发现问题 → 抽象问题 → 调研/实验 → 提出算法方案 → 回到真实系统验证价值。

这也是他与"纯论文研究岗位"的一个明显区别。

### 2. 算法岗和应用开发岗最大的区别是：必须具有"研究能力"

他认为随着 AI Coding、基础模型能力不断增强，很多过去所谓的"算法工作"正在迅速工程化、商品化。例如：调 API、Agent workflow、普通模型微调、参数配置、论文代码调用、常规工程实现，未来应用开发工程师一样可以完成。

所以："会用算法"已经不足以证明你是算法工程师。

- 应用开发岗更倾向于：把已有技术高效地做成产品。
- 算法岗除了同样要能开发之外，还多了一层：面对现有技术无法很好解决的问题，能够进行研究。

因此他的算法岗实际上更像：**Research Engineer / Applied Researcher**，而不是传统 ML Engineer。

### 3. "复现论文"只是研究过程中的副产物，不是工作目标

这是他说得非常清楚的一点。他并不认可"这周找一篇论文 → 复现论文 → 汇报效果"这种工作模式。他说："我们不会设定一个目标说复现一下论文。"

论文复现只是为了解决某个问题而进行调研、验证时，自然需要完成的步骤。真正的目标始终是：解决公司的核心问题。

因此顺序不是：Paper → 找业务场景；而应该是：Problem → 找方法 → Paper/实验 → Solution。这是很典型的 Problem-driven Research。

### 4. 现实问题比 Paper Benchmark 更重要，也往往更复杂

他说了一个很值得注意的观点："现实中的很多课题，我觉得比很多复现 paper 要复杂得多。"

因为论文为了进行科学实验，通常会主动约束问题：数据分布固定、benchmark 固定、metric 固定、假设固定、环境相对理想。而现实业务问题可能同时存在：数据质量问题、用户行为变化、系统工程约束、latency/cost、模型能力边界、长尾 case、上下游系统问题。

因此，他认为优秀算法工程师的能力不是单纯"这个 SOTA 算法我会不会？"，而是：**面对一个混乱、没有标准答案的问题，我能不能找到真正有效的解决路径？**

### 5. 他特别看重"选什么问题"，甚至高于"怎么解决问题"

这是整段访谈里非常重要的一句话："你为什么选择做这件事情，往往比你怎么做这件事情还重要。"

也就是说，他要求算法工程师不仅是执行者，还要具有一定程度的技术判断力 + Research Taste。包括判断：
- 哪个问题值得投入？
- 哪个问题只是短期工程问题？
- 哪个方向半年后可能会被基础模型直接解决？
- 哪种技术可能形成长期优势？
- 哪个课题值得公司投入 GPU、时间和人力？

甚至很多"核心问题"并不是老板直接安排，研究者自己应该能够提出问题，然后团队再讨论这个问题是否值得投入。这已经比普通算法工程师的要求高一层，本质上有一点 Research Scientist + Tech Lead 的早期能力要求。

### 6. 算法研究最终不是为了论文，而是为了"改变产品甚至公司的竞争力"

他把算法价值分成了几个层次：
- 最低层：完成任务。
- 再上一层：提高效率。
- 更高层：解决重要业务问题。
- 最高层：通过技术/算法布局，让产品甚至公司的竞争格局发生变化。

他说得很直接："什么样的技术、算法布局，或者未来技术投入，能够给产品、技术，最好最终给公司在未来竞争格局中带来比较大的变化，这个才是根本。"

因此他真正希望算法岗追求的是**技术杠杆**，不是"我优化了一个 pipeline，节省 20% 时间"，而更希望出现："因为这个算法/能力，我们能够做以前做不了的产品。"

### 7. 他认为"完成工作"只是算法岗最低要求

他说了一句非常能体现招聘标准的话："如果只是完成工作，那其实是很低的一个要求。"

因为在 AI Native 时代，很多过去需要专业岗位完成的工作，很快都会大众化。他的判断是：今天某个技能可能还能创造价值，但半年以后可能人人都会。

所以他区分了两个东西：**岗位价值 与 个人价值**。公司设立一个算法岗位，本身证明这个领域有价值；但一个人真正有价值，则应该是：因为"是这个人"，才额外创造了某种价值。这就是他说的："这个价值某种程度上是因为他才创造出来的，而不仅仅是说有这个岗位就能创造出来。"这其实是他整个算法人才观最核心的一句话之一。

### 8. 在他看来，算法工程师最重要的能力已经不是具体技术，而是"持续学习"

他说："所有当下已经掌握的技术，不管多先进，很快都会变成大路货。"所以算法岗位真正长期有效的能力是：**持续学习能力 + 好奇心 + 研究兴趣 + 判断力**。

具体技术，比如 DPO、GRPO、Agent、RAG、LoRA、Diffusion、某篇 SOTA Paper，都有"保鲜期"。今天可能稀缺，半年以后可能 Cursor/Claude/开源框架直接帮你完成。

所以他实际上把算法工程师看成了一个：持续吸收新技术，并不断寻找下一代技术机会的人，而不是掌握一个固定技术栈的人。

### 9. 他对算力资源的态度，也反映了他的算法观

你问 GPU 时，他其实给出了一个很典型的管理者视角："不是因为没有卡，所以好项目没办法做；很多时候可能是因为这个事情不值得做，所以没有必要给它卡。"

换句话说：算法工程师不应该首先问"我有多少 GPU？"，而应该首先证明"这个问题为什么值得投入 GPU？"。如果真的能够产生巨大价值，公司通常会去申请云资源。

所以他认为：**计算资源不是核心约束，研究问题的价值判断才是核心约束**。这与前面的"为什么做，比怎么做更重要"是完全一致的。

### 最后：把他的算法岗位画像压缩成一个公式

我认为可以这样概括：

> **算法工程师 = 深度业务/Agent 能力 + 算法研究能力 + 问题发现能力 + 技术判断力 + 快速学习能力 + 实证能力。**

而不是：算法工程师 = 会训练模型 + 会看论文 + 会复现代码。

如果进一步用他自己的思想划分（层级 → 在他眼中的价值）：

| 层级 | 在他眼中的价值 |
|---|---|
| 会调用现成算法 | 很快会商品化 |
| 能完成算法任务 | 算法岗最低要求 |
| 能复现论文 | 研究过程中的基本能力 |
| 能解决复杂现实问题 | 合格算法工程师 |
| 能主动发现值得研究的问题 | 优秀算法工程师 |
| 能判断未来技术机会 | 高阶算法人才 |
| 能通过算法改变产品/公司竞争力 | 他真正理想的算法人才 |

所以你之前跟他说自己希望做"应用型算法"，其实和他的需求并不冲突。但这里有一个很重要的差别：
- 你表达的"应用型算法"更接近：学习业界前沿方法 → 借鉴大厂经过验证的方法 → 应用到业务。
- 而他想要的更进一步：深入业务 → 使用已有方法 → 发现已有方法解决不了的问题 → 自己研究 → 形成新的解决方案。

也就是说，他并不是希望你成为"纯论文 Scientist"，但也不希望你停留在 Algorithm User。他真正希望的人是：**一个能够从 Algorithm User 逐渐成长为 Algorithm Researcher 的 Applied Research Engineer。** 这可能是你理解这个岗位时最关键的一点。
