## 一、文章在讲什么（30 秒版本）

Anthropic 官方发布的 Agent 评测方法论。核心论点：**让 Agent 变得有用的那些能力（自主性、灵活性、多轮交互），也正是让它们难以被评测的原因。** 文章给出了经过真实部署验证的评测框架——三种评分器、8 步构建路线图、针对 4 种 Agent 类型的评测方法。

## 二、10 个面试可用的核心观点

### 观点 1：Agent 评测的三个核心组件

```text
Task（任务）+ Trial（试验）+ Grader（评分器）= 一个完整的 Eval

任务：有明确输入和成功标准的单个测试
试验：每次运行是一次试验，因为模型输出有随机性，需要多次试验
评分器：对 Agent 表现评分的逻辑——可以多个评分器评同一个任务
```

**面试说法：** "Agent 评测不是跑一次看对不对，而是每个任务多次试验、多个评分器多维度打分。因为 Agent 的非确定性意味着单次结果不能代表真实能力。"

---

### 观点 2：三种评分器的选择策略

| 评分器类型 | 怎么做 | 什么时候用 | 优劣 |
|-----------|--------|----------|------|
| **基于代码** | 字符串匹配、单元测试、静态分析、状态检查 | 有明确对错答案的任务 | 快、便宜、确定、可复现 |
| **基于模型** | LLM 按评分标准打分、自然语言断言、成对比较 | 开放式任务、需要判断质量 | 灵活、能捕捉细微差别，但非确定、更贵 |
| **人工** | 专家评审、众包、A/B 测试 | 主观性最强的任务、校准 LLM 评分器 | 黄金标准，但贵、慢、不可规模化 |

**面试说法：** "我的原则是——能用代码就代码，代码搞不定的上 LLM 裁判，LLM 也搞不定的才上人。三层的选择逻辑和我之前做数据质检时的 Cascading Classification 是一样的。"

---

### 观点 3：能力评测 vs 回归评测

```text
能力评测（Capability Eval）          回归评测（Regression Eval）
──────────────────────────────────────────────────────────
问："Agent 擅长做什么？"              问："Agent 还能做以前能做的事吗？"
通过率应该低（否则没区分度）          通过率应该接近 100%
目标：攀登，提升能力                   目标：防守，防止退步
高通过率的任务 → 毕业进入回归套件      持续运行，分数下降 = 出问题了
```

**面试说法：** "评测分攻和守。能力评测是攻——设计困难任务来拉动模型能力上限。回归评测是守——确保每次改动不破坏已有能力。我质检项目里'新增规则'就是能力评测，'稳定规则纳入常规检查'就是回归评测。"

---

### 观点 4：非确定性——Agent 评测中最容易被忽视的挑战

```text
Agent 在不同运行中行为会变化——同一个任务，这次通过下次可能失败。

两个关键指标：
├── pass@k：k 次尝试中至少成功一次的概率
│   └── k 越大分数越高。一次成功就够的场景（如头脑风暴）
└── pass^k：k 次尝试全部成功的概率
    └── k 越大分数越低。每次都必须可靠的场景（如面向客户的 Agent）
```

**面试说法：** "评测 Agent 必须考虑非确定性。如果一个任务只有 75% 的单次成功率，跑 3 次全部成功的概率只有 42%。面向客户的 Agent 必须看 pass^k，因为用户每次都需要可靠的结果，不是'你多试几次总有一次对的'。"

---

### 观点 5：评分应该针对成果，不是路径

这是全文最重要的设计原则：

> "不要检查 Agent 是否遵循了特定的步骤序列。Agent 经常找到评测设计者预料之外的有效方法。Opus 4.5 在 τ2-bench 中按评测标准'失败'了，但实际上它发现了评测策略的漏洞，给用户找到了更好的解决方案。"

**面试说法：** "好的评测不限制 Agent 怎么达成目标，只验证最终成果对不对。如果评分规则太僵化，会惩罚创造力——你会得到一个'只会按规矩办事'的 Agent，而不是'能创造性解决问题'的 Agent。"

---

### 观点 6：部分得分——好的评测不是二元的

```text
对有多步骤的任务，用部分得分替代二元通过/失败。

举例：一个客服 Agent
├── 正确识别问题 + 验证客户信息 → 得部分分（不是零分）
├── 但未能完成退款操作
└── 这明显比"立即失败"好 → 评分应该反映这个连续谱
```

**面试说法（直接连接你的经验）：** "我做 CoT 数据质检时，不合格数据不是直接废弃，而是分了二级——needs_repair 和 discarded。这其实就是部分得分的思路：needs_repair 的数据有修复价值，不应该和直接废弃的混为一谈。评测也是一样——部分得分让你看到进步的梯度。"

---

### 观点 7：评测驱动开发的 8 步路线图

```text
0. 尽早开始（20-50 个任务就够）
1. 从你已经手动测试的内容开始
2. 编写明确的任务 + 参考解决方案
3. 构建平衡的问题集（正例 + 反例）
4. 构建稳健的评测框架 + 隔离环境
5. 精心设计评分器
6. 检查记录（读 Transcript！）
7. 监控评测是否饱和（100% 通过率的评测不给改进信号）
8. 通过开放贡献保持评测套件长期健康
```

**面试说法：** "Anthropic 的实践表明，评测不需要一上来就几百个任务。20-50 个从真实失败场景中抽取的任务就足够起步了。关键不是数量，是——任务规范是否明确？评分器是否公平？是否定期读 Transcript 来验证评分的有效性？"

---

### 观点 8：评测饱和——100% 通过率的陷阱

```text
评测饱和（Eval Saturation）：Agent 通过所有可解任务，没有改进空间。

危险性：
├── 大幅能力提升会被掩盖为微小分数增长
├── SWE-bench Verified 一年从 30% 涨到 80%+ → 前沿模型的提升开始"看不出"
└── 需要不断引入更难的任务来维持评测的区分度
```

**面试说法：** "一个好的评测套件需要定期更新。当某个任务的通过率接近 100%，它就毕业进入回归测试，同时引入更难的任务来维持能力评测的区分度。如果评测一直满分，你其实不知道 Agent 是不是真的变强了。"

---

### 观点 9：评测通过套件的平衡设计——类别不平衡的陷阱

```text
只测试"应该做什么"→ 得到一个什么都做的 Agent
只测试"不应该做什么"→ 得到一个什么都不做的 Agent

必须双向覆盖。Anthropic 在为 Claude.ai 构建搜索评测时亲身体验：
├── 既要测"该搜索时有没有搜"（避免漏搜）
└── 也要测"不该搜索时有没有搜"（避免过度搜索）
两个方向的平衡需要多轮迭代打磨。
```

**面试说法：** "评测最隐蔽的陷阱是类别不平衡。如果你只测 Agent 应该做某事的 case，你会得到一个过度积极的 Agent；只测不该做的 case，你会得到一个过度保守的 Agent。这和我做黑盒 20% 配比时的思路一致——样本分布必须均衡。"

---

### 观点 10：评测是产品和研究之间最高带宽的沟通渠道

```text
评测不只是测试工具——它是团队的沟通语言。

├── 对产品团队：评测强制明确"什么是成功"
├── 对研究团队：评测定义了可以优化的指标
└── 对新模型发布：有评测的团队几天内完成升级，没评测的团队需要几周
```

**面试说法：** "评测的价值不只是找 bug。它让产品、算法、工程三个团队有了同一套语言——不再是'Agent 感觉变差了'，而是'回归套件通过率从 97% 掉到 89%，我们定位到是因为去重策略改了导致某类数据被误过滤'。"

## 三、3 个面试可以直接讲的故事

### 故事 1：我的 CoT 质检项目就是一个 Eval System

```text
背景：我在字节跳动负责 Pretrain Eval Set 的数据质量保证。

和文章框架的对应：
├── 任务（Task）       = 每条 CoT 数据是一个测试用例
├── 评分器（Grader）    = 我的 5 层 Gate（格式/内容/一致性/修复/标签）
│   ├── Gate 1-2：基于代码的评分器（确定性规则）
│   ├── Gate 3（LLM Repair）：基于模型的评分器（LLM 判断 CoT 质量）
│   └── Gate 4（人工仲裁）：人工评分器（校准前几层的准确性）
├── 部分得分           = 三级分类：qualified / needs_repair / discarded
├── 评测平衡           = 黑盒 20% 配比确保各学科分布均衡
└── 结果               = 5497 条数据 → 4346 条合格（79.06%）

我学到的最重要的事：
"不要对路径评分，要对成果评分"——我的标签纠错 Pipeline 没有强制
人工审核每一条，而是只在算法标签和我的标签不一致时才介入。
这就是"用最便宜的方案处理尽可能多的 case"。
```

### 故事 2：我理解的 Agent 评测的关键挑战（从文章推导）

```text
如果让我来设计一个 Agent 产品的评测体系，我会关注三个核心挑战：

挑战一：非确定性的处理
同一个任务，Agent 这次答对下次可能答错。我的做法是：
- 每个任务至少跑 3 次试验
- 同时报告 pass@1 和 pass@3
- 对于面向用户的场景，看 pass^k（所有试验都通过才算通过）

挑战二：评分器的选择
不是所有维度都适合自动化。我的分层策略：
- 任务完成度（结果对不对）→ 确定性评分（单元测试、状态检查）
- 过程质量（做得好不好）→ LLM 评分标准（代码质量、交互效率）
- 主观体验（用户觉得好不好）→ 人工抽检 + 定期校准

挑战三：评测的长期维护
评测套件不是一次性的。我的做法是：
- 能力评测通过率 > 90% → 毕业进入回归套件
- 定期引入更难的任务维持区分度
- 每两周读一次失败 case 的 Transcript，验证评分器是否公平
```

### 故事 3：如果我做 Agent 评测 Pipeline 项目

```text
「这是连接自驱项目一的面试故事」

我基于 Anthropic 的评测方法论，独立设计了一个 Agent 能力评测 Pipeline。

设计决策：

1. 评分器组合
├── 代码评分器：单元测试验证生成代码的正确性
├── LLM 评分标准：评估代码质量、指令遵循度
└── 状态检查：验证任务完成后的环境状态

2. 非确定性处理
├── 每个任务跑 3 次试验
├── 报告 pass@1（首次成功率）
└── 分析失败 case 的 Transcript，区分"模型能力不足"和"评分器设计问题"

3. 评测维度（5 个维度，0-3 分制）
├── 任务完成度：最终结果是否满足需求？
├── 过程效率：几次交互完成任务？
├── 指令跟随：有没有做我没说的事？
├── 错误恢复：出错后能自己发现并修复吗？
└── 代码规范：生成的代码能直接运行吗？

4. 评测套件设计
├── 10 个真实场景任务（数据处理、代码生成、Debug 各占比均衡）
├── 正例（模型应该做对的）+ 反例（模型容易做错的）
└── 每个任务附带参考解决方案（验证任务本身是可解的）

我会在 GitHub 上展示这个项目，包含：
- 完整的评测代码
- 10 个测试用例及其评分标准
- 一份评测分析报告（包含 pass@1 和各维度得分分布）
```

| Grader | 评分器 | 描述评分逻辑 |

## 六、对你的自驱项目一的直接指导

基于本文，项目一的评测框架应该包含：

```text
agent-eval-pipeline/
├── tasks/                     ← 测试用例集（20 个任务起步）
│   ├── data_processing/       ← 数据处理任务
│   ├── code_generation/       ← 代码生成任务
│   └── debugging/             ← Debug 任务
├── graders/                   ← 评分器
│   ├── code_grader.py         ← 基于代码的（运行测试、状态检查）
│   ├── llm_grader.py          ← 基于模型的（评分标准打分）
│   └── rubric.md              ← 评分标准文档（每个维度 0-3 分）
├── harness.py                 ← 评测框架（运行试验、收集 Transcript）
├── report.py                  ← 报告生成（pass@1、各维度统计）
└── README.md                  ← 方法论说明 + 分析结论
```

**每个任务的设计模板（参考文章的两个示例）：**

```yaml
task:
  id: "data_clean_01"
  desc: "清洗一个有缺失值和异常值的 CSV，输出统计报告"
  graders:
    - type: deterministic    # 代码评分器：输出 CSV 格式正确、统计数字准确
    - type: llm_rubric       # LLM 评分器：代码风格、错误处理
    - type: state_check      # 状态检查：输出文件存在、行数正确
  tracked_metrics:
    - n_turns               # 几轮交互完成
    - n_total_tokens        # Token 消耗
    - time_to_complete      # 总耗时
```
