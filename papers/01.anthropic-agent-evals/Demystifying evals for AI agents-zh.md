# 揭秘 AI Agent 评测

让 Agent 变得有用的那些能力，也正是让它们难以被评测的原因。经过各类部署场景验证的策略，需要将多种技术组合起来，才能匹配所测量系统的复杂度。

## 引言

好的评测能让团队更有信心地交付 AI Agent。没有评测，团队很容易陷入被动循环——只在线上发现问题，修复一个故障又引发另一个。评测让问题和行为变化在影响用户之前就显现出来，其价值会在 Agent 的整个生命周期中持续累积。

正如我们在[《构建有效的 Agent》](https://www.anthropic.com/engineering/building-effective-agents)中所描述的，Agent 跨多轮运行：调用工具、修改状态、基于中间结果自我调整。正是这些让 AI Agent 有用的能力——自主性、智能性和灵活性——也让它们更难被评测。

通过与客户在 Agent 开发前沿的合作以及我们内部的实践，我们学会了如何为 Agent 设计更严谨、更有用的评测方法。以下是在真实部署场景中，跨多种 Agent 架构和用例行之有效的经验。

## 评测的结构

**评测**（Evaluation，简称 Eval）是对 AI 系统的测试：给定一个输入，对输出应用评分逻辑来衡量成功与否。本文重点讨论可在开发阶段运行、无需真实用户参与的**自动化评测**。

**单轮评测**很简单：一个提示词、一个回复、一套评分逻辑。对早期的 LLM 而言，单轮、非 Agent 式的评测是主要评估方法。随着 AI 能力的进步，**多轮评测**变得越来越普遍。

在一个简单评测中，Agent 处理一个提示词，评分器检查输出是否符合预期。对于更复杂的多轮评测，一个编程 Agent 会收到工具、一个任务（本例中是构建 MCP 服务器）和一个环境，执行"Agent 循环"（工具调用和推理），并将实现更新到环境中。评分则通过单元测试来验证 MCP 服务器是否正常工作。

**Agent 评测**更为复杂。Agent 跨越多轮使用工具，在环境中修改状态并持续适应——这意味着错误会传播和叠加。前沿模型还可能找到超越静态评测限制的创造性解决方案。例如，Opus 4.5 在解决 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 中一个关于预订航班的问题时，[发现了](https://www.anthropic.com/news/claude-opus-4-5)策略中的一个漏洞。按照评测标准它"失败"了，但实际上它为用户找到了更好的解决方案。

在构建 Agent 评测时，我们使用以下定义：

* **任务**（Task，也称**问题**或**测试用例**）是具有明确输入和成功标准的单个测试。
* 每次对任务的尝试称为一次**试验**（Trial）。由于模型输出在不同运行之间存在差异，我们会运行多次试验以获得更一致的结果。
* **评分器**（Grader）是对 Agent 表现的某一方面进行评分的逻辑。一个任务可以有多个评分器，每个评分器包含多个断言（有时称为**检查**）。
* **记录**（Transcript，也称**轨迹**或**执行轨迹**）是单次试验的完整记录，包括输出、工具调用、推理过程、中间结果以及其他所有交互。对于 Anthropic API，这是评测运行结束时完整的消息数组——包含评测期间对 API 的所有调用及所有返回的回复。
* **结果**（Outcome）是试验结束时环境中的最终状态。一个订票 Agent 可能在记录末尾说"您的航班已预订"，但结果取决于环境的 SQL 数据库中是否存在预订记录。
* **评测框架**（Evaluation Harness）是端到端运行评测的基础设施。它提供指令和工具，并发运行任务，记录所有步骤，评分输出，并汇总结果。
* **Agent 脚手架**（Agent Harness / Scaffold）是让模型能够作为 Agent 运行的系统：处理输入，编排工具调用，返回结果。当我们评测"一个 Agent"时，我们评测的是脚手架*和*模型的协同工作。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的 Agent 脚手架，我们通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用其核心原语来构建我们的[长运行 Agent 脚手架](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
* **评测套件**（Evaluation Suite）是为衡量特定能力或行为而设计的一组任务集合。套件中的任务通常共享一个宏观目标。例如，客户支持评测套件可能测试退款、取消和升级等场景。

Agent 评测的组成部分。

## 为什么要构建评测？

团队刚开始构建 Agent 时，通过手动测试、[内部试用](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和直觉的组合，可以走得比预期更远。更严格的评测甚至看起来像是拖慢发布的额外开销。但过了早期的原型阶段，当 Agent 上线并开始规模化后，没有评测的开发方式就会崩溃。

崩溃点通常出现在用户报告 Agent 在改动后感觉变差了，而团队"盲目飞行"，除了猜测和逐一检查外无法验证。缺乏评测时，调试是被动的：等待投诉，手动复现，修复 Bug，然后祈祷没有其他回归。团队无法区分真正的回归和噪声，无法在发布前对数百个场景自动测试变更，也无法衡量改进。

我们多次看到这一过程的上演。例如，Claude Code 最初基于 Anthropic 员工和外部用户的反馈快速迭代。后来，我们加入了评测——先是针对简洁性、文件编辑等狭窄领域，然后是过度工程化等更复杂的行为。这些评测帮助发现问题、指导改进、聚焦研究与产品的协作。结合生产监控、A/B 测试、用户研究等多种手段，评测为 Claude Code 在规模化过程中持续改进提供了信号。

编写评测在 Agent 生命周期的任何阶段都有价值。早期，评测强制产品团队明确 Agent 的成功定义；后期，则帮助维持一致的质量标准。

[Descript](https://www.descript.com/) 的 Agent 帮助用户编辑视频，因此他们围绕成功编辑工作流的三个维度构建评测：不搞破坏、按指令执行、执行出色。他们从手动评分演进到由产品团队定义标准并进行定期人工校准的 LLM 评分器，现在定期运行两套独立的套件，分别用于质量基准测试和回归测试。[Bolt](https://bolt.new/) AI 团队在拥有广泛使用的 Agent 之后才开始构建评测。在 3 个月内，他们构建了一个评测系统，通过静态分析运行 Agent 并对输出进行评分，使用浏览器 Agent 测试应用，并使用 LLM 裁判评估指令遵循等行为。

有些团队在开发之初就创建评测；另一些团队则在规模化后评测成为改进 Agent 的瓶颈时才添加。评测在 Agent 开发初期尤其有用，可以显式编码预期行为。两个工程师阅读同一份初始规格说明，可能对 AI 如何处理边缘情况有不同的理解。评测套件可以消除这种歧义。无论何时创建，评测都能加速开发。

评测还决定了你采纳新模型的速度。当更强大的模型出现时，没有评测的团队需要数周测试，而有评测的竞争对手可以快速确定模型的优势、调整提示词，并在几天内完成升级。

有了评测之后，基线和回归测试就是免费的：延迟、Token 使用量、单任务成本、错误率都可以在静态任务集上进行跟踪。评测还可以成为产品和研究团队之间带宽最高的沟通渠道，定义研究人员可以优化的指标。显然，评测的好处远远超出了跟踪回归和改进。其复利价值很容易被忽视，因为成本是立即可见的，而收益是逐渐累积的。

## 如何评测 AI Agent

我们今天看到几种常见类型的 Agent 在大规模部署，包括编程 Agent、研究 Agent、计算机操作 Agent 和对话 Agent。每种类型可能部署在各种各样的行业中，但它们可以使用类似的技术进行评测。你不需要从零发明评测方法。以下章节描述了针对几种 Agent 类型的成熟技术。以这些方法为基础，然后扩展到你的领域。

### Agent 评分器的类型

Agent 评测通常结合三种类型的评分器：基于代码的、基于模型的和人工的。每种评分器评估记录或结果的某一部分。有效评测设计的一个关键要素是为任务选择合适的评分器。

基于代码的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| - 字符串匹配检查（精确、正则、模糊等）<br>- 二元测试（fail-to-pass、pass-to-pass）<br>- 静态分析（lint、类型、安全）<br>- 结果验证<br>- 工具调用验证（使用的工具、参数）<br>- 记录分析（执行轮数、Token 使用量） | - 快速<br>- 廉价<br>- 客观<br>- 可复现<br>- 易于调试<br>- 可验证特定条件 | - 对不完全匹配预期模式的合法变体很脆弱<br>- 缺乏细粒度判断<br>- 对某些主观性任务评估能力有限 |

基于模型的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| - 基于评分标准的打分<br>- 自然语言断言<br>- 成对比较<br>- 基于参考的评估<br>- 多裁判共识 | - 灵活<br>- 可扩展<br>- 能捕捉细微差别<br>- 能处理开放式任务<br>- 能处理自由格式输出 | - 非确定性<br>- 比代码评分器成本更高<br>- 需要与人工评分者校准以保证准确性 |

人工评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| - 领域专家评审<br>- 众包判断<br>- 抽查采样<br>- A/B 测试<br>- 标注者间一致性 | - 金标准质量<br>- 符合专家用户判断<br>- 用于校准基于模型的评分器 | - 昂贵<br>- 慢<br>- 通常需要大规模获取人类专家 |

对于每个任务，评分可以是加权（综合评分必须达到阈值）、二元（所有评分器必须通过）或混合形式。

### 能力评测 vs 回归评测

**能力评测**（或"质量评测"）问的是"这个 Agent 擅长做什么？"它们的起始通过率应该很低，瞄准 Agent 有困难的任务，给团队一个明确的提升目标。

**回归评测**问的是"Agent 还能处理以前能处理的所有任务吗？"，应该有接近 100% 的通过率。它们防止能力退步，分数下降就意味着某些地方出了问题需要修复。当团队在能力评测上攀登提升时，同时运行回归评测以确保改动不会导致其他问题同样重要。

当 Agent 上线并优化后，通过率高的能力评测可以"毕业"成为回归套件，持续运行以检测任何漂移。那些曾经衡量"我们能做到这个吗？"的任务，现在衡量的是"我们还能可靠地做到这个吗？"

### 评测编程 Agent

**编程 Agent** 编写、测试和调试代码，像人类开发者一样浏览代码库并运行命令。现代编程 Agent 的有效评测通常依赖于明确的任务规范、稳定的测试环境以及对生成代码的全面测试。

确定性评分器天然适合编程 Agent，因为软件的评测通常很直观：代码能否运行？测试是否通过？两个广泛使用的编程 Agent 基准测试——[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)——都遵循这一方法。SWE-bench Verified 给 Agent 分配来自流行 Python 仓库的 GitHub Issue，通过运行测试套件来评分；只有在修复失败测试且不破坏现有测试的情况下，解决方案才算通过。LLM 在这项评测上仅用一年时间就从 40% 提升到了 80% 以上。Terminal-Bench 则走不同的路线：它测试端到端的技术任务，例如从源码构建 Linux 内核或训练 ML 模型。

一旦你有一套通过/不通过测试来验证编程任务的关键*结果*，通常对*记录*进行评分也很有用。例如，基于启发式规则的代码质量检查可以从更多维度而不仅仅是测试通过来评估生成代码，而具有清晰评分标准的基于模型的评分器可以评估 Agent 如何调用工具或与用户交互等行为。

**示例：编程 Agent 的理论评测**

考虑一个编程任务，Agent 必须修复一个身份验证绕过漏洞。如下面示例 YAML 文件所示，可以使用评分器和指标来评测这个 Agent。

```
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

请注意，此示例展示了完整的评分器类型范围以供说明。实际上，编程评测通常依赖单元测试来验证正确性，依赖 LLM 评分标准来评估整体代码质量，只有在需要时才添加额外的评分器和指标。

### 评测对话 Agent

**对话 Agent** 在支持、销售或辅导等领域与用户互动。与传统聊天机器人不同，它们维护状态、使用工具，并在对话过程中采取行动。虽然编程和研究 Agent 也可能涉及与用户的多轮交互，但对话 Agent 面临一个独特的挑战：交互质量本身就是你评测的一部分。对话 Agent 的有效评测通常依赖可验证的最终状态结果和能够捕捉任务完成度与交互质量的评分标准。与大多数其他评测不同，它们通常需要一个额外的 LLM 来模拟用户。我们在[对齐审计 Agent](https://alignment.anthropic.com/2025/automated-auditing/) 中使用这种方法，通过长时间的对抗性对话对模型进行压力测试。

对话 Agent 的成功可以是多维度的：工单是否解决（状态检查），是否在 10 轮内完成（记录约束），语气是否恰当（LLM 评分标准）？两个涵盖多维度评估的基准测试是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其继任者 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们模拟跨零售支持和航空预订等领域的多轮交互，一个模型扮演用户角色，Agent 在真实场景中导航操作。

**示例：对话 Agent 的理论评测**

考虑一个支持任务，Agent 必须为一位愤怒的客户处理退款。

```
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与编程 Agent 示例类似，这个任务展示了多种评分器类型以供说明。实际上，对话 Agent 评测通常使用基于模型的评分器来评估沟通质量和目标完成度，因为许多任务——比如回答问题——可能有多个"正确"的解决方案。

### 评测研究 Agent

**研究 Agent** 收集、综合和分析信息，然后产生答案或报告等输出。与编程 Agent 通过单元测试提供二元通过/失败信号不同，研究质量只能相对于任务来判断。什么算"全面"、"来源可靠"，甚至"正确"取决于上下文：市场扫描、收购尽职调查和科学报告各自需要不同的标准。

研究评测面临独特的挑战：专家可能对某个综合分析是否全面存在分歧，随着参考内容的不断变化基础事实会漂移，更长、更开放的输出也意味着更多的出错空间。像 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准测试，测试 AI Agent 能否在开放互联网的大海捞针中找到目标——问题是设计成容易验证但难以解决的。

构建研究 Agent 评测的一个策略是组合多种评分器类型。有据可查检查验证声明是否有检索到的来源支持；覆盖度检查定义好的答案必须包含的关键事实；来源质量检查确认所参考的来源是否权威，而不仅仅是第一个被检索到的。对于有客观正确答案的任务（如"X 公司 Q3 收入是多少？"），精确匹配即可。LLM 可以标记缺乏支撑的声明和覆盖度的缺口，同时也验证开放式综合分析的一致性和完整性。

鉴于研究质量的主观性，基于 LLM 的评分标准应经常与专家人工判断进行校准，以便有效评分。

### 计算机操作 Agent

**计算机操作 Agent** 通过与人类相同的界面——屏幕截图、鼠标点击、键盘输入和滚动——而非通过 API 或代码执行与软件交互。它们可以使用任何具有图形用户界面（GUI）的应用程序，从设计工具到遗留企业软件。评测需要在真实或沙盒环境中运行 Agent 使用软件应用，并检查是否达到了预期结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务，使用 URL 和页面状态检查验证 Agent 是否正确导航，同时对修改数据的任务进行后端状态验证（确认订单确实已下，而不仅仅是确认页面出现了）。[OSWorld](https://os-world.github.io/) 将这一方法扩展到完整的操作系统控制，通过评测脚本在任务完成后检查各种产物：文件系统状态、应用配置、数据库内容和 UI 元素属性。

浏览器操作 Agent 需要在 Token 效率与延迟之间取得平衡。基于 DOM 的交互执行快速但消耗大量 Token，而基于截图的交互较慢但 Token 效率更高。例如，让 Claude 总结维基百科时，从 DOM 提取文本效率更高；在亚马逊找新笔记本电脑壳时，截图更高效（因为提取整个 DOM 的 Token 开销很大）。在我们的 Claude for Chrome 产品中，我们开发了评测来检查 Agent 是否为每种上下文选择了合适的工具。这使我们能够更快、更准确地完成浏览器任务。

### 如何看待 Agent 评测中的非确定性

无论 Agent 类型如何，Agent 的行为在不同运行之间都会变化，这使得评测结果比表面看起来更难解读。每个任务有自己的成功率——可能在某个任务上是 90%，在另一个上是 50%——而且一次评测中通过的任务可能在下一次运行中就失败。有时我们需要衡量的是 Agent 为一个任务成功的*频率*（试验次数的多大比例）。

两个指标有助于捕捉这种细微差别：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量 Agent 在 *k* 次尝试中至少获得一个正确解的概率。随着 *k* 增加，pass@k 分数上升：更多的"射门次数"意味着至少 1 次成功的几率更高。50% 的 pass@1 意味着模型在第一次尝试中成功完成了评测中一半的任务。在编程领域，我们通常最关心 Agent 是否能在第一次尝试中找到解决方案——即 pass@1。在其他情况下，只要有一个可行，提出多个解决方案就是合理的。

[**pass^k**](https://arxiv.org/abs/2406.12045) 衡量*所有 k 次*试验都成功的概率。随着 *k* 增加，pass^k 下降，因为要求在更多试验中保持一致是更难跨越的门槛。如果你的 Agent 单次试验成功率为 75%，运行 3 次试验，全部通过的概率是 (0.75)³ ≈ 42%。这个指标对面向客户的 Agent 尤其重要，因为用户每次都期望可靠的行为。

pass@k 和 pass^k 随着试验次数增加而分道扬镳。在 k=1 时，二者相同（都等于单次试验成功率）。到 k=10 时，它们呈现出截然相反的情况：pass@k 趋近 100%，而 pass^k 趋近 0%。

两个指标都有用，使用哪个取决于产品需求：pass@k 适用于一次成功就足够的情况，pass^k 适用于一致性至关重要的 Agent。

## 从零到一：构建优秀 Agent 评测的路线图

本节提供我们经过实战检验的实用建议，帮助从没有评测到拥有可信赖的评测。把这看作评测驱动 Agent 开发的路线图：尽早定义成功，明确衡量成功，持续迭代。

### 为初始评测数据集收集任务

**第 0 步：尽早开始**

我们看到团队因为觉得需要数百个任务而推迟构建评测。实际上，20-50 个从真实失败场景中抽取的简单任务就足够了。毕竟，在 Agent 开发的早期，每次对系统的改动通常都有明显的影响，这种大效应量意味着小样本量就足够了。更成熟的 Agent 可能需要更大、更难的评测来检测更小的效应，但初期最好采用 80/20 法则。评测构建越拖延就越难。早期，产品需求自然会转化为测试用例。等太久，你就要从线上系统反向推导成功标准了。

**第 1 步：从你已经手动测试的内容开始**

从你在开发过程中运行的手动检查开始——每次发布前你验证的行为和最终用户尝试的常见任务。如果你已经上线，查看你的 Bug 追踪器和支持队列。将用户报告的失败转化为测试用例，确保你的套件反映真实使用情况；按用户影响优先级排列，帮助你把精力花在最有价值的地方。

**第 2 步：编写明确的任务并附带参考解决方案**

保证任务质量比看起来更难。一个好的任务是两位领域专家独立评估后会得出相同的通过/失败结论的任务。他们自己能通过这个任务吗？如果不能，任务就需要优化。任务规范的模糊性会成为指标中的噪声。基于模型的评分器的标准也是如此：模糊的评分标准产生不一致的判断。

每个任务应该能被正确遵循指令的 Agent 通过。这需要仔细考量。例如，审计 Terminal-Bench 时发现，如果一个任务要求 Agent 编写脚本但没有指定文件路径，而测试假定脚本在特定路径，Agent 可能并非自身原因而失败。评分器检查的所有内容都应该从任务描述中清楚可见；Agent 不应该因为模糊的规范而失败。对于前沿模型，多次试验中 0% 的通过率（即 0% pass@100）最常意味着任务本身有问题而非 Agent 能力不足，提示你需要仔细复查任务规范和评分器。对于每个任务，创建一个参考解决方案是很有用的：一个已知能通过所有评分器的工作输出。这证明了任务是可解决的，并验证了评分器配置正确。

**第 3 步：构建平衡的问题集**

既测试行为*应该*发生的情况，也测试*不应该*发生的情况。片面的评测会导致片面的优化。例如，如果你只测试 Agent 是否在应该搜索时进行搜索，你可能会得到一个几乎对所有事情都搜索的 Agent。尽量避免[类别不平衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评测。我们在为 [Claude.ai](http://claude.ai/redirect/website.v1.b62caaec-fcf2-4f06-8d93-1dc27b96dc46) 构建网络搜索评测时亲身经历了这一点。挑战在于防止模型在不应该搜索时进行搜索，同时保持其在适当情况下进行广泛研究的能力。团队构建了涵盖两个方向的评测：模型应该搜索的查询（如查找天气）和模型应该从现有知识回答的查询（如"苹果公司是谁创办的？"）。在未触发搜索（应该搜索时未搜索）和过度触发搜索（不应该搜索时搜索）之间找到恰当的平衡非常困难，需要多轮对提示词和评测的打磨。随着更多示例问题出现，我们持续添加到评测中以改进覆盖率。

### 设计评测框架和评分器

**第 4 步：构建稳健的评测框架和稳定的环境**

评测中的 Agent 功能必须与生产环境中使用的 Agent 大致相同，并且环境本身不应引入额外噪声。每次试验都应从干净的环境开始，做到"隔离"。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能导致因基础设施不稳定而非 Agent 性能问题引起的相关失败。共享状态还可能人为抬高表现。例如，在一些内部评测中，我们观察到 Claude 通过检查之前试验的 Git 历史记录在某些任务上获得了不公平的优势。如果多个不同的试验因为环境中相同的限制（如 CPU 内存不足）而失败，这些试验就不是独立的，因为它们受同一因素影响，评测结果对衡量 Agent 性能就不可靠了。

**第 5 步：精心设计评分器**

如上所述，优秀的评测设计涉及为 Agent 和任务选择最佳评分器。我们建议在可能的情况下选择确定性评分器，在必要时或需要额外灵活性时使用 LLM 评分器，并审慎使用人工评分器进行额外验证。

有一种常见的直觉是检查 Agent 是否遵循了非常具体的步骤，比如按正确顺序的工具调用序列。我们发现这种方法过于僵化，导致测试过于脆弱，因为 Agent 经常找到评测设计者未曾预料的有效方法。为了不过度惩罚创造力，通常更好的做法是对 Agent 产生的成果评分，而不是它走过的路径。

对于有多个组成部分的任务，要设置部分得分。一个正确识别问题并验证了客户信息但未能处理退款的支持 Agent，比一个立即失败的 Agent 明显更好。在结果中体现这种成功的连续谱很重要。

模型评分通常需要精心迭代来验证准确性。LLM 作为裁判的评分器应与人类专家密切校准，以确保人类评分和模型评分之间几乎无分歧。为避免幻觉，给 LLM 一个退出机制，比如当它没有足够信息时返回"Unknown"的指令。创建清晰、结构化的评分标准来评估任务的每个维度，然后用独立的 LLM 裁判分别评估每个维度，而非用一个 LLM 评估所有维度，这也有帮助。一旦系统稳健，偶尔使用人工审查就足够了。

有些评测存在微妙的失败模式，即使 Agent 表现良好也会导致低分，因为 Agent 因评分 Bug、Agent 框架约束或模糊性而无法完成任务。即使是经验丰富的团队也可能遗漏这些问题。例如，[Opus 4.5 在 CORE-Bench 上最初得分 42%](https://x.com/sayashk/status/1996334941832089732)，直到一位 Anthropic 研究人员发现多个问题：当期望值为"96.124991…"时，严格的评分将"96.12"判为错误；模糊的任务规范；无法精确复现的随机性任务。在修复 Bug 并使用较宽松的脚手架后，Opus 4.5 的得分跃升至 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645)其时间跨度基准测试中有几个配置错误的任务，要求 Agent 优化到声明的分数阈值，但评分要求超过该阈值。这反而惩罚了遵循指令的模型如 Claude，而那些忽略声明目标的模型获得了更好的分数。仔细双重检查任务和评分器可以帮助避免这些问题。

让评分器能够抵御绕过或取巧。Agent 不应该能轻易"作弊"通过评测。任务和评分器的设计应确保通过评测确实需要解决问题，而非利用非预期的漏洞。

### 长期维护和使用评测

**第 6 步：检查记录**

除非你阅读来自多次试验的记录和评分，否则你不会知道评分器是否工作良好。在 Anthropic，我们投资构建了查看评测记录的工具，并定期花时间阅读它们。当任务失败时，记录会告诉你究竟是 Agent 犯了真正的错误，还是你的评分器拒绝了一个有效的解决方案。它通常还会揭示 Agent 和评测行为的关键细节。

失败应该是令人信服的：很清楚 Agent 哪里做错了以及为什么错了。当分数无法提升时，我们需要确信这是因为 Agent 表现问题而非评测问题。阅读记录是验证评测是否衡量了真正重要内容的方式，这是 Agent 开发中的一项关键技能。

**第 7 步：监控能力评测是否饱和**

100% 通过率的评测能跟踪回归，但不能为改进提供信号。**评测饱和**是指 Agent 通过所有可解任务，没有改进空间的情况。例如，SWE-bench Verified 的得分今年从 30% 开始，前沿模型现在接近 80% 以上的饱和水平。随着评测接近饱和，进展也会放缓，因为只剩下最困难的任务。这会让结果具有欺骗性，因为大幅的能力提升会表现为分数的微小增长。例如，代码审查初创公司 [Qodo](https://www.qodo.ai/) 最初对 Opus 4.5 并不感冒，因为他们的一次性编程评测没有捕捉到更长、更复杂任务上的提升。于是他们开发了一个新的 Agent 评测框架，更清晰地呈现了进展。

作为原则，在有人深入研究评测细节并阅读一些记录之前，我们不接受评测分数的表面值。如果评分不公平、任务模糊、合法解决方案被惩罚、或者框架约束了模型，评测就应该修正。

**第 8 步：通过开放贡献和维护保持评测套件长期健康**

评测套件是一个活的产物，需要持续关注和明确的归属才能保持有用。

在 Anthropic，我们试验了各种评测维护方法。最有效的方法是建立专门的评测团队来负责核心基础设施，而领域专家和产品团队贡献大多数评测任务并自行运行评测。

对 AI 产品团队来说，拥有并持续迭代评测应该像维护单元测试一样常规。团队可能为"在早期测试中有效"但未能满足非明示期望的 AI 功能浪费数周时间，而这些期望本可以由精心设计的评测在早期就暴露出来。定义评测任务是压力测试产品需求是否足够具体、可以开始构建的最佳方式之一。

我们建议实践评测驱动开发：在 Agent 能够满足能力之前先构建评测来定义计划的能力，然后迭代直到 Agent 表现良好。在内部，我们经常构建今天"还可以"但赌的是模型几个月后能做什么的功能。以低通过率起步的能力评测让这一点清晰可见。当新模型发布时，运行套件能快速揭示哪些赌注得到了回报。

最接近产品需求和用户的人最适合定义成功。以当前的模型能力，产品经理、客户成功经理或销售人员可以使用 Claude Code 以 PR 的形式贡献评测任务——让他们做！或者更好的是，主动赋能他们。

## 评测如何与其他方法结合以全面理解 Agent

自动化评测可以在数千个任务上对 Agent 运行，无需部署到生产环境或影响真实用户。但这只是理解 Agent 表现的众多方法之一。完整的画面包括生产监控、用户反馈、A/B 测试、手动记录审查和系统化人工评估。

理解 AI Agent 表现的方法概览

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| **自动化评测**<br>*在无真实用户的情况下程序化运行测试* | - 迭代更快<br>- 完全可复现<br>- 不影响用户<br>- 可在每次提交时运行<br>- 无需生产部署即可大规模测试场景 | - 前期构建投入更大<br>- 随产品和模型演进需要持续维护以避免漂移<br>- 如果不匹配真实使用模式可能造成虚假信心 |
| **生产监控**<br>*跟踪线上系统的指标和错误* | - 大规模揭示真实用户行为<br>- 发现合成评测遗漏的问题<br>- 提供 Agent 实际表现的真实基准 | - 被动的；问题到达用户后才知晓<br>- 信号可能有噪声<br>- 需要投入仪器化建设<br>- 缺乏评分所需的真实标准 |
| **A/B 测试**<br>*用真实用户流量比较变体* | - 衡量真实用户结果（留存、任务完成率）<br>- 控制混淆变量<br>- 可扩展且系统化 | - 慢；需要数天或数周才能达到显著性，且需要充足流量<br>- 只能测试已部署的改动<br>- 对于指标变化的底层"原因"信号较弱，除非能彻底审查记录 |
| **用户反馈**<br>*明确的信号，如踩/差评或 Bug 报告* | - 发现你没预料到的问题<br>- 附带来自真实用户的真实示例<br>- 反馈通常与产品目标相关 | - 稀疏且自我选择<br>- 偏向严重问题<br>- 用户很少解释*为什么*失败<br>- 非自动化<br>- 主要依赖用户发现问题可能对用户体验产生负面影响 |
| **手动记录审查**<br>*人工阅读 Agent 对话* | - 建立对失败模式的直觉<br>- 发现自动化检查遗漏的细微质量问题<br>- 帮助校准"好"的标准并掌握细节 | - 耗时<br>- 不可扩展<br>- 覆盖率不一致<br>- 审查者疲劳或不同审查者可能影响信号质量<br>- 通常只给出定性信号而非明确的定量评分 |
| **系统化人工研究**<br>*由训练有素的评分员对 Agent 输出进行结构化评分* | - 来自多位人类评分员的黄金标准质量判断<br>- 能处理主观或模糊任务<br>- 为改进模型评分器提供信号 | - 相对昂贵且周期长<br>- 难以频繁运行<br>- 标注者间分歧需要协调<br>- 复杂领域（法律、金融、医疗）需要人类专家进行研究 |

这些方法映射到 Agent 开发的不同阶段。自动化评测在上线前和 CI/CD 中尤其有用，作为质量问题的第一道防线在每次 Agent 改动和模型升级时运行。生产监控在上线后启动以检测分布漂移和预料之外的真实世界故障。A/B 测试在你有足够流量时验证重大变更。用户反馈和记录审查是弥补缺口的持续实践：持续分类反馈，每周抽样阅读记录，根据需要深入挖掘。将系统化人工研究保留用于校准 LLM 评分器或评估主观输出（以人类共识作为参考标准）。

如同安全工程中的[瑞士奶酪模型](https://en.wikipedia.org/wiki/Swiss_cheese_model)，没有单一的评测层能捕捉所有问题。通过多种方法的组合，从一层漏掉的失败会被另一层捕捉到。

最有效的团队将这些方法组合起来：自动化评测用于快速迭代，生产监控用于获取真实基准，定期人工审查用于校准。

## 结论

没有评测的团队会陷入被动循环——修复一个故障又引发另一个，无法区分真正的回归和噪声。早期投入的团队发现情况完全相反：开发加速，失败变成测试用例，测试用例防止回归，指标取代猜测。评测为整个团队提供了清晰的攀登目标，把"Agent 感觉变差了"变成可操作的事情。价值会复利增长，但前提是你把评测当作核心组件而非事后补充。

不同 Agent 类型的模式有所不同，但本文描述的基本原则是不变的。尽早开始，不要等待完美的套件。从你看到的失败中获取真实任务。定义明确、稳健的成功标准。精心设计评分器并组合多种类型。确保问题对模型来说足够困难。迭代评测以提升信噪比。阅读记录！

AI Agent 评测仍然是一个新兴、快速发展的领域。随着 Agent 承担更长的任务、在多 Agent 系统中协作、处理越来越主观的工作，我们需要不断调整技术。我们会随着学习更多而持续分享最佳实践。

## 附录：评测框架

多个开源和商业框架可以帮助团队实现 Agent 评测，而无需从零构建基础设施。正确的选择取决于你的 Agent 类型、现有技术栈以及是否需要离线评测、生产可观测性或两者兼顾。

[Harbor](https://harborframework.com/) 专为在容器化环境中运行 Agent 而设计，提供跨云提供商大规模运行试验的基础设施以及定义任务和评分器的标准化格式。Terminal-Bench 2.0 等流行的基准测试通过 Harbor 注册中心发布，方便用户在运行自定义评测套件的同时运行成熟的基准测试。

[Braintrust](https://www.braintrust.dev/) 是一个将离线评测与生产可观测性和实验跟踪相结合的平臺——适合需要在开发中迭代同时监控生产质量的团队。其 `autoevals` 库包含预先构建的事实性、相关性等常见维度的评分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供追踪、离线和在线评测以及数据集管理，并与 LangChain 生态紧密集成。[Langfuse](https://langfuse.com/) 作为自托管的开源替代方案提供类似能力，适合有数据驻留要求的团队。

[Arize](https://arize.com/) 提供 Phoenix，一个用于 LLM 追踪、调试和离线或在线评测的开源平臺，以及 AX，一个为规模化、优化和监控而扩展 Phoenix 的 SaaS 产品。

许多团队组合使用多种工具，自行开发评测框架，或仅使用简单的评测脚本作为起点。我们发现，虽然框架可以是加速进度和标准化的宝贵方式，但它们的好坏取决于你通过它们运行的评测任务。通常最好的做法是快速选择一个适合你工作流的框架，然后将精力投入到评测本身——迭代高质量的测试用例和评分器。
