## 一、文章在讲什么（30 秒版本）

阿里云 AgentLoop 用一个 64 分钟实操演示走完了整个数据飞轮：**接入（OTel 探针）→ 观测 → 审计 → 数据集 → 评估（黄金指标 → Rubric → 评估器 → 评估任务）→ 实验（离线平台回测 + 题目级 Rubric）→ 经验库（自动挖掘）**，并用消融实验证明经验注入收益（耗时 ↓30%~40%、成本 ↓20%~47%）。核心论点：Agent 上线只是起点，持续性调优的系统化能力才决定 Agent 好不好用；而"证明变好了"必须靠可复现的评估 + 回测实验，不能靠感觉。

## 二、核心观点（带面试说法）

```text
1. 数据飞轮：7 个环节首尾相接，环环有明确输入输出
   [面试说法] 数据飞轮 = 运行数据 → 评估样本 → 优化动作 → 经验资产的循环；
              评估的产出是实验的输入，实验结论指回下一轮评估。
              关键不在某一环多强，而在"环节之间首尾相接"。

2. 评估体系两层结构：评估器（Evaluator）vs 评估任务（Evaluation Task）
   [面试说法] 评估器 = 考卷 + 评分标准（怎么评、可复用、与数据无关）；
              评估任务 = 组织一场考试（评什么数据、何时评）。
              分开的两层让"标准"成为资产：标准不变，试卷可以换学生。
   ★ 直接类比：我 CoT 质检里的"质检规则定义"= 评估器，"批量质检任务"= 评估任务。

3. 黄金指标（Golden Metrics）→ AI 拆解 → Rubric
   [面试说法] 先回答"这个场景什么算好"，再拆成"每个指标什么情况打什么分 + 权重 + 总分公式"。
              Rubric 把专家脑子里"这个回答不行"的隐性判断，固化成可复用、可回测的显性标准。
              AI 拆解是提效手段：你懂业务时人工写，AI 只是加速，不能替你定义"好"。

4. 评估器类型：Code 评估 vs Agent 评估
   [面试说法] Code 确定便宜但只覆盖规则可表达指标；Agent 评估吃语义（切题/流程合理），
              代价大 → 引出采样配置（只采样 badcase 关心的量，比如 100 条）。
              这是"量化指标 + 成本约束"的标准权衡（工程视角）。

5. 轨迹（Trajectory）vs Trace：评估要用轨迹数据
   [面试说法] Trace 是微服务视角（谁调谁、耗时）；Trajectory 是智能体视角
              （user prompt + 每步调用 + 思考 + 输出）。
              评 Agent 回答质量和执行过程必须用轨迹数据——只看结果会漏掉"蒙对的"。

6. 评估器三变量与输出定义：input / output / agent_trajectory + 结构化输出
   [面试说法] 三个参考变量让评估器既能评结果也能评过程（轨迹）；
              输出定义（score / raw_weighted_score / final_score / decision /
              scenario_type / summary / rubric_version）保证"分数可解释 + 可过滤 + 标准可追溯"。
              rubric_version 留版本号，才能区分"分数变化是 Agent 变了还是标准变了"。

7. 分数分析方法论：先查"尺子"再看"东西"
   [面试说法] 分数变低 → 先查 Rubric 是否模糊（同版本多次评估波动 = 标准问题）；
              再比不同版本差异（版本间稳定差异 = 真实优化效果）。
              避免最常见的误判：把"尺子不准"当成"东西变差"。
   ★ 这与评测归因（eval attribution）是同一件事的两种表述。

8. 题目级 Rubric：badcase 场景下每道题绑自己的评估标准
   [面试说法] 线上抓 badcase 时问题发散，只能用通用标准；一旦进了实验集，
              每道题应该绑定自己的 Rubric（数据集 schema 加 rubric 列 →
              评估器按传入评估，输出 rubric_id/score/reason/item_scores → 实验侧读取）。
              只用一套通用 Rubric 评不同题目，优化时会失去方向——
              哪道题低分，就该补哪道题的能力点。这是评测"粒度"问题（策略视角）。

9. 离线实验平台：数据不出内网（云端控制台 ↔ 内网实验平台 ↔ 本地 Agent）
   [面试说法] Agent 部署在客户内网，云端够不着、数据搬出去也不现实。
              内网平台：绑定 AgentSpace/region + 最小权限 AK（FullAccess、专用身份）+
              连接多个本地 Agent + 定时调度（每 5 分钟回归，生产配每天）。
              "数据不出内网，能力不打折扣"——数据治理红线驱动的产品设计。

10. 调用代码适配有状态 Agent：建 Session → 发消息 → 取响应
    [面试说法] 平台默认假设无状态 API；有状态（Claude Agent SDK 类）必须适配
               自定义调用代码，单题测试（如『我的位置在哪里』）验连通后再发起实验。
               工程视角：连通性验证是先行的最小冒烟测试。

11. 消融实验验证经验注入：耗时 ↓30%~40%、成本 ↓20%~47%
    [面试说法] 经验库自动化沉淀通用优化（工具调用执行情况、延时、准确率、路径），
               但面对真实业务还需实验严格验证"经验到底帮没帮上"——数字说话，不能凭感觉。
               ★ 直观信号：同一请求换 Session 重发，注入前约 12 步 → 注入后步骤显著减少
               （经验让 Agent 绕过试错），但"步骤少"不等于"更好"，仍要上消融实验证明。

12. 两种调优模式互补
    [面试说法] 模式一（人类专家驱动）：专家知识 → 评估标准 → 数据沉淀 → 回测验证，
               适合业务初期建立质量标准；模式二（经验库全自动）：平台从轨迹自动挖经验。
               模式一兜住业务底线，模式二在标准之上自动增益。

13. 经验库机制：可追溯的自动挖掘（Part 5）
    [面试说法] 算法从轨迹自动挖成功/失败模式 → 沉淀经验资产 → Skill 召回后注入上下文。
               关键设计：① 每条经验可回查来源 Trace（不是黑箱结论，排障必需）；
               ② 召回"宁缺毋滥"——无相关经验时不召回，防错误经验误导 Agent；
               ③ 集成靠一个 Skill + 三个权限（白名单 / Shell 权限 / allow shell，缺一不召回）。
    ★ 这是"经验作为可复用资产"的落地——和用户知识库"连接 > 知识量"同构：轨迹→经验→复用。

14. 经验注入的五个可调参数（Part 5 最核心干货 ★）
    [面试说法] 经验注入不是"塞进去就好"，注入方式直接影响效果甚至帮倒忙，必须消融：
               ① 召回阈值：1=最相似/0=最不相似；太高漏召回、太低召噪声 → 最终选 0.6；
               ② 注入条数：只取 top1，多了稀释注意力、挤占上下文（不是越多越好）；
               ③ 注入位置：真实问题 → 业务使用规则 → top1 经验（位置影响采纳程度）；
               ④ 经验瘦身：只留标题摘要/使用条件/关键结论 + 限字数（信噪比 > 冗余细节）；
               ⑤ 防护护栏：声明"经验只是历史参考"，给模型留"不照办"的余地（经验来自过去，
                  不一定适用当前）。
    ★★ 这五条 = context engineering 的具体工程手册，可直接迁移到 RAG / 用户纠正数据注入 /
       few-shot 选择——"检索到 ≠ 用得好"，注入策略本身要做实验验证。
```

## 三、与相关文章的对比

```text
- papers/06.eval-to-training-loop（评测→训练闭环，SWE-smith）：
  AgentLoop 是同一"数据飞轮"理念的可操作平台实例——SWE-smith 是闭环的机制设计，
  AgentLoop 是闭环落地成产品（接入/评估/实验/经验库四件套流水线）。
  面试时可先讲机制（06）再讲落地（13），形成"理论-实践"双证据。

- papers/03.aihot-real-world-agent-evals（真实业务场景评测）：
  03 讲"真实场景怎么评"（评测集构建），13 讲"上线后怎么持续评"（在线评估 + 回测）。
  题目级 Rubric = 03 里"真实场景标准定义"的工程化表达：每条 badcase 绑定自己的标准。

- papers/04.swe-bench-anatomy（benchmark 事实标准）：
  SWE-bench 定义"一次任务→补丁→测试"标准；AgentLoop 的评估器输出的
  final_score/decision/evidence 是"运营期标准"，两者都是"把模糊好坏变成可判定信号"。

- papers/11.xiaohongshu-from-zero-eval（评测五件套）：
  11 是方法论地图（任务/标准/数据/判定/分析），13 是这套五件套在 AgentLoop 里的
  具体配置项（评估器/任务/采样/字段映射/大盘）——可以互相印证着讲。

- notebook 的搜索系统全景（评测体系）：
  "评测：从黄金指标到 Rubric" 与搜索相关性评测同构：都是"定义标准 → 量化打分 → 迭代标准"。
```

## 四、面试故事模板

```text
30 秒版：我独立设计过 CoT 质检的多层级联分类质量门控（4 个 Stage、5000+ 数据、79% 合格率）；
        它和 AgentLoop 数据飞轮的评估体系是同一套逻辑：定义标准（Rubric）→ 量化打分 →
        badcase 沉淀 → 回测验证。看完这套飞轮的完整实操，我对"评测驱动优化"有了产品级理解。

2 分钟版（背景 → 设计 → 做法 → 结果）：
  背景：Agent 上线后"好不好"说不清，零散改 Prompt 不可复现。AgentLoop 飞轮给出答案。
  设计决策：
  ① 评估分两层——评估器（标准资产，可复用）与评估任务（执行配置）；
  ② 黄金指标用 AI 拆成 Rubric（0-4 分档 + 权重 + 总分公式）；
  ③ Agent 评估比 Code 覆盖更全（语义），但贵 → 采样降本；
  ④ 我的 CoT 质检 Gate 同理：每层定义判定逻辑（=Rubric），批量抽查（=评估任务），
     不合格样本回流（=badcase 沉淀）。
  做法：评估结果给出"为什么低分"（证据字段）；坏案例入数据集 → 实验回测。
  结果：能用 0.25/0.5 这样精确的分数定位"缺哪项能力点"，再针对性补。
  错题复盘版：最初把两道题的 Rubric 写进同一个评估器 → 分数失去指向性；
             改成题目级 Rubric（每道题绑定自己的标准）后才有指导意义。
             教训：评测粒度要和任务粒度对齐——这跟我的分层质检"每层判断逻辑独立"同理。

5 分钟版（加四视角）：
  PM：让"好"的定义成为团队资产（Rubric），而不是专家脑里的隐性判断；
  算法：想清楚量化指标（回答质量 60% + 执行过程 40% 加权）、验证方法（多次评估看均值、
        消融实验）、归因（分数低先查 Rubric 再比版本）；
  工程：采样/并发上限（最大并发 1，避免后端被打爆）、定时调度（5 分钟回归）、
        API 无状态 vs 有状态适配、连通性冒烟测试；
  策略：实验计划（数据集+评估器+变量映射/版本号）、离线平台解决"数据不出内网"、
        分数方法论（先查尺子再看东西）、题目级 Rubric 粒度。
```

## 五、知识树连接

```text
- 评测体系(Evaluation) ← → 数据飞轮闭环：评估产出是实验输入，实验结论指回评估（承上启下）
- 评测体系 ← → Rubric：把"好"拆成可判定细则（评分标准+权重+总分），评估从凭感觉→可复现
- 评测体系 ← → 题目级 Rubric：评测粒度与任务粒度对齐（badcase 级绑定标准）
- 评估框架 ← → 数据生产 Pipeline：评估器 = 质检规则；评估任务 = 质检任务；
  badcase 回流 = 不合格样本回流（与 CoT 质检项目同构）
- 实验设计 ← → 离线实验平台：指标/对照组（版本）/验证方法（回测、窗口均值、消融）
- Agent 可观测性 ← → OTel 探针 + Trajectory：观测先行，评估才有数据
- 数据治理 ← → 数据不出内网：合规红线驱动架构（内网执行引擎 + 云端大盘）
```
