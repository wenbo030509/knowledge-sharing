# 精读笔记：没有线上数据，如何为 Agent 构建冷启动评测集

> 来源：小红书 / Brench，2026-08-28 发布
> 阅读日期：2026-08-30
> 重要性：⭐⭐⭐ 直接对标 Agent PM / 评测主线——把"没有线上数据怎么评测"这个关键问题，从能力地图、金种子、受控变异、三层 Oracle 到六数据桶和发布门禁讲透了，可执行度极高

---

## 一、文章在讲什么（30 秒版本）

没上线就没有真实用户轨迹，但 PRD、SOP、工具 schema、错误码、权限矩阵和专家经验已经藏着大量可验证约束。冷启动评测集就是把这些材料翻译成"能重置环境、能执行任务、能自动判分"的案例：**人先定义能力地图 + 20-50 条金种子，LLM 只在规定维度内做受控变异，业务规则验收，程序验证最终状态。** 核心是"能力覆盖 + 可追溯 + 可重置 + 三层 Oracle + 六数据桶 + 安全门禁"这套工程化的评测产品。

---

## 二、核心观点（带面试说法）

### 观点 1：不要用 LLM 自由出题 + LLM 互相判分
出题模型、答题模型、裁判模型会共享相似偏好——三者都认可，业务人员却不认可。更稳的是"人定能力空间和金种子，LLM 只在规定维度受控变异，程序/规则验收"。

**面试说法：** "我不会让大模型自己出题再自己当裁判，那会形成共同偏好，业务侧不认。我的做法是能力空间和 GT 从业务约束来，LLM 只扩写表述，最终状态用程序验证。"

### 观点 2：先覆盖能力，再谈样本量
200 条全在测订单查询，退款/权限/失败恢复仍是空白。先建 Agent Capability Map，再按用户目标、任务复杂度、输入质量、系统状态、风险等级五维构造评测矩阵，而不是做笛卡尔积。

**面试说法：** "判断评测集好不好，先看它覆盖了哪些能力和风险，而不是有多少题。我会分维度报告覆盖率——业务能力、工具、异常状态、风险、多轮，不能合成一个数字。"

### 观点 3：GT 描述的是 expected_state，不是 expected_answer
"退 80 元"要验证的是退款记录、余额变化、工具只执行一次、权限、通知引用真实编号，而不是某句固定回复。最终回复可以有多种合法表达。

**面试说法：** "我把 GT 定义成世界终态而非参考答案。这样既允许 Agent 有多种合法路径，又能防止它'表面说退款成功、数据库其实没变'。"

### 观点 4：变量/状态/故障要分细，不能统一写成 timeout
工具故障至少区分"未执行且超时 / 已成功但响应超时 / 部分成功 / 空结果 / 重复请求 / 脏状态 / 并发修改 / 延迟可见"。其中"成功但返回超时"最危险——Agent 直接重试会二次退款。

**面试说法：** "我评估一个 Agent 时会把 failure 分细，尤其是'成功但响应超时'这种最危险的歧义——重试就是重复扣款。粗粒度的 timeout 会掩盖真实系统风险。"

### 观点 5：三层 Oracle，优先级 程序 > 规则 > LLM Judge > 人工抽检
Outcome Oracle（事情办成没）、Behavior Oracle（过程合不合规，只查 invariant 不强制标准路径）、Response Oracle（解释是否清晰可信）。安全事件不能被平均分抵消，高风险阈值常预登记为零。

**面试说法：** "我判分先看结果、再看行为、最后看表达。程序能验证的绝不交给 LLM Judge，Judge 只处理开放表达并允许返回 unknown。安全门禁是硬门槛，不能和成功率加权平均。"

### 观点 6：评测集 = 版本化数据产品，六个数据桶各司其职
Gold（人工金种子）、Synthetic Coverage（覆盖矩阵）、Challenge（边界/对抗）、Regression（已修失败+证据链）、Canary（30-50 条快速失败层）、Hidden Test（封存）。Canary 先跑，退化就停，不烧完整预算。

**面试说法：** "我把评测集当数据产品做版本化。改 prompt/模型/tool schema 先跑 Canary 快速失败，再跑完整发布评测；Hidden Test 按 seed family 切分防止语义泄漏。"

### 观点 7：可重置环境是评测数据的一部分
数据库/权限/工具/时钟/缓存/外部依赖都要恢复到 fixture，否则上一条退款影响下一条、trial 之间产生相关失败，破坏独立试验假设。Anthropic 甚至报告过 Agent 从前序 trial 的 Git history 拿到不公平线索。

**面试说法：** "环境重置不是测试基础设施的附属，而是 case 定义的一部分。不重置就会有状态污染和泄漏，结果根本不可信。"

### 观点 8：optimization metrics 与 guardrail metrics 绝不加权
成功率/延迟/成本可权衡；越权/重复扣款/隐私泄漏是门禁。Task Success 98% + Unauthorized 0.2% ≠ 95 分。同时要检查"正确拒绝的代价"，避免一律拒绝刷虚假安全分。

**面试说法：** "我绝不会把安全事件和成功率做加权。门禁是独立阈值，重复扣款这类就是零容忍；而且要看误拒绝代价，防止 Agent 用'什么都不做'刷安全分。"

## 四、面试故事模板

> 直接把你的 CoT 质检 / 评测 Pipeline 项目升级成"冷启动评测集"叙事。

**故事主线：**
1. **背景**：CoT 质检项目刚起步，没有历史标注/线上数据，但 PRD、SOP、判分规范、工具 schema 已经存在。
2. **方法**：我先建能力地图（哪些质检能力、哪些风险必须覆盖），人工做一批金种子（两位业务可独立判同、有参考解通过全部 grader、断言可追溯、能区分 Agent/工具/环境/grader 错误）。
3. **扩样**：用 mutation operators 只在语言、参数边界、状态故障、权限对抗维度做受控变异，再过语义去重、规则校验、可解性、分布四道验收。
4. **判分**：三层 Oracle——程序验证结果状态、规则检查行为 invariant、LLM Judge + 人工抽检处理开放表达。
5. **闭环**：按 Gold/Coverage/Challenge/Regression/Canary/Hidden 六桶落盘，Canary 快速失败 + Hidden 防泄漏，上线后用真实轨迹回流替换冷启动假设。
6. **收尾**：这是把"没有线上数据"从没法评测，变成"每条 case 都能回答来源、初始状态、允许/禁止、证据判分"四件事的可复核评测产品。
