## 引言：为什么不建议一上来研究概念

如果从零开始学大模型评测，我不建议一上来就研究各种 Benchmark，也不建议先钻进 LLM-as-a-Judge、Rubric、pass@k 这些概念里。因为在理解这些细节之前，需要先回答两个更基础的问题：
1. **一套完整的 Agent 评测系统是怎么运转的？**
2. **一道完整的 Agent 评测任务究竟要包含什么？**

## 如果只看两份材料，我会推荐：

- 第一份：Anthropic 的《Demystifying evals for AI agents》。
- 第二份：Harbor 框架的 Task Structure 文档。

它们刚好回答了上面两个不同层次的问题：
- 《Demystifying evals》解释评测系统有哪些零件，以及这些零件为什么存在。
- Harbor 展示如何把其中一道任务做成真正能够运行的东西。

## 第一份材料：Anthropic 讲的是"评测系统如何运转"

Anthropic 的文章首先定义了 Agent 评测中的一组基本概念：
- 一道具体的测试叫作 **Task**；
- Agent 对这道题的一次独立尝试叫作 **Trial**；
- 完整的工具调用和交互记录叫作 **Transcript / Trajectory**；
- 任务结束后环境中的最终状态叫作 **Outcome**；
- 负责判断结果是否正确的逻辑叫作 **Grader**。

在这些概念之外，它还区分了两个经常被混淆的 Harness：
- **Agent Harness** 是把模型变成 Agent 的系统，包括提示词、工具、上下文管理和执行循环。
- **Evaluation Harness** 则是运行整场实验的基础设施：创建环境、启动 Agent、记录过程、执行评分，并汇总最终结果。

所以，当我们说"这个 Agent 得分更高"时，实际上测到的通常不是一个裸模型，而是**模型 + Agent Harness 共同构成的系统**。

文章接下来解释了为什么要做评测：
- 在产品早期，团队可以依靠人工测试、内部试用和直觉快速迭代。
- 但随着 Agent 的任务越来越多、系统越来越复杂，团队会逐渐陷入一种被动状态：用户说效果变差了，团队却不知道是不是真的变差；修复了一个问题，又不知道是否破坏了其他能力；新模型发布后，也只能重新进行大量人工测试。

评测的作用，就是把"感觉变差了"变成一组可以重复运行和定位的问题。失败可以被沉淀成新的测试任务；修改前后可以运行同一套任务；能力提升和能力退化也可以被区分出来。

然后文章开始讨论 Agent 应该如何评分。它将 Grader 大致分为**代码评分、模型评分和人工评分**三类，并分别介绍它们适合判断什么。

它还进一步区分了 **Capability Eval 和 Regression Eval**：
- 前者关注 Agent 目前还不会做什么，为能力提升提供目标；
- 后者关注 Agent 过去会做的事情现在是否仍然稳定，用来防止系统发生退化。

在此基础上，Anthropic 又分别讨论了 Coding Agent、Conversational Agent、Research Agent 和 Computer Use Agent 的评测特点。不同 Agent 的任务形态不同，但背后的共同问题没有改变：
- Agent 在什么环境里行动？
- 它最终完成了什么？
- 我们如何稳定地判断它是否成功？

文章还专门讨论了 Agent 的随机性。同一个 Agent 面对同一道任务，第一次可能成功，第二次也可能失败。因此，一次运行不能完整代表能力。我们既可以关心"尝试多次后至少成功一次"，也可以关心"连续多次都能稳定成功"。这对应两种完全不同的产品要求。

最后，Anthropic 给出了一条从零开始建设评测的路线：
1. 从真实失败和人工测试中收集少量任务；
2. 把任务要求写清楚；
3. 准备参考解法；
4. 建立稳定、隔离的环境；
5. 组合不同的 Grader；
6. 反复阅读失败轨迹；
7. 随着模型进步持续增加新任务。

所以，这篇文章讲的是：**一套可信的 Agent 评测系统，需要由哪些部分组成，以及这些部分应该如何协同工作。**

## 第二份材料：Harbor 讲的是"一道任务如何落地"

看完 Anthropic，我们知道了 Task、Trial、Outcome、Grader 和 Harness 分别是什么。但接下来还会遇到一个很实际的问题："我现在想做第一道 Agent 评测任务，具体应该准备哪些文件？"Harbor 的 Task Structure 文档回答的就是这个问题。

Harbor 是一个用于评估和优化 Agent 的框架，也是 Terminal-Bench 目前使用的官方 Harness。它把一道 Task 组织成一个可以直接运行的目录。最核心的部分包括：
- **`instruction.md`**：写给 Agent 的任务说明。
- **`task.toml`**：任务的配置和元数据。
- **`environment/`**：Agent 完成任务所处的环境。
- **`solution/`**：一条经过验证的参考解法。
- **`tests/`**：判断 Agent 是否完成任务的测试程序。

这套结构看起来很工程化，但它表达了一个非常重要的思想：**一道 Agent 评测任务，不只是一段 Prompt，而是一个完整的实验包。**

- `instruction.md` 规定 Agent 要完成什么；
- `environment/` 提供完成任务需要的文件、依赖、工具和系统状态；
- `solution/` 证明这道任务至少存在一条可行解；
- `tests/` 负责检查 Agent 最终有没有完成任务；
- `task.toml` 则规定实验如何运行，包括时间限制、网络权限、计算资源和评分环境等条件。

Harbor 的文档还介绍了完整的任务创建流程：
1. 先初始化任务目录；
2. 再写任务说明和环境；
3. 手动验证解题思路；
4. 把正确路径写成 Oracle Solution；
5. 编写 Tests；
6. 先运行 Oracle，确认参考解法能够通过；
7. 再运行真实 Agent，并在 Viewer 中检查它的 Trajectory、日志和最终产物。

因此，Harbor 关心的是：**如何把一道题封装成可运行、可复现、可检查的工程对象。**

## 举个例子：差旅报销审核 Agent

假设我们要评测一个"差旅报销审核 Agent"。我们给它 10 份报销申请、发票、行程记录和公司差旅制度，要求它判断每笔费用是否合规，计算应报销金额，生成审核结果，并更新报销系统中的状态。

按照 Anthropic 的语言：
- 这是一道 **Task**；
- Agent 独立完成一次审核，是一次 **Trial**；
- 它读取制度、核对票据、计算金额、调用数据库的过程，是 **Trajectory**；
- 任务结束后生成的审核文件，以及数据库中真正发生的状态变化，是 **Outcome**；
- 检查金额、合规判断和数据库状态的逻辑，是 **Grader**；
- 如果我们再增加住宿费、交通费、招待费、缺失票据等不同任务，它们共同组成一个 **Evaluation Suite**。

再按照 Harbor 的结构：
- 任务要求被写进 `instruction.md`；
- 差旅制度、票据和模拟报销系统被放进 `environment/`；
- 专家预先完成的一份正确审核结果被放进 `solution/`；
- 检查审核文件和数据库状态的程序被放进 `tests/`；
- 运行时间、网络权限和资源限制则被写进 `task.toml`。

到这里，一道模糊的"让 Agent 审核报销单"，才真正变成了一道可以运行和评分的评测任务。
