## 二、核心观点（带面试说法）

### 观点 1：先理解系统零件，再学指标
Task（一道测试）、Trial（一次独立尝试）、Trajectory/Transcript（过程记录）、Outcome（终态）、Grader（判分逻辑）；还有两个易混的 Harness——Agent Harness（模型→Agent 的系统）与 Evaluation Harness（跑实验的基础设施）。

**面试说法：** "我们说'这个 Agent 得分更高'时，测的其实不是裸模型，而是模型 + Agent Harness 共同构成的系统。所以评测结果要标注是哪个 harness、哪个 prompt、哪个环境。"

### 观点 2：评测把"感觉变差了"变成"可重复定位的问题"
复杂系统下，用户说变差、修一处怕破坏别处、换模型就要重测。评测让失败沉淀成任务、让修改前后可比、让能力提升与退化可区分。

**面试说法：** "评测的本质是让'体感变差'变成一组能重复运行、能定位的问题。这样每次改动都能判断是提升还是退化，而不是拍脑袋。"

### 观点 3：Capability Eval 与 Regression Eval 是攻守两面
前者看"还不会什么"，为能力提升提供目标；后者看"过去会的现在是否仍稳定"，防退化。

**面试说法：** "我把评测分攻守：能力评测是设计难任务拉上限，回归评测是保证既有能力不塌。这正是我质检项目里'新增规则（能力）'和'稳定规则纳入常规检查（回归）'的对应。"

### 观点 4：随机性 → pass@k vs pass^k 对应不同产品要求
同一 Agent 同一任务，这次成下次败。"多次至少成功一次"（pass@k）与"连续多次都成功"（pass^k）是两种完全不同的产品要求。

**面试说法：** "如果面向真实客户，我更关心第一次能否完成、连续是否可靠（pass^k），而不是'多试几次总能成一次'。这两个指标对应完全不同的产品标准。"

### 观点 5：一道评测任务 = 一个完整实验包，不是一段 Prompt
Harbor 把 Task 组织成可运行目录：`instruction.md`（要做什么）、`environment/`（环境/依赖/工具/系统状态）、`solution/`（可行参考解）、`tests/`（判完成）、`task.toml`（时间/网络/资源/评分条件）。

**面试说法：** "一道评测任务不只是一段 prompt，而是一个完整实验包——要说明、环境、参考解、测试和运行配置。缺了 environment 或 solution，题目根本无法复现和判分。"

### 观点 6：先跑 Oracle 再跑 Agent，用 Viewer 查轨迹
创建流程：初始化目录 → 写说明和环境 → 手动验证思路 → 写成 Oracle Solution → 写 Tests → 先跑 Oracle 确认参考解通过 → 再跑真实 Agent，在 Viewer 检查 Trajectory/日志/产物。

**面试说法：** "我建评测任务一定先跑 Oracle 参考解，确认题目本身可解、grader 可用，再去跑真实 Agent。否则 Agent 得 0 分可能是题目或环境问题，不是模型问题。"

## 四、面试故事模板

> 用"差旅报销审核 Agent"的框架，替换成你 CoT 质检 / 评测 Pipeline 的故事。

**故事主线：**
1. **概念**：先交代 Task/Trial/Trajectory/Outcome/Grader 五件套，说明你评测的是一道完整实验包而非一段 prompt。
2. **落地**：把质检任务封装成 `instruction.md`（规则说明）+ `environment/`（样例/工具/状态）+ `solution/`（参考质检答案）+ `tests/`（判分程序）+ `task.toml`（判分环境）。
3. **方法**：先跑 Oracle 参考解确认可解，再跑真实质检 Agent，用 Viewer/日志查失败轨迹，区分 Agent 错、规则错、环境错、grader 错。
4. **指标**：用 pass^1 看一次完成、用 pass^k 看稳定可靠，并区分能力评测与回归评测。
5. **闭环**：把真实失败沉淀为新任务，持续扩充 Evaluation Suite。
